## Code scanning (CodeQL)

### 1. `js/request-forgery` – Server-side request forgery (alert number not visible in the screenshot)
- **Severity:** Error (CodeQL level; GitHub severity label not visible). Branches: `main`, `develop`.
- **Where:** `server/src/proxy.ts:155` (`client.request(url, …)`), flow starts at the `url` query parameter of `GET /v1/proxy`.
- **Assessment: false positive (sanitizer not modelled), but in the most sensitive file of the server.** The proxy is a deliberate fetch-by-URL feature and is already SSRF-hardened (`docs/DECISIONS.md`): `checkUrl` (http/https only, no credentials, ports 80/443/8080/8443), host resolved and every answer checked by `isBlockedAddress` (loopback, private, link-local/metadata, CGNAT, ULA, multicast, reserved, v4-mapped/NAT64/6to4), connection pinned to the checked address through a custom `lookup` (no second DNS lookup, so no rebinding), redirects followed by hand (≤ 3, each hop re-checked), 2 MB / 10 s limits, content-type allow-list. CodeQL's query only knows its own sanitizers (allow-list comparisons, etc.) and does not recognise `isBlockedAddress`.
- **Planned fix:** no behavioural change to the guard. Options, to be decided by the maintainer:
  - (a) Dismiss as "false positive" with the justification above, after a test review that `proxy.test.ts` covers each block class, redirect re-check and pinning (add missing cases first).
  - (b) Restructure so the request is built from already validated parts (`host: address`, `servername`, `path` from `URL`) instead of passing the `URL` object; CodeQL may still flag it, so this is only worth it if it also makes the code clearer.
  - Recommendation: (a), with extra tests. Not touching the proxy logic.
- **Fix risk:** (a) none; (b) medium (SSRF guard, TLS host name handling) – needs your approval.

### 4. `js/incomplete-multi-character-sanitization` – Incomplete multi-character sanitization
- **Severity:** High. Branches: `main`, `develop`. Copilot Autofix could not produce a fix.
- **Where:** `web/src/connectors/google/calendar.ts:50-53` (`plainText`).
- **Assessment: real as a code defect, low practical impact.** `/<[^>]+>/g` is applied once, so `<scr<b>ipt>` leaves `<script>` behind. The result is stored as the event note and rendered by React as text (no `dangerouslySetInnerHTML`), so there is no script execution today; the text is however wrong/odd (and would be dangerous if a future view rendered notes as HTML).
- **Planned fix:** replace the regex chain by an inert parse, as `core/io/feed.ts` `plainText` already does (`DOMParser`, drop `script/style/…`, `textContent`), keeping the line breaks for `<br>`, `</p>`, `</div>`, `</li>` and the existing length limit; entities are then decoded by the parser (no manual `&amp;` chain, which is also the second CodeQL concern). Test: nested/broken tags (`<scr<b>ipt>`), entities (`&amp;lt;` must stay `&lt;`), line breaks, limit; jsdom environment marker.
- **Fix risk:** low (note text of imported Google events; output format of normal descriptions stays the same).

## Dependabot

### 1. `glib` (Rust) – Unsoundness in `Iterator`/`DoubleEndedIterator` for `glib::VariantStrIter`
- **Severity:** Moderate (CVSS v4 6.9). Manifest `web/src-tauri/Cargo.lock`. Affected `>= 0.15.0, < 0.20.0`, patched `0.20.0`; locked `0.18.5`.
- **Dependency kind:** transitive, never direct: `tauri` → `tray-icon` → `libappindicator` → `gtk` 0.18 → `atk`/`gdk`/… → `glib` 0.18.5 (also via `webkit2gtk`/`wry`). Dependabot reports that the latest installable version is 0.18.5.
- **Assessment: unreachable in what we ship.** `cargo tree -i glib --target x86_64-pc-windows-msvc` and `--target aarch64-linux-android` print nothing: glib is compiled only for Linux desktop targets (gtk3 backend of tao/wry). We publish a Windows exe and an Android APK, no Linux build; Linux only appears in CI (clippy/tests) and developer machines. We also do not call `VariantStrIter`.
- **Planned fix:** none possible from our side: glib 0.20 belongs to the gtk4-rs generation, while Tauri 2 still uses gtk3-rs (0.18). `cargo update -p glib` stays at 0.18.5. Recommended: dismiss as "vulnerable code is not actually used" (not used on any shipped target) with this justification, and let Dependabot's Cargo group pick up the fix once Tauri/wry move to a gtk-rs release with glib ≥ 0.20. A note goes into the PR text.
- **Fix risk:** none for a dismissal; forcing glib 0.20 would require patching half of the gtk3-rs stack – not advisable.
