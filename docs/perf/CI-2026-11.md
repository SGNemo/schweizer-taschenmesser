## Diagnosis

1. **The main cause is the queue, and it is made by the number of triggers, not by slow jobs.** The account runs 20
   jobs at once; that cap was reached during 560 of 2532 minutes (22 %), 42 % of all jobs waited more than a minute
   and 13 % more than five. All jobs together waited 10 997 min for a runner and ran 18 262 min.
2. **Two sources fill the runners.** `develop` got 90 pushes in 42 h; 49 of the runs they started were full runs
   with code (the others: docs only, or replaced while pending), each with 35 jobs and 152 runner minutes at the
   median. CI on `develop` is 40 % of all runner time (49 % with CodeQL), runs to the end even when a newer push
   is already waiting (2709 runner minutes), and 25 of those 49 full runs were red. And every fourth pull-request commit (50 of 198) only
   merges `develop` in: 2689 runner minutes to re-test code that had not changed.
3. **On the pull-request path single jobs are short (median 7 min or less) with two exceptions:** seed shard 1 holds all twelve page walks
   (9.6 min of tests, shard 2: 4.8) and was the last job of a green pull request most often, and the Windows job
   spends 5.2 of 8.9 min on a release build for a size number. A green pull-request commit takes 12.3 min (p90
   21.9) from push to green; the longest job needs 7 to 11 of them, the rest is waiting.

Checked and left as they are:
- **`concurrency`:** every pull-request workflow cancels the older run of the same pull request (CI, CodeQL, Change
  note, Website); runs on `develop`/`main` and dispatches are never cancelled while running (a pending one is
  replaced by a newer push: the 31 % "cancelled" of CI on `develop`). No change.
- **Touched packages:** work as designed. Of 200 pull-request runs the unit tests ran in 126, Rust in 53, the small
  packages in 39. The range is the merge base, so a merge of `develop` adds nothing. A workflow change turns
  everything on (wanted).
- **Double triggers:** none (0 commits with a push and a pull_request run of the same workflow).
- **Caches:** npm, Playwright browser and font packages hit in every log read; Rust hits except after a toolchain
  bump (p90 8.6 min against 2.9). The cache API is blocked for this token, so the hit rate is from logs.
- **Docs-only pull requests:** 176 runs, 238 runner minutes: cheap. Pushes to `develop` whose head commit is docs
  only cost 1189 min: CodeQL analyses Rust on each (lever 8), CI builds what an unpublished code merge before
  them left, and a push of several commits is judged by its last one here.
- **Windows runners:** only the Windows job (Rust changes) and the Dev-Preview/release builds: 1607 of 18 262 min.
- **Merge queue:** not recommended. It is offered for repositories of an organisation only, and it would add a
  second full run per merge on top of a full `develop` run.
- **Required checks:** GitHub enforces a pull request, the merge rule of the chats enforces the green checks and
  the ratchet (`docs/howto/ci.md`); "up to date with `develop`" is asked for by the skills only (maintainer list).
- **Dead workflows or actions:** none. `Full CI` starts on every label (85 runs) but takes no runner unless the
  label is `full-ci`. The aggregate job `Web` runs (4 s) and turns red on a cancelled run: left, because
  "skipped" would read as passed.
- **Two gitleaks scans** of the same commit on a `develop` push (CI and the Dev-Preview build, 0.9 min): the
  second belongs to the signing path and is not touched.
