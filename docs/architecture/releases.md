# Releases, CI and self-update (Phases 9–10)

Part of the architecture notes ([index](../architecture.md)); map of paths: [ARCHITECTURE-MAP](../ARCHITECTURE-MAP.md); decisions: [DECISIONS](../DECISIONS.md).

- **Releases & CI (Phase 9).** `.github/workflows/ci.yml` (push/PR: version consistency, lint, typecheck, unit, app + a11y E2E, server tests, sync E2E, `cargo fmt/clippy/test`). `.github/workflows/release.yml`: a tag `vX.Y.Z` / `vX.Y.Z-beta.N` builds the portable Windows exe and the Android APK, signs both, and creates the GitHub Release with notes from the commits and stable asset names:

  | Asset                                           | Purpose                                                                                                                                                                                                                                                                      |
  | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `Nemo-Portable.exe` (+ `.sig`) | portable Windows executable (frontend embedded) and its minisign signature = the updater payload                                                                                                                                                                             |
  | `Nemo.apk`, `Nemo.apk.sha256` | signed Android APK and its checksum (used by the in-app updater)                                                                                                                                                                                                             |
  | `latest.json`                                   | Tauri updater manifest (`scripts/latest-json.mjs`; only the entry `windows-x86_64-portable` – deliberately **no** generic `windows-x86_64`, so an old NSIS install can never mistake the raw exe for an installer; URLs point to the versioned `/releases/download/<tag>/…`) |

  The asset list lives in `scripts/lib/releaseAssets.ts` (used by the workflow's completeness check, the post-release `scripts/check-links.mjs` that requests every asset URL – and the `latest` ones for stable releases – and a test that keeps README links and the workflow in step).

  `releases/latest/download/<asset>` therefore always serves the newest **stable** release (pre-releases are skipped by GitHub). Pushes to `develop` touching `web/src-tauri`, `web/scripts` or the workflow, and manual runs without `version`, are **dry runs** (artifacts, no release; unsigned when secrets are missing; summary in the run). A tag run _fails_ when signing secrets are missing or when the tag differs from `web/package.json`.

  **Creating the keys (once, on your machine – never in CI, never in the repo):**
  1. `cd web && node scripts/keys.mjs updater` → Tauri updater key pair in `~/.taschenmesser-keys/` (the script refuses paths inside a git checkout). The **public** key goes into `plugins.updater.pubkey` of `src-tauri/tauri.conf.json` (commit it); the private key file + its password become secrets.
  2. `node scripts/keys.mjs android` → release keystore (`taschenmesser-release.jks`, alias `taschenmesser`) plus a base64 copy.
  3. `node scripts/keys.mjs secrets` prints the six GitHub secrets and the `gh secret set …` commands: `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, `ANDROID_KEYSTORE_BASE64` (the keystore, base64-encoded), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.

  > ⚠️ **The Android keystore (and its passwords) must NEVER be lost.** Android only installs an update over an existing app when it is signed with the _same_ key; without the keystore every installation is stranded (users would have to uninstall – losing local data – and install a new app). Keep at least two copies in different places (password manager + offline medium). The same goes for the updater private key: without it, the Windows app can no longer be updated. Never commit either, never paste them into issues or chats.

  **Cutting a release:** (1) make sure `develop` is green in CI; (2) `cd web && npm run version:set -- 0.2.0` (or `0.2.0-beta.1`; only `alpha|beta|rc` suffixes) and commit it as `chore(release): 0.2.0`; (3) `git tag v0.2.0 && git push origin develop v0.2.0` (the tag must equal `package.json`); (4) watch the _Release_ workflow; **second way:** instead of step 3, run the _Release_ workflow manually on `main` with input `version` = `0.2.0` – it checks `main`, version = `package.json` and that the tag does not exist yet, then creates tag and release on that commit (`gh release create --target`). Use one way per release, never tag push _and_ dispatch; the release appears with all assets. A pre-release (`-beta.N`) is flagged as such and is only offered to the beta update channel. Windows binaries carry no Authenticode certificate, so SmartScreen shows a warning (documented in the README); the updater payload itself is verified with the updater key.

- **Public downloads are safe by construction (release security).** Releases may be public; these checks make sure nothing private goes with them: (1) **gitleaks** scans the _whole history_ in `ci.yml` and at the start of `release.yml` (built from source via the Go module proxy, `.gitleaksignore` holds reviewed false positives – test fixtures; new fixtures get a `gitleaks:allow` comment); (2) **`scripts/audit-release.mjs`** (+ tested `scripts/lib/audit.ts`) runs in the Windows job (frontend `dist`, the app binary, the staged assets), the Android job (`dist`, the signed APK – ZIP contents are unpacked), and as a **final gate in the release job** before `gh release create`: it fails on the _values_ of the signing secrets (also base64-decoded keystore bytes), private-key markers (PEM, Tauri/minisign secret key files), and forbidden file names (`*.jks`, `*.keystore`, `*.p12`, `*.pem`, `*.key`, `.env*` except `.env.example`/`.env.e2e`, `*.db`/`*.sqlite`); it prints only variable names, never values, and checks that every `.sig` was made by the key belonging to the public key in `tauri.conf.json` (key-id comparison) – a mismatching key stops the release; (3) the temporary keystore file is written with `umask 077`, removed by an `EXIT` trap (also on failure) and by an `always()` step; GitHub masks the secret values in logs; (4) `.gitignore` covers keystores, keys, `.env*`, databases, backups and exports; (5) a tag run refuses to start when any of the six secrets is missing (the error lists the _names_), and the artifacts contain only the public updater key (in `tauri.conf.json`) and `.sig` signatures. The only personal data in the repo is the git author metadata.
- **Self-update (Phase 10).** `PlatformService.updater: UpdateService` (`core/update/types.ts`; the browser build has `supported: false` – the PWA updates via its service worker). Flow lives in `core/update/controller.ts` (plain functions + a zustand store; `UpdateBanner` in `AppShell` and `pages/settings/UpdateSection` only render it): `checkForUpdate({manual})` → `available` / `up-to-date` / `error`; automatic checks run at start and on returning to the foreground, **at most once per 24 h** (`_meta` `update.lastCheckAt`), obey the "auto" preference, stay silent on errors and skip a version the user postponed with "Später" (`update.dismissedVersion`); manual checks always run. `installUpdate` first writes a **full JSON backup into the app-private data folder** (`backups/pre-update-<from>-to-<to>-<stamp>.json`, newest 3 kept, other files untouched via `core/update/backup.ts`) – if that fails the update is **not** started (`backup-failed`). Preferences (channel `stable|beta`, auto on/off) are device-local in `_meta` `update.prefs`. Banner: discreet, changelog preview from the release body (`core/update/notes.ts` – plain-text extraction, never HTML), "Jetzt aktualisieren" / "Später".
  - **Desktop:** Rust `update.rs` (on `tauri-plugin-updater`) exposes `check_update(endpoint)` / `install_update`; the plugin **verifies the minisign signature** with `plugins.updater.pubkey` – nothing unsigned can be installed. **Windows (portable):** `tauri-plugin-updater` 2.13 can only _launch_ NSIS/MSI installers, so on Windows it just checks (`updater_builder().target("windows-x86_64-portable")`, download URL must be a `Nemo-Portable.exe` or legacy `Taschenmesser-Portable.exe` release asset of this repo, `PORTABLE_ASSETS`) and downloads + verifies (`Update::download`). `portable.rs` then **re-verifies the signature independently** (`minisign-verify`), and `swap`s the running exe: write `<exe>.new` → rename the running exe to `<exe>.old` (allowed on Windows) → move `.new` in place; any failure restores the original (`rollback`); the new exe is started with `--updated`, waits until the old image can be deleted and cleans up leftovers. Error strings carry a code (`folder-not-writable`, `signature-invalid`, `swap-failed`, `start-failed`) that `core/update/controller.ts` maps to German texts. The pre-update JSON backup runs first as before. Non-Windows desktops keep `download_and_install` (development only). The endpoint is chosen at runtime (stable = `releases/latest/download/latest.json`; beta = the `latest.json` of the newest release incl. pre-releases via the GitHub API) but `validate_endpoint` only accepts release downloads of this repository (unit-tested). `tauri.conf.json` carries the **real updater public key** (key id `3CDE64C14F49277E`); the _Release_ workflow still refuses to publish while the old development placeholder (`76760D11981F2BAC`) is in place.
  - **Android:** `platform/tauri/updater.ts` reads the GitHub releases API (`core/update/github.ts`, Zod-validated, only https URLs of this repo's release assets, `isTrustedAssetUrl`), picks the update with SemVer rules (`pickUpdate`: stable channel ignores pre-releases, beta sees both, never offers an older/equal version), downloads `Nemo.apk` (falls back to the legacy `Taschenmesser.apk`, `APK_ASSET_PAIRS`) with `apk-installer.download(url, sha256)` (hash from the matching `.sha256` asset), then `install`; result `needs-permission` when the "install unknown apps" switch must be enabled first (the user retries afterwards). Android itself rejects an APK not signed with our keystore.
  - **DB migrations on update:** `core/db/schema-history.json` holds the Dexie stores of every released version; `schema-upgrade.test.ts` opens a database at each old version with sample rows, upgrades it to the current schema and checks that rows and tables survive. **When you run `npm run db:bump`, add the previous version's stores to `schema-history.json`.** Data-shape changes still go through `manifest.migrations`.
  - Not verifiable in the sandbox: the actual download/installation on Windows and Android (needs a published release; first proof = the pre-release tag test `v0.2.0-beta.1` and a manual old → new update on a device).
- **Local verification in the sandbox:** `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`, `tauri build --debug --no-bundle`, and starting the binary under `xvfb-run` (exit 124 from `timeout` = it stayed alive). The portable exe and the Android APK can only be built in CI (no Windows toolchain, Android SDK download blocked). `cargo check` for the Windows target fails in `ring` (needs MSVC headers) – typecheck Windows-only code by temporarily switching the `cfg(windows)` attributes of `lib.rs`/`update.rs` to `cfg(target_os = "linux")` and running clippy, and `webview2.rs` in a scratch crate with `--target x86_64-pc-windows-msvc` (it only needs the `windows` crate).
