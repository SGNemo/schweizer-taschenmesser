# Decisions in full – Imports/API, connectors, disk module, setup assistant

Full text (decision, reason, source). One-line summary table: [DECISIONS](../DECISIONS.md).

## Imports & AI import API
- **Preview-before-write for every import:** wizard shows per-row checkboxes, duplicates pre-deselected, invalid rows; nothing is written before confirmation; each import is one undoable batch (`_imports`, ids `imp-<batch>-<n>`). Source: architecture.md "Start data"; commit 14205c5.
- **One import format per collection derived from its Zod schema** (no second hand-kept schema); `scope.ts` is the single filter. Source: commit 4d8b3f1; architecture.md "Data contract".
- **A move from another app is one run:** the sheet gives every part one `groupId`; the run is listed and undone as a whole (`core/importer/runs.ts`), each batch keeps its own undo rules; recognition shows reason, certainty in words and counts before the preview. Source: [features/import-v2.md](../features/import-v2.md).
- **Local AI import API: desktop only, off by default, loopback-only, transport in Rust, meaning in TypeScript.** No bind-address setting, no CORS, Host/Origin checks, hashed tokens with per-module rights, nothing logged. API imports wait as pending batches for user confirmation; changes to existing entries are never pre-ticked or auto-committed; no delete endpoint. Source: commits 4a0b230, 0944e68; architecture.md.
- **MCP wrapper is a thin separate project with no data access, not shipped in release downloads.** Token only sent to 127.0.0.1/localhost, no redirects. Source: commit c4e9b30.

## Connectors & network
- **User brings their own Google OAuth client (Desktop app type); nothing shipped in repo/binary.** OAuth via PKCE + loopback listener; Google login not on Android yet. Source: architecture.md "Connectors"; CLAUDE.md.
- **Gmail scan reads only metadata + snippet, never the body; user confirms each suggestion.** Source: architecture.md.
- **Sync-server proxy `/v1/proxy` is deliberately narrow (SSRF hardening)** – needed by the PWA for ICS/RSS; native app fetches directly. Source: commit 7e93948; architecture.md.
- **Spotify connector (desktop): own Client ID, fixed port 38417; "Läuft gerade" line, ≤ 1 request/30 s while visible.** [spotify.md](../features/spotify.md)

## Disk module & platform-only modules
- **Modules can declare `platforms`; the filter is `availableManifests()`, resolved lazily.** Module states are synced, so a desktop-only module must vanish from router, nav, dashboard and services on the other platforms, not only from the library. The platform is known only after `initPlatform()`; importing it in the registry would create a cycle through the DB, hence `core/modules/available.ts`. Source: PR #8 (2026-09-30).
- **Own recursive scan with `read_dir` + `rayon`, not `jwalk`/`walkdir`.** Folder sums come straight from the recursion (jwalk yields flat entries and would need a rebuild), cancel is per folder, errors are collected per folder, no hidden-file skipping by default. `walkdir` is single-threaded. Source: PR #8 (2026-09-30).
- **Size = space on the volume (rounded to clusters), file size shown next to it; cloud-only files count 0.** The tool answers "what eats my space". `GetCompressedFileSizeW` per file would be too slow. Source: PR #8 (2026-09-30).
- **Scan tree stays in Rust; the webview gets views by node id.** Keeps IPC small for millions of files and means a compromised webview cannot name arbitrary paths to delete. Source: PR #8 (2026-09-30).
- **Recycle bin through `IFileOperation` with an abort sink instead of the `trash` crate.** `trash` runs with `FOF_NO_UI` (includes no-confirmation) so an item the bin cannot take is deleted silently. Here `PreDeleteItem` without `TSF_DELETE_RECYCLE_IF_POSSIBLE` returns `E_ABORT`; the report offers a separate, deliberate "permanent" step. Source: `trash` 5.2.9 source; PR #8 (2026-09-30).
- **Block list checked in Rust on resolved paths, twice (plan and run), text-based rules.** Deleting takes node ids, never paths; the resolved path must equal the planned one (link swap after the scan is refused). Source: PR #8 (2026-09-30).
- **A second confirmation is enforced in Rust** for permanent or large (> 10 GiB / > 10 000 files) deletions: the dialog asks "Wirklich löschen?" once more and `disk_delete` refuses without `confirmedTwice` (`confirmation-missing`). The second "yes" only works 0.6 s after the question appears, so a double click is not two confirmations. Replaces typing the name / `LÖSCHEN` (PR #8), which the maintainer found tiring; block list, plan and recycle-bin default are unchanged. Source: maintainer request 2026-10-11.
- **Per-command Tauri permissions (`AppManifest::commands`) granted on desktop only.** Before, every app command was open to the webview. Source: PR #8 (2026-09-30).
- **Scan results are never persisted, synced, backed up or given to the assistant/local API** (no collections, no `aiSchema`, `dataApi: false` + id block). Optional scan cache and MFT quick scan (admin) are ideas only. Source: PR #8 (2026-09-30).
- **`pdf-lib` 1.17.1 pinned, loaded only when the PDF tool opens.** Last release (unmaintained, MIT); the alternative is a WASM PDF engine (much bigger). Source: PR #8 (2026-09-30).
- **Pantry → shopping list through the event `shopping.requested`**; the shopping module subscribes while enabled (no module import). Source: PR #8 (2026-09-30).

## Setup assistant
- **Manual start, never forced.** Fresh empty app: a discreet welcome card ("Später" = `dismissed` for good). Existing installations: the start migration sets `dismissed` + hidden checklist, the assistant stays available in the settings. Why: no surprise for users with data. Source: task brief; `core/setup/detect.ts`.
- **Progress is device-local (`_meta` `setup.state`), holds step ids only.** Not synced, not in backups, no values/secrets (strict Zod schema, tested). Why: setup differs per device (notifications, keystore), and secrets must never leak through it.
- **Each step saves on its own "Weiter"; cancelling drops only the current draft.** No end-of-run commit, so an abort never applies half a setup. Vault is created only with a confirmed password on "Weiter".
- **Steps are contributed via `setupSteps` on module/tool/connector manifests** (`core/setup/types.ts`); ids carry the owner's id as prefix. Why: new modules extend the assistant without special cases. The vault step lives in `modules/accounts` and carries no data (exclusion test).
- **Reuse instead of rebuild:** sync/backup/connector steps embed the settings sections/cards; start data opens the existing wizard; AI keys go through `setProviderKey` (secret store), test result shows only the mapped reason.
- **Profiles set the target state, including switching modules off, but only after a visible diff and an explicit confirmation; always `keep` data.** `ModuleManifest.requires` (invoices, budgets → finance) only informs/auto-adds, never blocks.
- **`connectOAuth` takes an `AbortSignal`:** an abandoned login stores no token and writes no status (the loopback listener times out by itself). The connector card aborts on unmount.
- **First weekday is a synced setting (scope `core`, `useWeekStart`).** Currency/format/language/time zone are shown as info only (fixed: EUR, de-DE, local wall clock). AI week ranges still use Monday.

## Browser extension & vault bridge (2026-10)
- **App as the only source.** Entries are read and written only through the app's vault (`decryptAll`, `saveEntry` → normal repo/outbox), so sync brings extension-created entries to the phone without a special path. The extension keeps in memory only the bridge session and per-tab pending saves (5 min, dropped on tab close); no `chrome.storage`, no web storage.
- **Native messaging instead of loopback.** The local import API (`crates/local-api`) rejects every request with an `Origin` header and has no CORS; extension fetches carry one. Opening a vault endpoint there would mean weakening a security rule. Native messaging gives a fixed allowlist (`allowed_origins`), a per-user pipe and no open port.
- **Host as a mode of the portable exe.** One signed file, no second artifact for audit/update; `main.rs` runs the relay before Tauri starts when the first argument is the extension origin. A moved portable folder only means re-registering the path (done at start when the bridge is on). A separate small binary was rejected (second signed artifact, easy to forget when moving the folder). Unverified on hardware: GUI-subsystem exe as host (stdio handles).
- **Lockstep protocol, no push.** A synchronous Windows pipe handle serialises read and write, so every connection is request/response; the extension polls `status` while it holds data. Session id + strictly increasing `seq` + unique request id; strict Zod schemas on both sides.
- **Brave first (Chromium MV3); Chrome, Edge and Chromium registered too, Firefox only a written proposal.** Brave reads only its own registry key, so the native-messaging host is written under all four keys.
- **Extension zip is a CI artifact only; release integration is a written proposal** – `release.yml` stays untouched until the maintainer decides.
- **Pairing.** First contact: the app shows the extension id and a 6-digit code, the popup shows the same code; confirming stores the id device-locally in `_meta` (not synced, not in backups). No key material in the extension.
- **One pipe name per user, shared by Dev-Preview and release:** the browser registers only one host; the second app to start fails to bind ("belegt") instead of stealing the channel.
- **Origin matching in `packages/vault-core`** (`tldts`, private suffixes count): used by the app handler and the extension; scheme/port always strict.
- **Form detection is a score**, not a rule: `autocomplete=new-password` +5, two password fields +5, sign-up button/heading text +5, terms checkbox +1; current-password −4, login text −4, "forgot password" link −3; ≥ 5 = registration. Links are ignored for the text signals ("Already have an account? Log in"), provider buttons ("Sign in with Google") too. Limits in [../security/VAULT-EXTENSION.md](../security/VAULT-EXTENSION.md).
- **`data-nemo-ignore`** opts a field/form/page out; the web app sets it on `<body>` so the extension never sees the vault's master password.
- **Strength in the extension = generator entropy** (the value is random, not user-chosen); the app keeps zxcvbn for user-chosen passwords.
- **Clipboard:** copy in an offscreen document, clear after 30 s only if unchanged (needs `clipboardRead`).
- Comfort package 4 (2026-10-13): hits link to `<module>?open=<id>` (`core/ai/query/rows.ts`); a page that shows records through dialogs uses `useOpenParam`, one that shows them through its URL (people, lists) returns its own parameters. An unknown id is dropped silently. "Als Notiz speichern" in the chat writes through the capture adapter (`saveCapture('note')`), so the notes module stays optional and the chat never imports it.
- Comfort package 2 (2026-10-13): Quick Capture gets `n` (note) and `r` / "Rechnung" (invoice, no confirmation: an open invoice is not a booking and undo exists); finance captures keep the confirm step. Capture & presence (2026-10-31, unasked; details [features/quick-capture.md](../features/quick-capture.md)): shortcuts/tile pass only 3 fixed screen names; multi-line splits only when every part is an entry, all-or-nothing, one "Ändern"; tray "Heute" on but switchable, ToDo/calendar titles only.
- Voice input (2026-10-17): Web Speech API only, no new dependency; off by default, one-time privacy notice; text is appended to the input, never auto-sent. Rules: [features/voice.md](../features/voice.md).
- **Reminders by sentence:** the code computes times from `now()` (`parser/dates.ts`, `ai/write/rules/clock.ts`), never a model. Spoken hours: 1–6 mean afternoon first, 7–11 morning while ahead, "halb eins" the next 12:30/00:30; "um … zu <infinitive>" is a purpose, not a time. Time over with no day named → tomorrow (preview says so); explicit "heute" stays and warns. No time → 09:00, flagged. Clock time + errand ("in 20 Minuten Pizza rausnehmen") = reminder; date-only errand = ToDo; no title is asked. Every assistant reminder gets `notify` via `aiCreateDefaults(collection, data)`. Not handled: the 02:30 clock-change night; "Montag um 9" on Monday morning means next Monday; "heute Nacht um 2" is 02:00 today.
- **First run = three questions (2026-10-29):** name + text size, profile, "Nur lokal, ohne KI" (pre-selected); the rest waits in the dashboard checklist. "Weiter" without a change is skipped, not done; profile cards name what they switch off; the Ollama probe runs only after a click. [features/first-run-setup.md](../features/first-run-setup.md)
- **Spotify widget and player (2026-10-30):** on the maintainer's wish the "Läuft gerade" line became a switchable widget card (cover, album, progress, previous/pause/next) that opens a player dialog with playlists, saved songs and search. Chosen without asking: covers are fetched via the platform fetch and shown as `blob:` URLs (CSP unchanged, host restricted to `i.scdn.co`, connection log covers it); saved songs are a separate opt-in feature (`user-library-read`); search runs on submit and keeps nothing; while nothing plays the card gives way to one quiet row (so the player stays reachable), and the whole widget is off with one switch on the Overview. No playback inside Nemo, no queue editing.
- **Setup step "Umzug von einer anderen App" (2026-10-31):** one step `core.migrate` plus the same tiles in Settings → Sync & Backup, no new parser/network/account; it reuses the existing importers and only stores origin and point ids in `_meta` `migrate.state` (device-local). Decided without asking, calmer variant: skippable, no counter or percentage; a point ticks itself only from a real committed import batch (newer than the choice), vault import and calendar subscription are ticked by hand because the app cannot see them; the row keeps its checklist place instead of adding a sixth row; Bitwarden opens Passwords with `?tools=1` instead of a second importer (vault rule); Google ZIP is not unpacked ("unzip first"). Details: [first-run-setup](../features/first-run-setup.md).
- **Several Google accounts (2026-11-01):** needed for the mail module. First account keeps its keystore keys (no migration), extra accounts get `oauth:google#<id>:refresh` and a list in the connector status; the account address is read with already granted scopes instead of requesting `email`/`openid`. Calendar sync and the mail scan stay on the first account until a feature needs more.
- **Mail module, package 1 (2026-11-02):** read-only Gmail inside the existing Google connector (`gmail.readonly`, no new scope, no second login). The seam is `ConnectorDef.mailbox: MailProvider` in `core/mail`, so IMAP can follow as another connector. Mail content stays out of every model: no `aiSchema`, not searchable, `dataApi: false`, `core/ai` cannot import it (test). The cache holds headers and opened mails only, sealed with the device key, device-local and deletable (an unlocked-vault key was rejected: reading mail must not need the vault). HTML is untrusted: DOMPurify + sandboxed `srcdoc` iframe with its own CSP; remote images are fetched by the app on request and inlined (the app CSP stays strict). Opening a mail does not mark it read (writes come in a later package with their own scope).
- **Mail → Nemo entries (2026-11-02):** one menu, six destinations, reusing the capture sheet instead of a second form: it already shows a live preview and saves only on confirm (the "Vorschau-Pflicht"). The heuristics moved to `core/mail` so the module can use them without importing a connector. The link to the mail travels in the entry's own fields (no schema change in other modules); the back-reference is a device-local `mail_link` collection of ids only, titles are read from the entry. Mail text is never copied unless the user ticks "Anfang der Mail in die Notiz übernehmen".
- **Mail write actions (2026-11-02):** off until the user switches on `mail-modify` / `mail-send` in Verbindungen (two scopes, two explanations, a new login). Google lets `gmail.modify` send as well; Nemo still only sends with `mail-send` on, and the service layer enforces the per-feature gate, not just the UI. Anything that moves or deletes asks first (archive/label: setting, default on; the trash always), and every change has an undo. Sending is the only step that cannot be recalled, so it has three stops: a review screen, a confirmation, and a 10 s send window with "Zurückziehen"; the wait is in memory only, so a closed app sends nothing. No auto-reply, no scheduled send, no write from background code, widgets or the assistant. Plain-text compose only; original attachments are not forwarded.
- **New-mail notifications (2026-11-02):** opt-in and read-only, built on the existing calm pipeline instead of a second one: a poller keeps ids and times, a `soft` notification source says "N neue E-Mails". The text is a count by default (a lock screen is not private); names are a switch. `DueNotification.local` keeps such notifications off the Web Push upload (the sync server would see the text). Quiet hours, "Stumm", game mode and the per-hour limit apply unchanged, so there is no mail-specific quiet-hours setting. Only while the app runs: pushing "new mail" needs either the content on a server or a provider push channel (Gmail Pub/Sub), both rejected for a local-first app. Polling is at most every 5 minutes and slows down after failures.
- **Local model may read mail (2026-11-02):** opt-in, default off, and structurally local: the guard resolves only the built-in model or Ollama on loopback and routes its fetch through `loopbackOnly`, so a cloud or LAN endpoint cannot be reached even by a misconfigured entry; when no local model is ready the user gets a hint and a link to the AI settings, never a cloud fallback. Loopback instead of the existing `isLocalHost` because a LAN host is another machine. Results are plain text on screen only (not cached, not in `mail_link`); the model gets no tools or grammar, and the prompt says the mail is data, not instructions.
- **Spotify playlist editing (2026-11-03):** its own opt-in feature `playlistEdit` (`playlist-modify-private`, `playlist-modify-public`), off by default; no other feature asks for a modify scope (test). Add to a playlist from the track menu, create a playlist by name; paths `/items` first, `/tracks` as fallback (docs were unreachable; live check open). The queue stays append-only because the API offers nothing else. Keyboard shortcuts are a module setting (on, skipped while typing). Header mini player not built (AppShell hotspot).
- **Use case „Kopf leer“ – capture and mail (2026-11-08, maintainer answers in `docs/design/usecases/kopf-leer/TARGET.md` §6, packages in `PACKAGES.md`):** (1) A many-lines capture never books money: an invoice word makes an invoice, a reminder word first looks for the open invoice (module-free lookup in the capture layer: reference, then payee prefix with amount ≥ open rest within a fee tolerance, oldest overdue; ties stay a ToDo „… prüfen“) and raises it through `CaptureTarget.amend?` (writes only `dunningLevel` ≤ 3, `dunnedAt` and one note line; undo restores only that and never removes), everything else becomes a ToDo with the amount and a chip „Als Ausgabe buchen“; the single sheet keeps the draft and „Buchen“ – why: an overwhelmed batch must not stop for one money line, and the finance rule stays untouched because nothing books. (2) The mail row action „In den Plan“ and the invoice line „Anlegen“/„Mahnung vermerken“ write without the capture sheet – the one named exception to the „Vorschau-Pflicht“ of 2026-11-02 – because the values the sheet would preview (title „<Absendername> · <Betreff>“; payee, amount, date) are visible in the row before the tap and an undo follows it; a missing value falls back to the sheet, the folder batch keeps a real preview, `automation.md` („suggest, never silent create“) is unchanged. (3) Entries made from a mail get deterministic ids `mail-<hash>` from the thread id (ToDo) or the message id (invoice) only – never an address or the device-local account key – written create-if-absent via `createMany` (an existing id, live or tombstoned, stops both stages, registers no undo; a tombstone offers „Wieder einplanen“); the guarantee against duplicates holds once the first device's entry has synced; the mail module's link row is of type `todo`; the ToDo link is `kind: 'mail'`. (4) Stored Gmail links lose `?authuser=<address>`; shared text never splits (first line = title, the body only behind a tick). Rejected: bookings in a batch behind a named button (Q1 b) and no new shape at all (Q1 c) – both keep a stop or the selects; the minimal mail package (Q2 b) – still opens every mail; the name-only title with the fixed label „Mail“ (Q3 b) – loses the topic, two mails of one person would read the same; the explicit mode „Abladen“ now (Q1 d) and the automation „Label → Plan“ (Q2 c, reverses „mail only reports“) – later, own decisions.
- **„Kopf leer“ package 1 – what a batch turns into a ToDo (2026-11-08, maintainer: recommendation taken):** only lines that would be a booking (`requiresConfirm`, i.e. finance, also via `$`) become a ToDo with the amount and „Als Ausgabe buchen“; a subscription line („Netflix 12,99 monatlich“) or an invoice read from a due date without an invoice word („Strom 84 € bis 30.10.“) keeps its target – why: only bookings fall under the confirmation rule, these are open items. Narrows (1) of the bullet above.
- **„Kopf leer“ package 2 – the capture contract (2026-11-08):** a save with a fixed id goes through `createMany` (never `create`, which would overwrite or revive a tombstone); an empty result is read once more to tell `existed: true` from `'tombstone'`, and either stops both stages, registers no undo and is skipped by batch undo/rollback; `reinstateCapture` brings both records back through `restore`. `findOpenInvoice` order: reference → payee name prefix (also after „im Auftrag von“) with an amount from the open rest up to rest + max(20 €, 25 %) → oldest overdue; ties, a known payee whose amount does not fit, or a payee whose invoices are already paid come back as candidates (the line becomes a ToDo „Mahnung … prüfen“; without ToDos it asks for a target), a new invoice only when no invoice of that payee exists; what is saved must be what the preview showed (another or vanished match → the ToDo). `amend` reads and writes in two steps (a payment in between is a known, seconds-wide gap). `amend` writes only level + 1 (max 3), `dunnedAt`, one note line; its undo removes only that line and resets the two values only while they still hold what was written, never removes. The lookup runs at preview time and again at save; a settled invoice falls back to the ToDo. Why: a typed reminder never doubles an open invoice and never changes money.
