# Decisions in full – Core – remote control (power, presentation, programs)

Part of [core](core.md). Index of areas: [DECISIONS](../DECISIONS.md). Plan: [design/remote-power-deep/PLAN.md](../design/remote-power-deep/PLAN.md).

- **Power is its own grant, not a third level (2026-11-15, `feat/remote-power-p1`):** shut down, restart, sleep, hibernate and sign out are reachable only with a per-device flag `remotePower` set at the PC (default off, widening via the native dialog like the level, refused while a mouse/keyboard session is or was open since the ticket). Not a level above mouse/keyboard: someone who may only pause the music from the sofa may want "PC aus" without ever moving the pointer, and someone with the mouse can already shut down by hand – the flag is about the sofa case, not about rank. Each action: the phone's own unlock prompt names the action and is the confirmation (a plain confirm dialog only without a screen lock), then a 10-second countdown in a window the PC shows from Rust state (no window, no action), stoppable at the PC, in the tray and from the phone; never forced (`EWX_FORCE` is never used, so programs with unsaved work still ask); never on a locked PC; 2 starts per 60 s per device, kept by the shell across reconnects (a per-session bucket could be reset by reconnecting). A dropped phone connection does not stop a countdown ("PC aus, Handy weg"). Wire: power has its own tag with exactly one answer per command; `open` may carry a features byte the PC echoes, and a phone whose 2-byte `open` is closed silently by an older PC opens again with one byte – an updated phone never loses media/touchpad on an older PC (council p1, Architect F1). Lock and monitor off stay media-level actions without a countdown (they only darken or reduce access). Clipboard phone → PC stays out (rule "never … clipboard … in either direction"); typed text from the Tastatur page covers "send this text to the PC". Programs: only from one PC-kept list of at most 8 entries plus a per-device switch, entries added only through a file dialog Rust opens (a widening), the phone sends a slot number; the entry names are the one string the PC ever sends. A stop at the PC quiets that device for 10 minutes and the second within an hour takes its power permission away (council p1 round 2: no window flood).
- **Power at the PC, package p2a (2026-11-15, `feat/remote-power-p2a`):** the hub gates (session, `power_effective`, lock) and hands the action to `InputSink::power`; the shell's `src/remote_power.rs` owns the countdown (`Machine`: one at a time, 2 starts/min/device, 10 min quiet after a stop at the PC, second stop within an hour takes the permission away – memory only) and calls `remote_input::power` only when it ran out, from the tray thread's tick, after the window was **visible with its page loaded** for 10 s (the count starts when the page first asked for the countdown and the window is on screen; not shown within 3 s = stopped; closed, hidden or minimised afterwards = a stop at the PC, with its quiet time and revoke). The PC state is read for the lock check only while a countdown runs (no polling otherwise). Every power frame costs at least an ordinary event and refusals count as drops, so none of them can be sent without end. The main window gets neither countdown command; `lan_hub_stop` and the settings page's „Fernsteuerung beenden“ stop a countdown first. Hibernate on a PC without it answers `failed` at once. The countdown window `power.html` is a tiny vanilla page (no React, no app module) with its own capability (status + cancel); its sentence is worded in Rust (`texts.rs`), so the page carries no texts and adds nothing to the app's critical path (a React page split 8 shared chunks off the app's start). The tray's "Fernsteuerung beenden" stays visible during a countdown also after the phone left, and stops it. "Nemo is working" = another device's open LAN sync session, a running download, or cloud sync/backup reported by the main window (`remote_set_busy`, can only add a hint). Monitor off is media id 8, posted as `SC_MONITORPOWER` (never waits for a hung window). Clippy and tests run on Linux; the Windows calls are checked with `cargo clippy --target x86_64-pc-windows-msvc -p taschenmesser-remote-input`.
- **Power on the phone, package p2b (2026-11-15, `feat/remote-power-p2b`):** „Monitor aus“ and „PC ausschalten …“ sit in the header menu of the Fernbedienung (no own tab); the sheet is the choice only (three main actions, hibernate and sign-out quieter). The confirmation is native in Rust (`remote_client_power`): the phone's unlock prompt names the action; a phone without a screen lock gets a native confirm dialog instead – never nothing, so the page alone can start no countdown. „Trotzdem“ after `working` re-uses that unlock once, only because the PC answered `working` (same action, 30 s, same pairing); any other answer or a `cancel` clears it. After `started` one still line with „Abbrechen“; a connection that drops then shows the calm „Der PC fährt herunter …“ line, never „nicht erreichbar“. A PC that hung up on the features `open` is asked the old way for the rest of the app run (a PC updated meanwhile shows power after the app restarts).
- **Programs, package p4 (2026-11-15, `feat/remote-power-p4`):** feature bit 2 (`FEATURE_PROGRAMS`), three new tags: `programs` (PC → phone, `[count, len, name…]`, ≤ 8 names of ≤ 60 bytes so the frame stays ≤ 512 B), `program start` (`[slot]`, slot ≥ 8 closes) and `program answer` (started, not-granted, locked, limit, failed). The list goes only to a phone that asked for the bit **and** whose device has `remotePrograms` with level Full and no pause – right after `opened` (first thing the tick says) and again whenever the list changes; no list = no menu entry. The hub remembers the list number and length it told; a start on a slot outside it, or after the list changed (`ProgramsCore` checks the number under its lock), answers `failed` instead of starting whatever moved into that slot. A start on a media session closes it like a key; refusals count as drops; limit 1 per 5 s per session. Adding an entry is a widening with a ticket: Rust opens its own file dialog (`.exe`/`.lnk`), asks natively, checks the hub is the same and `Remote::confirm(ticket)` (new: the ticket check for widenings that are neither switch nor grant). The list file is read once per app run (a removal that could not be written holds; an unreadable or invalid file is an empty list, replaced by the next add). The launch is `remote_input::launch` – `ShellExecuteW("open", path, NULL, NULL)` on its own thread, COM initialised there; the sink reaches it only through the closure `remote::attach` hands `ProgramsCore` (no app handle there: the p2 Windows test-exe lesson). The sink does not wait for Windows' answer (a UAC prompt would block it), so `started` means "handed to Windows"; a vanished file answers `failed`. The phone reaches the mouse level the way the touchpad does (`raise`, the same unlock window), then sends the slot. The list on the phone stays across sessions of one visit while the PC keeps sending it; `not-granted` or a PC without the bit drops it.
- **Presentation, package p3 (2026-11-15, `feat/remote-power-p3`):** feature bit 1 (`FEATURE_PRESENT`) and two keys appended to the fixed list – F5 (id 17) and the letter key B without a modifier (id 18) – so the older ids never move. The PC takes ids 17/18 only on a session whose `open` asked for the bit (otherwise it closes, as an unknown id did before); like every key they need the mouse/keyboard level, act only on an unlocked PC and share the key bucket. Asking for the bit widens nothing: no grant of its own, it only names two more keys. The phone sends them only when the PC echoed the bit (`no-present` otherwise) and shows the tab „Präsentation“ only then (`opened.present`, kept across a dropped connection until the next `opened`). Weiter = Right arrow (works in PowerPoint, Impress and PDF viewers; PageDown scrolls in some viewers instead). The view reuses the level states of Tastatur (`useMouseLevel`, `describePad`, `LevelState`). Volume keys do not turn slides (declined in the plan).
