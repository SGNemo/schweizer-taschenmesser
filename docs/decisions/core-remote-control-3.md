# Decisions in full – Core – remote control (package 3, part 3)

Part of [core](core.md). Index of areas: [DECISIONS](../DECISIONS.md).
- **Remote control package 3, part 3a: the phone's client for the mouse level (2026-11-11, `feat/remote-client-full`):** part 3 of package 3 is split again – 3a client and seam (no screen), 3b the page Touchpad, 3c the PC's settings offering the level together with the notice's off switch (the level is usable only after 3c). `remote_client_open` takes `full`: it opens only after a media session of this run told the grant (`media-first`, `not-granted` – nothing is asked and the open session is left alone), and when the PC asks for it the phone is unlocked first, **natively from Rust**: the biometric prompt of the secure-store plugin over a value under the Rust-only prefix (`lan-client:remote-unlock`; first use seals it, later uses open it), with the page's translated texts. No new Kotlin. Valid 8 hours in process memory; the media session stays open until the unlock succeeded. A brake on a phone lying around unlocked, not a proof to the PC. Limits: only a strong biometric counts (the plugin's prompt) – a phone with PIN only or no lock is not blocked and the page says so (`noLock`). New command `remote_client_pointer(session, move|scroll, dx, dy)`: numbers become records in Rust (≤ 127 per record, ≤ 32 records = one frame, a longer way is cut); mouse buttons are four fixed action names in `remote_client_send`. A mouse action on a media session is refused in the shell (`bad-level`; the PC would close the session), and while the PC's last state says locked no pointer and no button is sent. Still no key and no text. The unlock code is compiled on every target so the desktop checks see it; nothing ran on a phone.
