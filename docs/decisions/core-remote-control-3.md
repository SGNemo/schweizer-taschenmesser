# Decisions in full – Core – remote control (package 3, part 3)

Part of [core](core.md). Index of areas: [DECISIONS](../DECISIONS.md).

- **Remote control package 3, part 3a: the phone's client for the mouse level (2026-11-11, `feat/remote-client-full`):** part 3 of package 3 is split again – 3a client and seam (no screen), 3b the page Touchpad, 3c the PC's settings offering the level together with the notice's off switch (the level is usable only after 3c). `remote_client_open` takes `full`. **The PC decides grant and lock, the phone only its own prompt:** a `full` open needs a media session of this run first (`media-first`), because only the PC's `opened` tells whether it wants the phone unlocked; everything else the PC refuses itself (`not-granted`, `locked`, …) without touching the open session, and the shell keeps that session too – its events keep coming, it is ended only once the mouse session stands. An earlier version also refused locally from what the PC had said before; dropped in review, because that knowledge goes stale (a grant given at the PC meanwhile could never be used). **Unlock at the phone, natively from Rust,** when the PC asks for it: a new presence prompt in the secure-store plugin (`confirm_user`: Kotlin `BiometricPrompt` with weak biometric or device credential – fingerprint, face or PIN; no key, nothing stored). The first version reused the vault's biometric seal/unseal – dropped in review: it shared the vault's Keystore key and could reset the vault's fingerprint unlock, and a PIN-only phone would not have been asked. The prompt is a method for Rust callers only (no plugin command or permission maps to it, so the page can neither raise nor answer it), its two texts are fixed in Rust (German/English by the app's language – the page words nothing), it gives up after two minutes, and only one is up at a time. Valid 8 hours of wall-clock time in process memory (a clock set back counts as expired); forgotten on unpair and re-pair, together with the session. **What the PC says in the mouse session's own `opened` is checked again:** it asks for an unlock nobody gave in the window → the session is closed at once (`unlock-needed`). A brake on a phone lying around unlocked, not a proof to the PC. A phone without any screen lock (`KeyguardManager.isDeviceSecure` false) is not blocked and the page says so (`noLock`); every other reason the prompt cannot be shown, any error and no answer is a failure, never a pass. New command `remote_client_pointer(session, move|scroll, dx, dy)`: numbers become records in Rust (≤ 127 per record, ≤ 32 records = one frame; a longer way is shortened along its direction); mouse buttons are four fixed action names in `remote_client_send`. A mouse action on a media session is refused in the shell (`bad-level`); while the PC is locked no pointer and no press is sent, a release always goes. Known: on a locked PC the phone may ask for the unlock before the PC says `locked` – the page (3b) knows the PC's state from Medien and does not try. Still no key and no text. **Not verified:** nothing was compiled for Android (no SDK/NDK in the build environment) – the Kotlin of the prompt is new and unbuilt until the Dev-Preview workflow runs after the merge – and nothing ran on a phone.
