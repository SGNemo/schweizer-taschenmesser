# Decisions in full – Core – remote control (package 3, part 3)

Part of [core](core.md). Index of areas: [DECISIONS](../DECISIONS.md).

- **Remote control package 3, part 3a: the phone's client for the mouse level (2026-11-11, `feat/remote-client-full`):** part 3 of package 3 is split again – 3a client and seam (no screen), 3b the page Touchpad, 3c the PC's settings offering the level together with the notice's off switch (the level is usable only after 3c). `remote_client_open` takes `full`. **Gate before anything is asked or touched:** a locked PC → `locked`; nothing known about this device in this run → `media-first`; grant below full → `not-granted`. **Unlock at the phone, natively from Rust,** when the PC asks for it: a new presence prompt in the secure-store plugin (`confirm_user`: Kotlin `BiometricPrompt` with weak biometric or device credential, so fingerprint, face or PIN; no key, nothing stored). A first version reused the vault's biometric seal/unseal – dropped in review: it shared the vault's Keystore key and could reset the vault's fingerprint unlock, and a PIN-only phone would not have been asked at all. The prompt is a method for Rust callers only; no plugin command maps to it, so the page can neither raise nor answer it (the page supplies the two texts, only the system's own chrome is trusted). Valid 8 hours in process memory; forgotten with the pairing. **What the PC says in the mouse session's own `opened` is checked again:** it asks for an unlock nobody gave in the window → the session is closed at once (`unlock-needed`). A brake on a phone lying around unlocked, not a proof to the PC. A phone without any screen lock is not blocked and the page says so (`noLock`); an error of the prompt is a failure, never a pass. **Medien survives a refused mouse open:** the media session is ended only after the mouse session stands. New command `remote_client_pointer(session, move|scroll, dx, dy)`: numbers become records in Rust (≤ 127 per record, ≤ 32 records = one frame; a longer way is shortened along its direction); mouse buttons are four fixed action names in `remote_client_send`. A mouse action on a media session is refused in the shell (`bad-level`); while the PC is locked no pointer and no press is sent, a release always goes. Still no key and no text. **Not verified:** nothing was compiled for Android (no SDK/NDK in the build environment) – the Kotlin of the prompt is new and unbuilt until the Dev-Preview workflow runs after the merge – and nothing ran on a phone.
