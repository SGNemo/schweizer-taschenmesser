# Decisions in full – Core – remote control (package 3, part 3)

Part of [core](core.md). Index of areas: [DECISIONS](../DECISIONS.md).

- **Remote control package 3, part 3a: the phone's client for the mouse level (2026-11-11, `feat/remote-client-full`):** part 3 of package 3 is split again – 3a client and seam (no screen), 3b the page Touchpad, 3c the PC's settings offering the level together with the notice's off switch (the level is usable only after 3c). `remote_client_open` takes `full`. **The PC decides grant and lock, the phone only its own prompt:** a `full` open needs a media session of this run first (`media-first`), because only the PC's `opened` tells whether it wants the phone unlocked; everything else is the PC's word: a refusal (`locked`, `not-granted` for a device granted nothing, …) leaves the open session alone and the shell keeps it too – its events keep coming, it is ended only once the new session stands; a device granted only media gets a new media session for a `full` ask (the PC opens at the smaller of asked and granted), so the page reads `level` of the answer. The PC ends the replaced session before it answers: the shell holds that end back and tells the page only if the open then fails. An earlier version also refused locally from what the PC had said before; dropped in review, because that knowledge goes stale (a grant given at the PC meanwhile could never be used). **Unlock at the phone, natively from Rust,** when the PC asks for it: a new presence prompt in the secure-store plugin (`confirm_user`: Kotlin `BiometricPrompt` with weak biometric or device credential – fingerprint, face or PIN; no key, nothing stored). The first version reused the vault's biometric seal/unseal – dropped in review: it shared the vault's Keystore key and could reset the vault's fingerprint unlock, and a PIN-only phone would not have been asked. The prompt is a method for Rust callers only (no plugin command or permission maps to it, so the page can neither raise nor answer it), its two texts are fixed in Rust (German/English by the app's language – the page words nothing), the plugin takes it off the screen after two minutes (a dismissal; the limit sits in Kotlin, so the shell needs no timer on Android), and only one is up at a time. Valid 8 hours of wall-clock time in process memory (a clock set back counts as expired); forgotten on unpair and re-pair, together with the session (a prompt still up then does not count either). **What the PC says in the mouse session's own `opened` is checked again:** it asks for an unlock nobody gave in the window → the session is closed at once (`unlock-needed`). A brake on a phone lying around unlocked, not a proof to the PC. A phone without any screen lock (`KeyguardManager.isDeviceSecure` false) is not blocked and the page says so (`noLock`); a lock the system cannot ask for is `unlock-unavailable` (this phone cannot use the level); any error and no answer is a failure, never a pass. New command `remote_client_pointer(session, move|scroll, dx, dy)`: numbers become records in Rust (≤ 127 per record, ≤ 32 records = one frame; a longer way is shortened along its direction); mouse buttons are four fixed action names in `remote_client_send`. A mouse action on a media session is refused in the shell (`bad-level`); while the PC is locked no pointer and no press is sent, a release always goes. Known: on a locked PC the phone may ask for the unlock before the PC says `locked` – the page (3b) knows the PC's state from Medien and does not try. Still no key and no text. **Not verified:** nothing was compiled for Android (no SDK/NDK in the build environment) – the Kotlin of the prompt is new and unbuilt until the Dev-Preview workflow runs after the merge – and nothing ran on a phone.
- **Remote control package 3, part 3c: the PC offers "Medien, Maus und Tastatur" together with the notice's off switch (2026-11-11, `feat/remote-full-level-host`):** `RemoteHostSection` lists the level `full` (the shell took it since package 1b; it was held back in the page until the pointer existed) and, for a device at that level, the switch "Vor Maus und Tastatur am Handy entsperren" (the grant's `unlock`, on by default; dropping it is a widening and asked at the PC). **The notice gets its switch in the same PR** (the level must not exist without it): new command `remote_set_notice(on)`, state in Rust in `remote-notice.json` next to `remote.json` (device-local, never synced), stored as the loosening it is – a missing or unreadable file and a stopped hub all mean "notice on" (the closed switch cannot be set). On is immediate and remembered for the run even if the write fails; off is asked in a native dialog of its own (warning sign, it says the tray keeps showing it) and refused while a mouse/keyboard session is open or if one was opened since the question was put (counted before, compared after – such a session could have clicked the answer). While it is off the watcher still follows the session count, so nothing is told late and nobody counts as told. The tray icon, tooltip and "Fernsteuerung beenden" have no switch. `crates/lan-sync` is unchanged. Known: the level's name says "Tastatur" although keys and text come with package 4 – the PC's dialog has said so since 1b, and a grant given now covers the keyboard once it exists (the notice and the dialog name it). **Not verified:** no real Windows notification or dialog was seen (Linux build environment); FB16.
