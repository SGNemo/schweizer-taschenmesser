# Decisions in full – Core: data, sync, AI

Full text (decision, reason, source). One-line summary table: [DECISIONS](../DECISIONS.md).

## Product & data

- **Local-first, IndexedDB as source of truth; sync is a separate optional layer.** Data stays on the device; a self-hosted server only relays field operations. Source: CLAUDE.md intro; architecture.md "Sync & backup".
- **One Dexie table per collection, every synced record has an envelope (`id, createdAt, updatedAt, deviceId, deletedAt, _f`); writes only via `createRepo`.** Validation, HLC stamping, tombstones and outbox in one place. Source: architecture.md "Data".
- **Money = integer cents; dates `YYYY-MM-DD`, times `HH:mm` (local wall clock).** Calendar/reminders stay put across time zones and recurrence works on plain dates. Source: architecture.md "Data".
- **`now()` / `today()` instead of `Date.now()`.** Injectable clock makes date logic testable. Source: architecture.md "Data".
- **German-only UI, all texts in `web/src/strings.ts`; code/comments/commits English.** Source: CLAUDE.md.
- **Modules are manifest-driven and isolated (event bus + manifest contributions; only read-only `public.ts` exceptions).** Modules can be switched on/off and stay independent; enforced by ESLint and `registry.test.ts`. Source: architecture.md "Isolation".
- **Subscriptions are forecasts, never auto-booked transactions.** Source: architecture.md "Money & finance".
- **Local-only collections (`CollectionDef.local`, `_blobs`)**: news articles, feed state, vault files never enter outbox/sync/backup. Source: architecture.md "News module", "Extra modules".

## Sync

- **Field-level last-write-wins by greatest HLC; rule implemented twice on purpose** (`core/sync/ops.ts`, `server/src/store.ts`), pinned by `contract/lww-cases.json`. The server never merges values, only assigns a monotonic `seq`. Change both or neither. Source: architecture.md "Sync & backup".
- **`SyncAdapter` abstraction** (`selfHosted` built; `googleDrive.stub.ts` documents the unbuilt second backend). Source: architecture.md "Layers".
- **Optional E2E encryption of each op value (Argon2id → AES-GCM, AAD = `collection/id/field`)**; old PBKDF2 vaults are recognised and refused, not joined (`core/sync/vaultKey.ts`); ids/fields/HLC stay readable because the server needs them. Source: architecture.md "Encryption".
- **Server is single-tenant, no tombstone GC** – accepted known limits. Source: architecture.md "Not built / known limits".
- **Home-network sync with the PC as server (2026-11-06, `design/sync-lan-concept`; maintainer chose all recommendations 2026-11-07, Fable check pending):** variant (b) a Rust hub in the desktop shell (`crates/lan-sync`), star topology with exactly one hub, Noise `IK` (hub key only in the QR; `IKpsk1` pairing that checks the current single-use secret in message 1, 6-digit code on both screens, trust list), QR with a single-use 2-minute secret (no long-term secret), E2E always on with a random data key handed over in the channel, raw keys owned by Rust in the OS keystore, binds only private addresses on a positively identified home network (fail-closed, except an open pairing window; Local API rule unchanged), key rotation wipes the hub store, third LWW copy pinned by `contract/lww-cases.json` plus a small paging contract, server path stays, Android syncs on open/Wi-Fi change while the app runs. Source: [design/sync-lan/CONCEPT.md](../design/sync-lan/CONCEPT.md) §10–11.
- **LAN sync hub store: variant (b) (Rust store with LWW), (b′) append-only mailbox rejected (2026-11-07):** see [CONCEPT §3](../design/sync-lan/CONCEPT.md). Built in package 1: `crates/lan-sync/src/store.rs` is the third LWW copy (one SQL upsert, HLC compared as text), pinned by `contract/lww-cases.json`; the paging the engine assumes of a store (cursor/`more`, refused ops use no `seq`, epoch on reset, `hlc-drift`, ops limit) is pinned by `contract/sync-paging-cases.json` with levels `store` (Node store test, Rust) and `handler` (Node server now, hub in package 2b). The Sync rule now says "three copies"; the hub rule line follows with package 2a.
- **LAN sync package 2a: Noise channel, pairing window, trust list (2026-11-07, `feat/lan-sync-noise`):** `crates/lan-sync` `noise` (`snow` 0.10.0 pinned `=`, pure Rust ChaChaPoly/BLAKE2s/X25519, no `std` feature because it enables `ring`), `pairing`, `trust`, `endpoint`; no sockets yet (2b). Pairing `IKpsk1`, sessions `IK`, prologue carries the mode; only `TransportState`. SAS = first 8 bytes of the handshake hash mod 10^6. Policy: window 120 s, renewed only by the open dialog; a wrong code, wrong attempt id or timeout ends the attempt (fresh secret, no retry); confirm deadline = `min(burn + 120 s, window open + 240 s)`, all deadlines checked lazily on every entry point (monotonic `Instant`); first message 1 that cannot be authenticated, a stale one, or a key already trusted gets no reply; a **revoked key is never trusted again** (tombstone, stricter than CONCEPT §5 row 2: "Neu koppeln" needs a new key on the device). KCI accepted and keys never logged (`tests/rules.rs`). Static key only via `StaticKeyStore` (OS keystore, fail-closed, no fallback). **Residual risk accepted by Sven (2026-11-07): `snow` has no independent audit.** Overturned by: an audit preference for rustls with pinned certificates plus a separate PSK proof and SAS (CONCEPT §5). Hub modules compile out on Android/iOS.
- **LAN sync package 2b-1: hub core without sockets (2026-11-07, `feat/lan-sync-hub-core`; Sven approved the plan with all four recommendations):** (1) 2b is split – 2b-1 is the pure core (`crates/lan-sync/src/hub`: push validation, handler, rotation, per-connection router, handshake admission, address policy; no new dependency, no Tauri), 2b-2 the OS side (listener, mDNS, network list, keystore, commands, firewall). (2) The hub-local client and remote clients use one request/response JSON shape (`handler.rs` header) and every request carries `keyVersion`; a mismatch answers `stale-key-version` before anything else, under the store lock, and rotation to n+1 wipes the store, new epoch, closes all sessions in that one lock. (3) The data key and static key will live in the OS keystore via `keyring`, fail-closed, after checking that the desktop `secrets` implementation cannot be reused (2b-2). (4) v1 binds and accepts IPv4 RFC 1918 + link-local only; CGNAT, loopback, wildcard and all IPv6 are refused; no listener unless a window is open or a device is paired, and only on interfaces with a default route in a Private network (home network id when no window). Push validation mirrors the Node server (counts, `^\d{13}-\d{4}-[a-z0-9]{1,32}$` HLC, value size) and adds `enc:v1:` for every value including `deletedAt` tombstones (the client encrypts all ops); a refused batch stores nothing, takes no `seq`, keeps the epoch. The 16-byte QR secret is zero-extended to 32 bytes; hub and client are pinned by a golden value test.
- **LAN sync package 2b-2: the hub gets its network (2026-11-07, `feat/lan-sync-hub-net`):** sockets exist only in `crates/lan-sync/src/transport` (`std::thread`, no async; frame = u16 length + Noise message; listeners only on the exact addresses of `netpolicy::decide`, refused otherwise even in `Server::start`; caps per address and in total, handshake/frame/idle deadlines); a `Supervisor` re-decides every 2 s and tears all sockets down before any restart on a change of network, address, wish or UTC day; mDNS (`mdns-sd` 0.21.7, desktop target table only) announces on the bound interfaces only with TXT `v`,`h` (HMAC-SHA256 hint written out over `sha2`, pinned to the prototype). Raw hub keys (static key, versioned data key) live in the OS keystore through `keyring` (same crate as the secure-store plugin, service name `<bundle id>.lan-sync` so Dev-Preview and stable never share them); any keystore error means no hub, a corrupt entry is never replaced. The trust list and the single home network are JSON files in the app data folder, replaced atomically, unreadable = no hub. LAN values are capped at 60 000 B so a pull of one max-size op always fits one frame (larger values would need fragmentation). Windows identifies the home network via the network list (id + category Private) and `GetAdaptersAddresses` (default route); other systems cannot identify one and never listen (the gateway-MAC fallback is not built). Commands: `lan_hub_start/stop/status`, `lan_pair_open/confirm/cancel`, `lan_devices`, `lan_revoke`, `lan_hub_rotate`, `lan_hub_request`, `lan_home_set`, desktop capability only.
- **LAN sync package 3a: the hub PC syncs with its own hub, settings UI (2026-11-08, `feat/lan-sync-pc`):** `SyncConfig` is a union (`selfHosted` | `lanHub`); the hub PC talks to the hub only through `getPlatform().lanHub.request` (in process, `LanHubAdapter`, key version in every request) and never names a Tauri command in `core/sync`. Every round (re)starts the hub and takes its current data key, so a renewed key is imported before the next pull. Push, the feed proxy and the server device list read `loadServerConfig` (own server only). One path per device: `enableLanHub` refuses while a server is connected. The pairing UI is desktop-only and lazy-loaded (no QR generator in the browser's or phone's start path). The phone side (client, scanner) is package 3b.
- **LAN sync package 3b: the phone pairs and syncs (2026-11-08, `feat/lan-sync-phone`):** the device side is `lan_sync::client` (in `src/transport/client.rs`, compiled on every target; sockets stay under `src/transport`): `IKpsk1` pairing with the QR secret, `hello`, the 6-digit code shown on the device, then the data-key frame after the confirmation on the PC; sessions `IK`, one request/answer per frame. Only the hub's authenticated `unknown-device` becomes "revoked"; no answer or a wrong hub key is a calm `network`. The crate's `store` feature (SQLite) is desktop-only, Android builds the client without it. The shell gets its first Android commands (`lan_client_*`, `src/lan_client.rs`); the device key and the pinned hub live in the OS keystore via the secure-store plugin, only the data key reaches the web app (non-extractable `CryptoKey`). Device requests stay under 60 KB (`LanClientAdapter` slices pushes, pages ≤ 200 and halves on `response-too-large`); a renewed hub key means "pair again" on devices. QR scanning on Android: in-app camera dialog (`QrScanDialog`, `getUserMedia` + jsQR, lazy), see the next bullet. Every pairing uses a fresh device key (the hub never trusts an unpaired key again), stored only after the data key arrived; the device key and the pinned hub sit under the Rust-only keystore prefix `lan-client:`, which the secure-store plugin's webview commands refuse. Cancel on the PC ends the waiting connection at once (`Deliverer::abort`). A paired phone that cannot reach its PC is a calm state everywhere, also in the top-bar badge. Not built: Wi-Fi trigger (`lan-watch`), mDNS on Android (the QR's address is used and remembered), second PC as client (the commands are Android-only), „Nur im WLAN“ on the sync button, the 7-day hint „Lange keinen PC gefunden“, telling the PC later about an unpair done while it was unreachable.
- **In-app QR scanner instead of the native one; a way out of a public network (2026-11-08, `fix/lan-sync-qr-camera`):** the native `tauri-plugin-barcode-scanner` crashed the app on a real phone and put a full-screen camera over the app with no way back; the phone now scans in its own dialog (`getUserMedia` in the WebView, frames ≤ 720 px decoded with jsQR every 200 ms, camera off when the dialog closes). wry asks Android for CAMERA on `getUserMedia`, so the Android manifest declares CAMERA (optional feature) via `scripts/android-manifest.mjs`. On the PC a network Windows calls public still blocks the hub (rule unchanged); the pairing dialog then shows only the steps to "Privat" and opens `ms-settings:network-status` (the only extra opener URL); the QR follows by itself once Windows reports the network as private.
- **The hub keeps its port (2026-11-08, `fix/lan-hub-stable-port`):** the supervisor restarts the listeners on every app start, at UTC midnight (mDNS hint) and when the address set changes; each start used to pick a random port, while a paired phone only knows the QR's address (no mDNS on Android) – so after the first restart every phone waited forever. The first start picks a free port and remembers it in `lan-sync/port`; later starts take that port and fall back to a free one (and remember it) only if it is taken. Phones paired before this change pair once more. A changed PC address still needs a new pairing.
- **Switch from server to home network (2026-11-09, `feat/lan-sync-switch`):** a device on an own server gets _Vom Server auf das Heimnetz umstellen_ (PC and phone): a backup is required before _Vom Server trennen_ is enabled, the server's other active devices are listed with _Am Server sperren_ (they keep syncing there until switched, CONCEPT §7), disconnecting keeps local data; pairing is the usual next step. Nothing merges the two worlds automatically. A paired phone that has not reached its PC for 7 days shows one calm fact line „Lange keinen PC gefunden …“ (no button: also on holiday).
- **LAN sync package 4 rest B: Wi-Fi trigger and finding a moved PC (2026-11-09, `feat/lan-watch`):** own plugin `plugins/lan-watch` (Kotlin, like `share-intent`): a `NetworkCallback` for `TRANSPORT_WIFI` (internet capability removed, so an offline router still counts) emits `wifi-available`/`wifi-lost`; the web side reads it only through `getPlatform().lanWatch` and `startSync` runs a round when Wi-Fi comes up and the config is `lanClient` (`core/sync` names no command); `wifi` lives in the status store and disables „Jetzt abgleichen“ with „Nur im WLAN“ (unknown never disables). Finding the PC again is Rust-only: only when a round cannot open a session at the pinned address (at most once per 30 s), `lan_client.rs` asks the plugin's `NsdManager` search (3 s, multicast lock held, IPv4 only) – a Kotlin command without any webview permission, so announcements never reach the web app – keeps services with `v=1` and a hint of the pinned hub (`lan_sync::hint`, now on every target; `rediscover::candidates`, ≤ 3, private IPv4), tries them with the pinned `IK` session and stores the first that opens as `HubEntry.addr`; the hub's authenticated `unknown-device` there counts as the answer. Permissions: normal only (`ACCESS_NETWORK_STATE`, `CHANGE_WIFI_MULTICAST_STATE` via `scripts/android-manifest.mjs`, which fails on any location permission); no SSID. Not built: WorkManager background sync, mDNS for a second PC as client.
- **A second PC pairs as a client of the hub PC (2026-11-09, `feat/lan-second-pc`):** the `lan_client_*` commands run on the desktop too (one shared `generate_handler!`, granted in `capabilities/default.json`; `mobile.json` is gone). The device key and the pinned hub stay Rust-only under the secure-store prefix `lan-client:` (desktop: `keyring`/Credential Manager, service = app identifier). One path per device, checked twice: `enableLanHub` refuses as client (`client-paired`, also `lan_hub_start` in Rust), `pairWithPc` refuses while the hub is on (`hub-on`, also `lan_client_pair` in Rust). The QR is read by the webcam in `QrScanDialog`; no webcam (`NotFoundError`) is a calm `no-camera` line with a pointer to the own server. mDNS re-discovery of a moved hub on the desktop client is not built.
- **Remote control: the phone steers the PC over the paired LAN hub (2026-11-10, `design/remote-control-concept`; the maintainer chose all four recommendations 2026-11-10: grant once per device, media with a locked PC, keyboard as its own package, module name „Fernbedienung“):** pairing is not permission. Input travels in an own session of the hub (same listener, keys and trust list, handshake mode 3, binary one-way records), never in the sync session and never on a new port; shown in the prototype with an assumed store time: input on a shared session waits as long as the store works, on its own session it does not. Accepted only on the stored home network. Grant per device, off by default, set only at the PC (device-local, native confirmation for every widening, none while a mouse/keyboard session is open), two levels: media/volume/lock without any simulated input, mouse/keyboard via `SendInput` (`windows` crate in a new `crates/remote-input`, no `enigo`, Windows only). Visible on the PC, one click ends and pauses the grant; locked PC: media only; never screen, clipboard, files, titles; input is never logged. Phone: module `remote` (`platforms: ['android']`, no collections); PC: a settings section. Rule in force since package 0 (2026-11-10): `docs/rules/remote-control.md` (own file because `RULES.md` is at its size budget), short line in root `CLAUDE.md` and in `RULES.md`. [CONCEPT](../design/remote-control/CONCEPT.md), [PACKAGES](../design/remote-control/PACKAGES.md).
- **Remote control package 1a: input session and grant in `crates/lan-sync` (2026-11-10, `feat/remote-hub-session`):** `src/input/` = `wire` (tags `0x20`–`0x26`, 4-byte records, every target), `remote` (master switch `MasterSwitch`/`FileSwitch`, grants, the one controller slot), `session` (hello → open → events through the gate), `limits`, `sink` (`InputSink`, typed `Action`s; the shell passes one in with `Router::with_input`, without it every input session is refused). Decided while building: (1) where input is not accepted (not the home bind, nothing wired) the hub answers message 1 with the **same authenticated `unknown-device` refusal** a stranger gets, not silence – no transport is kept, and the phone can tell it from an old hub (which stays silent) by trying sync; (2) binds carry `is_home` from the stored network id (also with a window open, fail-closed), checked by the **local address** a connection came in on; a flag that changes restarts no listener (`Launcher::home_changed`); (3) the grant is not a field of `Device` but `TrustStore::remote_of`/`set_remote` (defaults closed), stored per device in `trust.json` as `remote`, `remotePaused`, `remoteUnlock` (`serde` defaults, old files open with no grant, an unknown level is a broken file); (4) a session's level is fixed in `Remote::claim`; the same device opening anew replaces its older session, another device gets `busy`; (5) "Fernsteuerung beenden" marks the session (it says `ended` on its next tick) and pauses the device; the master switch off marks it `remote-off` the same way and refuses every later `open`; a grant that changes while its device controls ends that session without a reason when something is left (the phone opens again and reads its new grant from `opened`), with `not-granted`/`paused` when nothing is; none of this touches a sync session. A bind that stops being home (`Router::set_binds`) closes every input session; (6) limits per session: 500 events/s (burst 250), clicks 20/s, keys 30/s, text 512 B/s, media 10/s, volume up 5/s, lock 1 per 10 s; 2000 drops, then 200/s, close with `limit`; (7) the PC's state is polled from the sink on the connection's tick and sent at most every 200 ms; that never counts as activity. (8) home = the connection came in on a home bind **and** its peer is in that bind's subnet (a peer on a pairing-window network that dials the home address is not home); (9) widening needs a `Ticket` taken before the PC's confirmation: the setter refuses without one (`Unconfirmed`) and when a mouse/keyboard session is open or was opened since (`BusyControlled`); a session counts as open until its connection has finished, not until it was told to end; (10) a session remembers the mouse buttons it pressed: letting go of one of those passes every limit and the lock, and at its end it lets go of exactly those (the sink has no "release all"; a session never lets go of a button it did not press itself, so never of another device's); any other release is an ordinary, limited event; what a locked PC does not take counts as a drop; after frames came in the hub tells its state once within about half a second even if unchanged (the phone's sign that they arrived); the hub keeps reading for up to 500 ms after its last frame so the reason arrives while the phone still sends; (11) an app version from before this package rewrites `trust.json` without the three fields, so a downgrade loses all grants (closed). Phone side: `InputError::NoAnswer` = the hub hung up on the first message (a hub from before remote control, not this hub, or a hub shedding load), `InputError::Closed` = a send on a session that is over, `UnknownDevice` = authenticated refusal (never a reason to unpair), `Event::Closed(None)` = open again on the next touch. `input_client::InputSession` (reader thread, the Noise state behind a mutex held only to seal or open one frame).
- **Remote control package 1b, part 1: PC side in Rust (2026-11-10, `feat/remote-host-media`):** package 1b is split – this part is Rust only, the settings page, chip and web seam follow as their own PR (one topic per PR; the commands are complete without them). `crates/remote-input` knows neither the hub nor Tauri: typed commands in, four facts out (volume, mute, playing, locked), one worker thread that owns COM/WinRT, a bounded queue that drops instead of waiting, a state that is refreshed only when somebody asks. Media keys are **not** simulated (`VK_MEDIA_*` would be input): play/pause/next/previous go to the system media session, volume to the audio endpoint. The shell's `Sink` drops every non-media action until packages 3/4. `src/remote.rs`: every widening = `Remote::ticket()` → native blocking dialog (device name as plain capped text, level, last contact in whole days) → setter with the ticket; a narrowing never asks; one dialog at a time; an unreadable switch file = a switch that stays off. The ticket is taken **before** the "is a mouse/keyboard session open" check, and after the dialog the stored grant must still be the one the question described (`changed` otherwise). The claimed name never sits inside a sentence: own labelled line, invisible/direction characters dropped, quotation marks replaced; no name = a label with the first id characters. Narrowings of this run are remembered in the process and re-applied when a restarted hub reloads switch and grants from disk (without a ticket, so they can only narrow). The controls live in their own state (`RemoteHost`), not behind the hub lock, so the tray's "Fernsteuerung beenden" never waits for a slow hub command; they exist only while the hub runs. Tray: the page's labels, tooltip and "Heute" block are stored and every rebuild goes through one function that adds the controller from Rust state; updates from other threads are handed to the main thread (the tray state is only locked there); one thread is the only writer of the controller (commands and the tray click only wake it), and the tooltip names the controller first because Windows cuts tooltips at the end. Under "Fernsteuerung beenden" a grey line says that the device stays paused. `Worker::state` answers at once while somebody keeps asking; only the first question after a quiet time (reading older than 2 s, e.g. the `open` of a session) waits for a fresh one, at most 150 ms – an `open` must not be answered from a stale "unknown, locked" (the `InputSink` contract says so now), repeated refresh requests take one queue place, and `supported` is decided on the worker thread (a failed COM setup = unsupported). Native texts German/English in `texts.rs`. Guards: `tests/commands.rs` (async, no command simulates input, ticket before dialog before setter, hub wires and drops the controls), source tests in the crate.
- **Remote control package 1b, part 2: settings, chip, web seam (2026-11-10, `feat/remote-host-settings`):** seam `getPlatform().remoteHost` (status, setEnabled, setDevice, end; web stub unsupported, E2E fake `fakeRemoteHost.ts` that follows the shell's rules and lets a test answer the "Windows dialog"). The page never confirms a widening itself – no in-app confirm dialog on top of the native one (two questions for one step would teach clicking through); it says once that Windows will ask. `cancelled` is the person's answer and shows no message. The choice is a plain select per device, inactive with one sentence while the master switch is off. **Held back until package 3:** the level "mouse and keyboard" and the "Am Handy entsperren" option – nobody should confirm in a Windows dialog what does nothing yet and would then switch on silently (a level set elsewhere still shows). A paused device shows only "Wieder einschalten". A change sends one field merged into a reading made at that moment, so a device paused from the tray a second ago is not un-paused by lowering its level. State lives in a transient store (`core/remote/host.ts`, never persisted, device names in memory only; diagnostics canary added): the open section reads every 4 s, the always-mounted top-bar chip only while this PC is the home-network hub – no hub, no polling. Chip = neutral surface, icon + "Fernsteuerung: <device>" (icon alone in a narrow window), no motion, absent when nobody controls; a failed reading drops the controller from the page (the tray, drawn by Rust, stays the authority), and answers that overtake each other are dropped by a sequence number. Section is `preview`, visible on desktop only, and stays listed while the switch is on (`inUse.remote`). The shell's own texts (tray rows, tooltip, dialogs) now follow the app language: the page sends `lang` with the tray labels, Rust maps it to its fixed German/English texts (system language until then; kept in its own lock, so the tray state stays main-thread-only); the quit question follows it too.
- **Remote control package 2, part 1: phone client, seam, session logic (2026-11-10, `feat/remote-module-media`):** package 2 is split like 1b – this part has no screen (shell client, seam, state logic), the module "Fernbedienung" with the Medien page, widget and volume keys follows as its own PR. `src/remote_client.rs` (compiled for the phone and for unit tests; commands only in the mobile handler and `mobile.json`, guarded by `tests/commands.rs`): `remote_client_open(level, channel)`, `remote_client_send(session, actions)`, `remote_client_close(session)`. A connection of its own through `lan_sync::input_client`, never the sync `Link`; key and pinned hub are read from the keystore per `open` and never leave Rust; the page passes action **names** from a fixed list (seven media actions, ≤ 8 per call), so no key code or text can be sent in this package. Sessions are numbered: events of a replaced session are dropped in Rust, a `send` to an old number answers `closed`, an `open` overtaken by a newer one closes itself. The client never unpairs. Web: seam `getPlatform().remote` (Android only; stub; `fakeRemote.ts` = demo PC "PC-Sven", volume 42 %, answers with its state after every bundle). `core/remote/session.ts` turns the crate's signals into the states of CONCEPT §7 and owns the rules: one `open` at a time and at most one a second; `no-answer` + sync ok twice, 4 s apart = "PC zu alt", `no-answer`/`network` + sync failed = not reachable, sync "not paired" always wins; `network` + sync ok = one more try (the sync round just found a moved PC); `unknown-device` = "takes no input here" unless sync says unpaired; `protocol` = try again; a send error or 3 s without the PC's answer = not connected, the next touch opens again; nothing is sent in refused or unreachable states (there the volume keys stay with the phone). After the council: while it connects only the **last** press waits (held keys never pile up) and a key repeat never opens a connection; "connecting" is shown 5 s at most, then the view `slow` ("no answer yet" – not a verdict, so a PC that turns out too old is never called unreachable on the way) while the attempt goes on, and a press that waited until then is dropped; a session that did not answer in 3 s is shown as not connected but kept for a late answer (which heals it without a new connection) and replaced on the next touch; the volume keys belong to the PC only with a session and for 5 s after it was last alive, never during a first connect; `close()` invalidates a running attempt, which then dials nothing more and leaves no session; what the PC says before the answer to `open` arrives is buffered. The shell accepts only `media` as a level until it can send pointer and key records, and writes outside the session lock. The sync round is a dependency the module passes in – the session logic knows no sync code.
- **Remote control package 2, part 2: the module "Fernbedienung" (2026-11-10, `feat/remote-module-page`):** `modules/remote`, `platforms: ['android']`, area system (order 198), `preview`, no collections, `dataApi: false`, in `BLOCKED_MODULES`, no `aiSchema`, `seed: none 'live-data'`, `noOnboarding`. Identity `fern` / head `schreib` / widget `status`; signature `display` for now – the concept's own mark `touchpad` comes with the touchpad (package 3), a mark for something that does not exist yet would be decoration. One page, Medien only (no tab bar until there is a second tab): volume in the lowest row, transport above it, the state as one line, "Ton aus" and "PC sperren" in the menu. `view.ts` maps every session view to its sentence and one step; the phone does not know its PC's name, so the line says "Dein PC"; `too-old` is worded as a check ("Ist Nemo auf dem PC aktuell?"), not a verdict; an unconnected session keeps the last known state quietly. One module-level session (`modules/remote/session.ts`) for page and widget; it opens when the page is visible and closes when it is hidden or left; `syncRound` = one `syncNow` and the status store (`via !== 'lanClient'` or `revoked` = not paired). A held volume button acts when the finger goes down (tick + first step), then repeats ≤ 5/s as `repeat` (never opening a connection); the click after a pointer press is ignored, a keyboard or screen-reader click acts once. Inactive keys are flat and outlined, also the main one. The widget opens nothing and claims nothing about the PC: "Dein PC" + _Öffnen_ when paired, "Noch kein PC gekoppelt." + _PC koppeln_ otherwise. Settings: haptics (on), keep screen on (off). Keep-awake is a counted hold (`core/shell/keepAwake.ts`) shared with the cockpit, so leaving one never switches it off for the other. `syncRound` runs a round when the sync path is not known yet (app just started) instead of answering "not paired". **Not in this PR:** the phone's hardware volume keys (Kotlin in `plugins/screen-mode`; cannot be compiled or tried here) – own PR with an Android build. Hue `lime`, not the concept's `fern`: every hue but `cobalt`/`slate` is a settings head in area system, and a settings head must never look like a module (`categoryLook.test.ts`); so the head "Schnellerfassung" moved from `lime` to `teal`.
- **Remote control package 3, part 1: the pointer sink on the PC (2026-11-10, `feat/remote-touchpad-host`):** package 3 is split – this part is Rust only (sink and shell), the PC's notification and the phone's page follow as their own PRs; the latency measurement the prompt puts first needs a real phone and gates only the page. `remote-input` gets `src/pointer.rs`, the one file that simulates input (`tests/rules.rs`): the mouse part of `SendInput` – relative move, left/right, wheel – one call site, seven flags; no key, no absolute position. Its **own thread**, not the media worker's: reading volume and media session takes milliseconds and the hub asks for the state per pointer record. Waiting moves are summed into one, anything else keeps its place. Bounds: 64 waiting actions, then moves, wheel steps and presses are dropped. A **release is never dropped** and never waits for room, but only one per press that was taken: a flood of spare releases cannot crowd out the real one, and a spare release from the hub at session end or a button held on the real mouse is left alone. A press the system refused (secure desktop, desktop switch) is not held; an elevated window swallows the event and reports success, so that case cannot be told. The thread releases what it holds when it ends, also when it unwinds; a process that exits or is killed does not (the button stays down until the person clicks once). Accepted: the buttons belong to the PC, not to a session – a replaced session's closing release also lifts a press the new one just made; a click on the real mouse during a remote press makes the next remote press of that button a no-op once. Media and pointer run on two threads, so order holds within each level only. Wheel: one wire unit = 15 of the system's delta (8 = one notch), `dy > 0` moves the view down. Lock, level, limits stay the hub's (1a); nothing is reported to the phone. Keys and text are still dropped in the shell sink.

## AI

- **Never send user data to the model.** Only instructions, compact `aiSchema` of enabled modules, the date and the question; results are computed locally, no second call. Guarded by `privacy.test.ts` for every adapter. Source: architecture.md "AI assistant"; CLAUDE.md rules.
- **Three tiers, cheapest first:** local German parser (0 tokens) → full text → intent cache → model. Goal: as few tokens as possible. Cache key excludes provider/model so fallbacks share hits. Source: architecture.md "AI assistant".
- **Model output is never evaluated; it is a Zod-validated `Intent` executed against a field whitelist.** Creating entries needs an explicit confirmation card. Source: architecture.md.
- **Multi-provider router with fallback, cooldowns and local limits;** presets are only editable defaults (names/prices unverified). API keys live in `PlatformService.secrets`, never in the config list. Source: architecture.md "Multi-provider AI".
- **`accounts` (password vault) is invisible to AI, search, dataapi and local API** (no `aiSchema`, `dataApi: false`, id block; `exclusion.test.ts`). Source: architecture.md "Password vault"; CLAUDE.md.
- **`accounts` has exactly one widget, and it shows vault status only (2026-11-10, maintainer's yes 2026-11-09):** `docs/RULES.md` "AI privacy" reads "a widget with entries" like root `CLAUDE.md`. "Entries" means anything derived from `accounts_entry`: contents, titles, counts, categories, strength/breach results, attachment names; the status widget shows only not set up (vault header) / locked / unlocked (session state), a fixed hint and one link. Pinned by `modules/accounts/__tests__/exclusion.test.ts`: `widgets` equals `['status']` (a second widget fails), and the source of `StatusWidget.tsx` must not contain `entryRepo`, `useEntries`, `decryptRow`, `saveEntry`, `password` (that file only, not its imports – the rule covers the rest, a transitive check is an open follow-up). Source: [ui-audit-2026-11/LEDGER.md](../design/ui-audit-2026-11/LEDGER.md) Guardian F4.
- **Connectors must not import `core/ai`; news has no `aiSchema`.** Mail/feed text can never reach a model except via the explicit news-brief button (headlines only). Source: architecture.md "Connectors", "News".

- **AI writes (2026-10-05): stage order rules → local model → cloud, every write only after the preview.** Reason: tokens and privacy – most sentences are fully determined by the module words and the extractors (stage 0 handles 94 % of the 154 entries of the eval set exactly, 0 wrong module, 0 false positives on 30 searches/questions; run `npm run ai:eval`); the cloud is the last resort and only with the sentence, the date and field schemas. Actions are declared per module (`aiSchema.actions`, validated by `validateAiActions`), so a new module needs no core change. Deletes and changes show before/after, are one undoable group, and skip entries edited since the preview. Update/delete/mark targets are the user's own words matched on the device, so no candidate list is sent. Modules without actions and the vault stay read-only/invisible. Claude subscriptions cannot be used by third-party apps (Anthropic terms); the supported path for a subscription is Claude Code on the PC driving the local API / MCP ([AI-IMPORT](../AI-IMPORT.md)). Source: `core/ai/write/`, `docs/architecture/ai.md`.

- **A server with a vault holds ciphertext only (2026-11-10):** `POST /v1/push` refuses a batch with any non-`enc:v1:` value as a whole (400 `missing-enc`, the LAN hub's code), and `PUT /v1/vault` refuses when ops are stored (409 `not-empty`), so plain data and a vault cannot come to coexist; before, a keyless device whose round fell between the vault's creation and the first encrypted push (empty page), or an older client, uploaded everything in plain text.
