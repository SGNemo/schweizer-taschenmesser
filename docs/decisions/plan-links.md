# Decisions – Day and week planning – links between modules (planner hub)

Part of [plan](plan.md). Index of areas: [DECISIONS](../DECISIONS.md).

- **One link contract: `EntityLink` + `contributions.linkTarget`, read only through `resolveLink` (2026-11-15, planner hub K1a):** a link is `{ from, to, rel, label, on? }` over `EntityRef { module, id }` (`core/entitylinks/types.ts`); the four literal link unions are the one `LegacyLink` (stored ToDo shape and Zod schema unchanged, no version step). The target module says what its entity is – `alive` (title, route, its own `done`), `gone`, `elsewhere` – from its own data, without network, the id untrusted; core answers `unavailable` itself while the module is off or not on this platform, and `gone` for `accounts` without asking a module. Why: routes and „does it still exist“ were a table in the ToDo editor plus a second rule in the planner, and a new linkable module needed five edits. Links, `action` and `detail` are display only and stay out of the input hash (test `linksDisplayOnly`). `fixed`, `blocks`, `actuals`, `list` ctx `requested` and `ref` on `plan.requested` / `shopping.requested` are types only until S4, TT2, K2 and S3 read them. Source: [CONCEPT-LINKS](../design/planner-hub/CONCEPT-LINKS.md) §1.1, §1.4, §1.6.
- **One row per link in the synced system table `_links`, id = SHA-256 of `[fromKey, rel, toKey]` (2026-11-15, planner hub K2):** stores `id, updatedAt, fromKey, toKey` (Dexie 38), written only through `createRepo` in `core/entitylinks` (`addLink` = tap, restores a tombstone; `addLinksIfAbsent` = every other writer, a tombstone counts as present, so a removal wins). Why rows: an array is one LWW field, so two devices adding at once lose one; why a hash: a record id travels in clear. Reads drop rows with an end in `accounts` or in a module without `linkTarget`. Orphans: purging a carrier's tombstone or wiping its module tombstones its `from` rows. ToDo `links[]` stays frozen and is copied (`migrate.ts`): only when no row has the id, and stamped with the HLC of the task's `links` field on every field (the app-migration path, not `createRepo`), so a copy never beats a removal made later anywhere. It runs at every app start (with sync configured only after this device's first completed pull), after a sync round that moved something and after a restore; cost: one scan of `todos_task` per run. `removeLink` of a ToDo's link also strips the task's array entry. The editor shows rows ∪ array.
- **Cursor repair for newly synced tables (2026-11-15, K2):** the store keeps the synced table names in `_meta` `sync.tables`; when this app version has a name the stored set lacks (or no set is stored and the cursor moved), the pull cursor restarts at 0 once – one store and cursor for server, LAN hub and LAN client. Why: an older app drops ops of unknown tables while its cursor moves on. A page that starts below the replaced cursor is a replay and never logged as a conflict (the page crossing the mark included: a missed note there, never a false one). Cost: one full pull per device at the update that brings the repair **and again at every release that adds a synced table or collection**. Known limit, not fixed (ops carry no sequence number, so old and new ops of the crossing page cannot be told apart): the re-pull re-creates tombstones this device already purged, and a record whose `deletedAt` op sits in a later page is live between those pages; an interrupted pull leaves it visible until the next round resumes at the stored cursor and applies that page (`sync.pullComplete` stays false meanwhile). Nothing is lost or pushed by it.
- **First cross read in core: `plannedDay` (2026-11-15, K2):** `core/entitylinks` reads `planner_assignment` through the generic manifest repo (as `modules/mail/planMail.ts` does) – the earliest live day from today on, `undefined` while the planner is off; nothing is written and `core/plan/**` stays free of db imports.
