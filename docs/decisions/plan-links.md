# Decisions – Day and week planning – links between modules (planner hub)

Part of [plan](plan.md). Index of areas: [DECISIONS](../DECISIONS.md).

- **One link contract: `EntityLink` + `contributions.linkTarget`, read only through `resolveLink` (2026-11-15, planner hub K1a):** a link is `{ from, to, rel, label, on? }` over `EntityRef { module, id }` (`core/entitylinks/types.ts`); the four literal link unions are the one `LegacyLink` (stored ToDo shape and Zod schema unchanged, no version step). The target module says what its entity is – `alive` (title, route, its own `done`), `gone`, `elsewhere` – from its own data, without network, the id untrusted; core answers `unavailable` itself while the module is off or not on this platform, and `gone` for `accounts` without asking a module. Why: routes and „does it still exist“ were a table in the ToDo editor plus a second rule in the planner, and a new linkable module needed five edits. Links, `action` and `detail` are display only and stay out of the input hash (test `linksDisplayOnly`). `fixed`, `blocks`, `actuals`, `list` ctx `requested` and `ref` on `plan.requested` / `shopping.requested` are types only until S4, TT2, K2 and S3 read them. Source: [CONCEPT-LINKS](../design/planner-hub/CONCEPT-LINKS.md) §1.1, §1.4, §1.6.
- **One row per link in the synced system table `_links`, id = SHA-256 of `[fromKey, rel, toKey]` (2026-11-15, planner hub K2):** stores `id, updatedAt, fromKey, toKey` (Dexie 38), written through `createRepo` in `core/entitylinks` – except the copy of ToDo links, which uses the sync-apply path with the task's stamps (precedent `core/db/appMigrations.ts:177`) – (`addLink` = tap, restores a tombstone; `addLinksIfAbsent` = every other writer, a tombstone counts as present, so a removal wins). Why rows: an array is one LWW field, so two devices adding at once lose one; why a hash: a record id travels in clear. Reads drop rows with an end in `accounts` or in a module without `linkTarget`. Orphans: purging a carrier's tombstone or wiping its module tombstones its `from` rows. ToDo `links[]` stays frozen and is copied (`migrate.ts`): only when no row has the id, stamped with the HLC of the task's `links` field on every field, so the copy loses against any removal made after that array was written – on any device, pulled or not; hence it needs no completed pull and runs at every app start (not awaited, serialised), after a sync round that moved something and after a restore; cost: one scan of `todos_task` per run. Removing a ToDo's link always leaves a tombstone (`removeLinkOf` writes the row stamped first when this device has none) and strips the task's array entry. Known limits: (1) the protection lasts while the tombstone exists – after its purge (90 days) a device that was offline that long and still holds the array entry re-creates the link; (2) an older app removes a link from the array only, so the row stays live and the link stays visible in newer apps until removed there. The editor shows rows ∪ array.
- **Cursor repair for newly synced tables (2026-11-15, K2):** the store keeps the synced table names in `_meta` `sync.tables`; when this app version has a name the stored set lacks (or no set is stored and the cursor moved), the pull cursor restarts at 0 once – one store and cursor for server, LAN hub and LAN client. Why: an older app drops ops of unknown tables while its cursor moves on. A page that starts below the replaced cursor is a replay and never logged as a conflict (the page crossing the mark included: a missed note there, never a false one). Cost: one full pull per device at the update that brings the repair **and again at every release that adds a synced table or collection**. Known limit, not fixed (ops carry no sequence number, so old and new ops of the crossing page cannot be told apart): the re-pull re-creates tombstones this device already purged, and a record whose `deletedAt` op sits in a later page is live between those pages; an interrupted pull leaves it visible until the next round resumes at the stored cursor and applies that page (`sync.pullComplete` stays false meanwhile). Nothing is lost or pushed by it.
- **First cross read in core: `plannedDay` (2026-11-15, K2):** `core/entitylinks` reads `planner_assignment` through the generic manifest repo (as `modules/mail/planMail.ts` does) – the earliest live day from today on, `undefined` while the planner is off; nothing is written and `core/plan/**` stays free of db imports.
- **Lists are a plan source: ONE row per list, an undated list only on request (2026-11-15, planner hub S3):** `modules/lists/plannable.ts` lists a packing list whose trip date's day before lies in the planned days as „Packen: <Name>“ (20 min, hard due = the day before, today on the trip day) and a shopping list (or an undated packing list) only for an id in `ctx.requested`, as „Einkaufen · 7 Dinge“ (45 min); a list with nothing open is not listed; no tick, `action` „Zur Liste“; checklists never (routines own that); switch `showInPlan`. Why on request: a shopping list is never empty, so it would be a permanent row (CONCEPT-SOURCES §3.1 rule 1). **The request is the planner's item row, not a field on the list:** `plan.requested` with `ref` (`actions.ts placeRequested`) writes `planner_item` `<module>:<id>` with `excluded` off, creates no ToDo and runs as one undoable action; `run.ts requestedIds` hands every live, not excluded item row's id to its module's source (`collectPlannable(ctx, manifests, requested)`; run, input snapshot and board read the same set), so the request enters the input hash through the item it lists. „Nicht planen“ or the undo takes the list out; a ref whose source lists nothing leaves no row; the vault and modules without a source are refused. The request has no end of its own (the row stays after the list was emptied, so the list returns with its next open entry), so it is made visible instead of a new planner field: while the item row is live and not excluded the list's menu reads „Im Plan · Di“ (or „Im Plan · noch ohne Tag“) and offers „Nicht mehr planen“, also on an emptied list, which emits `plan.unrequested` – the planner's own exclude path (`actions.ts unrequest`), one undo; archived lists are never listed. The row action is `core/entitylinks/planRow.ts` (`usePlanRowAction`: nothing while the planner is off, „In den Plan“ → the event, „Im Plan · Di“ → `/planner?day=`); its wording comes from the calling module's strings. Source: [CONCEPT-SOURCES](../design/planner-hub/CONCEPT-SOURCES.md) §3.1–§3.3.
- **Pantry → shopping list is a link, expiry stays `attention` (2026-11-15, S3):** `shopping.requested` carries `ref` (the pantry entry); the lists service links the open list entry of that name to it (`_links`, entry → pantry entry, `origin`, `addLinkIfAbsent`). Both modules got a `linkTarget`. The pantry reads the reverse link through core: while the entry is open the badge reads „Auf der Einkaufsliste“ instead of „Wird knapp“ and the cart leads to the entry; a ticked or removed entry no longer counts. No plan row for an expiry.
- **A reminder is a state of the invoice, shown in three places (2026-11-15, planner hub S1, L5):** noting a reminder never makes a second thing: the plan row keeps its key `invoices:<id>` (pins and the day survive), there is one „done“ (paying, in invoices). The taps write synced link rows invoice → mail thread: „Anlegen“ `origin`, „Mahnung vermerken“ `dunning` with the mail's day (`modules/mail/links.ts` `linkInvoiceToThread`, through `addLink`; the capture sheet does the same for an invoice, except for sample mail). One undo takes entry and link back; noting twice writes nothing. The invoice shows them („Aus Mail“, „Mahnung aus Mail vom …“, „Im Plan“ → `/planner?day=`), in the panel and in its dialog (the phone has no panel); the thread's „Aus dieser Mail angelegt“ reads `_links` ∪ the device-local `mail_link` and opens `?open=<id>`. New invoices from the mail row carry no mail URL note (P56). Known limit: a second reminder in the same thread is the same link row, so its `on` stays the first reminder's day (`dunnedAt` on the invoice is right). No back-fill for older invoices (L12).
- **The reminder's deadline and amount are fields: `dunnedDueDate`, `dunnedAmountMinor` (2026-11-15, S1, L6):** invoices version 5, an empty migration step; written by `amendInvoice` when the reminder states them, each reset by the undo only while it still holds what was written. The invoice's `dueDate` / `amountMinor` stay. The source hands the planner `dunnedDueDate ?? dueDate` as the hard due (the planner still takes the earlier of it and a hard deadline set on the plan row) and priority 3 while dunned; the detail reads the fields in the language of now and keeps the note-line parse for reminders noted before. Why: the engine needs a date, not prose. Like `dunningLevel` / `dunnedAt` the fields are plain money facts: part of the import format and data API, not listed in `aiSchema` (structure only, and only what the assistant acts on). Known limit: an older app that rewrites the invoice drops them from its own row.
- **Money rows get `action`, never a tick; `?open` and `?do=pay` are untrusted (2026-11-15, S1, L7):** the invoice source hands over `action: „Bezahlt …“ → /invoices?open=<id>&do=pay`; the planner writes nothing. The page checks the id against live invoices, `do=pay` only opens the pay step (`components/PayStep.tsx`: day, sum, part payment below the rest, the undo toast) of an invoice that is still open and never calls `markPaid`; any other value is ignored and both parameters leave the URL. No pay dialog existed before (the list paid in one tap), so the step is new and small; „settle a late invoice“ is two taps. Test: the route causes zero writes (`payRoute.test.tsx`, `e2e/seed/dunning-chain.seed.spec.ts`). Subscriptions get „Kündigen …“ with package S2.
- **Deadline sources: trial ends, passed deadlines, documents (2026-11-15, S2, P55, P86):** subscriptions hand over the next of the missed notice deadline (`missedDeadline`), the next one in the plan and the trial end (kind `cancel`, „<Abo>: Probezeit endet“, hard on its last day) – one row per subscription, all with `action` „Kündigen …“ → `?open=<id>&do=cancel`. The module has no cancel step, so `do` adds nothing to `?open=`: the page writes nothing and strips both parameters. The vault is plannable: end minus notice → kind `cancel` („Vertrag/Versicherung kündigen“, only while the term runs), an end without notice → kind `renew` („Ausweis verlängern“, „Garantie prüfen“ …), 15 min, `action` „Zum Dokument“, `showInPlan` on. A date passed within 7 days (a trial end, a document date) is still handed over with its date in the past, so R2's „Frist vorbei“ (kinds `invoice`, `cancel`) can show it; never a permanent row (a subscription's missed notice deadline too, whatever its cycle). A document whose notice deadline passed more than 7 days ago gets no row for its end either: the term runs on, so the end is no deadline.
- **Vault plan titles are category wording only (2026-11-15, S2):** never the document's name, its file name or a custom category's name (the person's text) – titles reach calendar chips, timed blocks, the agenda, the widget and the run record. The name is `detail`, which only the planner page renders. Pinned by `core/modules/vaultPlanPrivacy.test.ts` (item titles, run record, planner rows, calendar, notifications).
- **The plan row shows links and the main action itself; one chip line, the action in the lead slot (2026-11-15, planner hub K1b):** `ThingRow` renders `PlannableItem.links` (the deprecated `link` read as `links[0]`) through `useResolvedLinks` as at most two chips under the meta (a reminder first; one per target; never wrapping, a long word ends in „…“, the full name is the accessible name and tooltip); every link also stands in ⋯ under „Verknüpft“ („Verknüpft · 3“ beyond two). Alive → the entity's in-app route; elsewhere/unavailable with an address → „Im Browser öffnen“, opened only on a tap; gone (and elsewhere without an address) → said in muted words, no action; loading → the chip is there, disabled. A row without a tick shows `item.action` as an outlined glyph in the lead slot (its word in the name, the tooltip and as first ⋯ entry); only an in-app route is followed, the planner writes nothing (L7). The same grammar for „Frist vorbei“, „Nächste Fristen“ (no ⋯ there) and the waiting group (chips and „Verknüpft“). Removed: the hard-coded ⋯ entries „Zur Notiz“ / „Zur Mail“ (`rowMenu.ts`) and the duplicated kind icon (the source glyph stands once: in the lead when nothing acts there, else in the meta). Shared parts got additive props: `ItemRow.below` (DOM between title and ⋯), `RowMenuItem.disabled`. Chip words follow the link: `dunning` „Zur Mahnung“, invoice „Zur Rechnung“, mail `origin` „Aus Mail“, other mail „Zur Mail“ – so the mockup's invoice row reads „Zur Mahnung · Aus Mail“, not „· Zur Rechnung“ (its own title opens the invoice). The kopf-leer phone bound for interactive elements rises 26 → 27 for the late invoice's „Bezahlt …“ lead (maintainer's approval in the chat, 2026-11-15).
