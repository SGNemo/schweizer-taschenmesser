# Decisions – Automations

- **Rules are data, the vault is out (2026-11-03):** a rule is trigger + conditions + actions (`core/automation/types.ts`, Zod). The action union is closed: entry (create/change through `aiSchema.actions`), reminder, notice, focus round, profile, suggestion. There is no delete, send or pay action; an `aiSchema` action of kind `delete` is refused at run time. `accounts` is neither a trigger nor a target (`EXCLUDED_MODULES`, `exclusion` tests).
- **Entries are written through the assistant's contract (2026-11-03):** `prepareOp` (validation, only enabled modules with an `aiSchema`) and `commitOps` with an additive `writer` option (importer `automation`, origin `automation`, shared `groupId`). Undo is `undoGroup` (edited entries stay) plus removing the run's notices, focus round and profile switch. The in-memory undo journal is not used: it does not cover background writes.
- **Fixed ids make devices agree (2026-11-03):** new entries get the id `auto-<hash(rule, occurrence key, action index)>`, so two synced devices that run the same occurrence create one record. Rule settings are the synced scope `automation`; the engine's books (limits, seen occurrences, notices, cursor) and the log (`_automationLog`) are device-local.
- **Events: one write hook plus module checks (2026-11-03):** `createRepo` reports local writes to `core/db/writeHook.ts` (no-op unless a listener is installed, never for sync-applied writes, listener errors are swallowed). State events (due soon, below minimum, price changed) come from per-module detectors run by the scheduler at most every 10 minutes. Nothing about how a module looks changes.
- **Guards (2026-11-03):** a rule is not run when it is already in the chain that caused the event (`cause.ruleIds`), at chain depth 3, twice for the same occurrence, above its limit per hour (default 3) or above the global limit per hour (default 10). Dry runs keep separate books and write only a log row. Refusals are logged once per rule and hour.
- **Calm by construction (2026-11-03):** reminders and hints are `soft`, `local` notifications from a core source in `collectDue`, so quiet hours, mute, game mode and the hourly limit apply unchanged and nothing is uploaded for Web Push. Everything is off until the master switch is on.
- **Modules opt in, and only to `create` (2026-11-03):** `manifest.automation` (lazy `automation.ts`) lists the collections that report writes, the domain events with their fields, detectors and the `aiSchema.actions` rules may call. Today that is `create` for todos, lists, calendar, invoices (suggestion), pantry; subscriptions, timetrack, habits and mail only report. `check:modules` refuses `delete` and unknown ids; modules without `aiSchema` and the vault cannot be targets. Mail events come over the bus and carry no title, so the rule log keeps nothing from a mail.
- **Occurrence keys, not timers (2026-11-03):** detectors report state ("due in 30 days") every ten minutes; the rule's conditions pick the moment (`daysLeft <= 3`), and the key `<type>:<id>:<date>` makes it fire once. Dry runs keep separate books.
- **Operated through existing parts only (2026-11-04):** two preview sections (settings: switch rows and a template list; log: `ItemList` like "Zuletzt gelöscht"), three palette commands and a dev button; no new components, no CSS. Suggestions (`suggest`) are confirmed in the assistant's `WritePreview` inside a `Dialog`, so one preview flow writes everything. A full rule editor is a proposal for later (see the PR text of package 3).
- **`ignoreFields` on a watched collection (2026-11-05, planner package 1):** `AutomationEventDef.ignoreFields` lists fields whose update alone is no `updated` event (`Object.keys(before) ⊆ ignoreFields`, checked in `ingest.ts`, carried from `module.ts` through `registry.watched` – which now returns the entry instead of a boolean – and `start.ts`). ToDos ignore `plannedFor` and `planMark`, so the planner's write-backs fire no rule; a user's date-only tap is silent too (accepted). `created`, `deleted`, `restored` and derived events (`todos.task.completed`) are unaffected.
