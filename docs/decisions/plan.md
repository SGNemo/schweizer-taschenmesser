# Decisions – Day and week planning (`planner`)

Index: [DECISIONS](../DECISIONS.md). Concept and prototype: [design/plan/CONCEPT.md](../design/plan/CONCEPT.md), packages: [design/plan/PACKAGES.md](../design/plan/PACKAGES.md).

- **Own module `planner` in the area Planen, not part of ToDos (2026-11-05, phase 1 answers):** own tables `planner_day`, `planner_item`, `planner_assignment`; sources from many modules through one contract. Why: ToDos stay the calm list; invoices, cancellation deadlines and notes need a contract anyway; a week-load widget needs its own place. Rejected: `/todos/plan` inside the ToDo module (grows the module, no place for non-ToDo sources).
- **Source contract `contributions.plannable` with write-back callbacks, requests over the bus (2026-11-05):** a source lists its open items and offers `onAssign`/`onDone`/`onEstimate`; other modules put something into the plan with `plan.requested` (mirrors `todo.requested`). The source owns what it already has (title, done, priority, due, estimate); the planner stores only planning facts (pin, split, energy, exclusion, overrides for sources without a field). `accounts` never gets the contribution (pinned in `exclusion.test.ts`).
- **Every open ToDo is plannable by default; the add field makes a ToDo (2026-11-05):** no own entry type in v1 (opt-out per item „Nicht planen“; `someday` and subtasks excluded). The planner writes `plannedFor` back, so the „Heute“ card, the morning digest, „Später“ and the focus round keep working unchanged; a `plannedFor` the planner did not write is read as a pin for that day. Rejected: a second „today“ surface in the planner (duplicate of the card).
- **Engine in `core/plan/` is pure and deterministic; assignments are stored (2026-11-05):** rules in a fixed order (capacity with buffer → pinned → hard due before priority → priority before age with sticky days → honest leftovers with reasons); the run writes assignments in one undo group. Stored rather than recomputed per device so all devices show one plan and the diff has a base. Nothing is pulled forward by itself; sessions of one item go on different days except under deadline pressure; main items per day reuse `focus.planLimit`.
- **AI replanning is local-only (2026-11-05, maintainer answer 1):** stage 0 rules (also with „KI aus“) and stage 1 local model (sees titles, nothing leaves the device); no cloud stage, the planner is excluded from every cloud prompt. Every instruction ends in a preview with a diff and an undo toast. Rejected: cloud with title-less numbers (dates and durations are still personal data; ~1 €/month for little gain).
- **Plan in the calendar = chips plus a link, not a tab (2026-11-05, answer 2):** the planner contributes `calendarItems` (`kind: 'plan'`); the calendar's view switcher gets a „Plan“ entry that links to the planner. Rejected: a tab (modules never import each other, so it would be a link in disguise) and a sixth calendar view.
- **Package 1 = the minimum to plan a week (2026-11-05, answer 4):** engine, contract, module with week board, ToDos source, available time and blockers per day, write-back, widget, undo; starts after `feat/identity-v3-frame` is merged (hotspot `core/modules/types.ts`). Identity: `indigo`/`sky`, head `kennzahl`, widget `fortschritt` (week load), signature `weekBars`, `order: 15`, `maturity: 'preview'` until package 3.
