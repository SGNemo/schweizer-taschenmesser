# Decisions – Day and week planning (`planner`)

Index: [DECISIONS](../DECISIONS.md). Concept and prototype: [design/plan/CONCEPT.md](../design/plan/CONCEPT.md), packages: [design/plan/PACKAGES.md](../design/plan/PACKAGES.md).

- **Own module `planner` in the area Planen, not part of ToDos (2026-11-05, phase 1 answers):** own tables `planner_day`, `planner_item`, `planner_assignment`; the manifest sets `dataApi: false` (the plan, blocker labels and day notes describe the user's days); `requires: ['todos']`. Ids are deterministic (day = date, item = `module:id`, session = `<itemKey>#<k>`), written through one helper (restore if tombstoned, then `upsert` – `upsert` alone keeps `deletedAt`), plain indexes only (`day.date`, `assignment.date`/`itemKey`) – a synced LWW table must merge two offline edits of the same day, not collide on a unique index; a unit that stops being placed is `remove`d. Why an own module: ToDos stay the calm list; invoices, cancellation deadlines and notes need a contract anyway; a week-load widget needs its own place. Rejected: `/todos/plan` inside the ToDo module.
- **Source contract `contributions.plannable` with write-back callbacks, requests over the bus (2026-11-05):** a source lists its open items and offers `onAssign`/`onDone`/`onEstimate`; other modules put something into the plan with `plan.requested` (mirrors `todo.requested`). The source owns what it already has (title, done, priority, due, estimate); the planner stores only planning facts (pin, split, exclusion, a hard due marked in the plan or written as „bis <Tag>“ in the planner's field, the user's earliest, overrides for sources without a field; own titles stay empty in v1). `accounts` never gets the contribution – already pinned by the vault's fixed contribution keys in `exclusion.test.ts`. Blockers come from timed `calendarItems` of kind `event`/`external` only; reminders never block. The run is driven by live queries over the sources, the timed calendar items and the planner's tables, not by `core/db/writeHook` (one listener, owned by the automation engine).
- **Every open ToDo is plannable by default; the one field makes a ToDo (2026-11-05):** no own entry type in v1 (opt-out per item „Nicht planen“; `someday` and subtasks excluded; no estimate = 30 min). The planner writes `plannedFor` and a new optional `planMark = { date, order, prior }` back for every item of a day (`prior` = the user's own date it overwrote), so the „Heute“ card (marked items first by `planMark.order`, then the rest by `order`, `planLimit` shown plus „+ n mehr“), the morning digest, „Später“ and the focus round keep working unchanged; the card and „Anfangen“ keep using the ToDo's whole estimate, the session length lives on the board (accepted). **The mark carries its date:** a `plannedFor` is planner-own only if `planMark.date === plannedFor`; every other combination (no mark, another day, a mixed field-level LWW merge) reads as user-set – the safe direction, because sync merges each field on its own. Every ToDo-side writer of `plannedFor` (editor, inbox sorter, wrap-up, „Für heute“, create-on-Heute, „Später“, board move) goes through one helper that clears the mark only when the date really changes; the import and data-API write path strips it; the „Heute“ card sorts by the mark only when its date matches; while the planner is inactive the ToDo side ignores the mark and, behind the sync gate and a stored disabled state, restores `prior` or clears. A user `plannedFor` is read as **earliest**, never as a pin, is copied to the planner-owned `item.earliest` before the first overwrite, is replaced by any later user change (a clear removes it) and is restored from `prior` when the module is disabled (written back only when it is not in the past); pins come only from the planner's „Festnageln“. On the ToDo page a planner-written date behaves like a user date (Heute/Bald) with a quiet „im Plan“ label in Bald. Rejected: a write-back cap per day (splits „today“ between card and board), treating user dates as pins, a stored write stamp (unknowable before the write and racy under paged pulls), a bare order marker without its date (loses under field-level LWW).
- **Runs write back idempotently; user actions are one `undoable` (2026-11-05, council rounds 2–4):** every run writes only planner-own values and only when they differ. A run started from the planner UI runs inside the user's `undoable`, write-backs included; every other run (ToDo-page edit, calendar change, sync, day change, app start, undo) is background: serialised, not undoable, same idempotent write-back. a user date is copied, cleared or overwritten only while a new core helper `syncSettled()` is true (always without sync; otherwise the sync lock chain is free and the last pull ended complete – a paged or failed pull can split one record's field ops); with the gate closed the run uses the date in memory only. Convergence comes from determinism: the input hash (today, settings, items with their planner flags, days, stored and calendar blockers) leaves out `prev`, the mark and the `planner_assignment` rows; a run whose output equals the stored rows writes nothing; the in-day order is recomputed without `prev` (tier from the placing rule), so the fixpoint `plan(x, prev = plan(x)) == plan(x)` holds over (unit, date, minutes, order); a unit that keeps its day keeps its stored reason; a sync-applied assignment change triggers one recompute that writes only differing rows (tests: zero follow-up writes, fixpoint, undo stays undone, two devices converge, a new appointment replans, no sync → earliest copied, gate closed → no overwrite, split pull pages copy no earliest). A later-stamped background write-back may beat a concurrent offline „Später“ from another device under field LWW – accepted, as for every synced field. Write-backs that touch only `plannedFor`/`planMark` emit no `todos.task.updated`: a new `ignoreFields` on `AutomationEventDef` carried from `module.ts` through `registry.ts`/`start.ts` into `ingest.ts` (`Object.keys(before) ⊆ ignoreFields`, updates only), which also silences a user's date-only tap (accepted; `todos.task.completed` is unaffected). Disabling the module uses a new additive, awaited `module.disabling` event emitted before the state write and any wipe: the planner stops its runs and restores user dates from `prior` in both policies; `bus.emit` swallows handler errors, so the fallback is the ToDo side, which restores or clears whenever it sees a stored disabled state and the sync gate open; a user date that never reached `prior` (offline device) is lost – accepted and tested. Rejected: "background runs never write back" (the „Heute“ card shows `plannedFor ≤ today`, so a morning without a planner action must still move yesterday's leftovers), an origin signal (live queries have none), a cleanup on `module.disabled` (fires after the delete-policy wipe).
- **Engine in `core/plan/` is pure and deterministic (2026-11-05):** rules in a fixed order (capacity with buffer → pinned → hard due inside the horizon before priority, the only rule that pulls forward → priority before age with kept over carried → honest leftovers with every cause named); nothing is pulled forward by itself (a done item frees room and the rest stays); causes name only units that outrank the moved one, never a session of the same item, and a later session „folgt auf Teil 1“; sessions of one item go on different days except under deadline pressure; main items per day reuse `focus.planLimit`; `free = usable − planned` is the figure every surface shows; `alles neu mischen` (`prev = []`) is the only explicit reshuffle. Rejected: recomputing per device without stored rows (plans would differ while sync lags).
- **AI replanning is local-only and the planner has no `aiSchema` (2026-11-05, maintainer answer 1, council round 4):** like mail, music and feeds the planner does not exist for the assistant, the cloud, the full-text search, the data API or chat context (`aiModules()` is the single filter; `exclusion.test.ts` pins the list). Stage 0 rules (also with „KI aus“) and stage 1 local model (desktop with a downloaded model; own prompt and grammar, called directly, not via `aiModules()`; gated on `(await isAiOn()) && localStageReady()`) work only in the planner's own field and apply their ops through the planner itself, never through `core/ai/write`. What it costs: „Donnerstag frei“ in the global bar stays a ToDo sentence. Every instruction ends in a preview with a diff and an undo toast. Rejected: cloud with title-less numbers (dates and durations are still personal data), an `aiSchema` with a cloud-only filter (a `transition` cannot carry minutes or a date, an unstored day cannot be targeted, and the filter would have touched `assistant.ts`, `scope.ts` and chat context), filtering in `aiModules()` (would switch stages off for every module).
- **Plan in the calendar = one chip per day plus a link, not a tab (2026-11-05, answer 2):** the planner contributes one summary `calendarItems` chip per day (`kind: 'plan'`, switchable), the „Heute“ card and the home agenda skip it, and the calendar's view switcher gets a „Plan“ entry that links to the planner. Rejected: a tab (modules never import each other), a sixth calendar view, one chip per assignment (crowds month cells, duplicates the card).
- **Calm by construction (2026-11-05, council rounds 1–4):** the board head carries one figure (today; „Heute ist frei.“ on a day with no time), the week lives in the widget („Bis So“ over the shown rows); rows show title and minutes, the reason sits behind „Warum hier?“; a toast names at most two moves plus „n weitere“; the waiting group is „Wartet auf freie Zeit“ (never „freier Tag“, which means a day off); a toast names at most two moves plus „n mehr“ under 68 characters per line; the field is „Eintragen“ in package 1 and „Eintragen oder sagen“ from package 2, German only, and one user-doc line says plan sentences go there, not into the global bar; the „Woche prüfen“ sheet is always reachable via ⋯, a quiet text link on Mondays from package 2 (switch `focus.weekCheck`, off by default, × dismisses per ISO week), never a dialog that opens by itself; the widget line is labelled with the last shown day; the overload figure lives in the head of the waiting group and is toasted only when it first goes above zero, at most once per week (switch) – no attention item, and the „Neu planen möglich“ hint there goes while the planner is on; no automation action and no `watch` on the planner (only the `planner.overloaded` event; `decisions/automation.md`: modules opt in to `create` only); „Neu planen“ of the ToDo page is hidden while the planner is enabled (it rewrites due dates); the widget uses `ProgressList` (`key`, `title`, `value`, `max`, `detail`) without `overText`; `formatMinutes` moves the timetrack duration helper into `core/i18n/format` and adds a compact form for boards; duration steps 5/15/30/60 plus free entry; learning from time tracking, energy profile, habit blocks and the week review are a later concept of their own.
- **Package 1 = the minimum to plan a week (2026-11-05, answer 4):** engine, contract, module with week board, ToDos source (plus the optional ToDo field `planMark`, the core `ignoreFields`, the `module.disabling` event and the `syncSettled()` helper), available time and blockers per day, write-back, widget, undo; starts after `feat/identity-v3-frame` is merged (hotspot `core/modules/types.ts`); packages 2–5 follow in sequence. Identity: `indigo`/`cobalt`, head `kennzahl`, widget `fortschritt` (week load), signature `weekBars`, `order: 15`, `maturity: 'preview'` until package 3; the 26° distance to cobalt and violet is re-checked after the frame merge.
- **Package 1 as built (2026-11-05):** rolling week from today on board, strip and widget; available minutes = three settings (weekday/Sa/So), per-date values in `day` rows; a background run skips while hash, row signature and the `item.earliest` copies are in step (source dates are not hashed); „Später“ on the board = `onAssign(id, tomorrow)` without order; excluded things end the waiting group; `PlannableItem.createdAt` is the age tie-break; `PlannableSource.onRelease` hands a date back on switch-off (also a past `prior` – the same rule as the ToDo side's clean-up), while `onAssign(id, undefined)` in a run keeps a past date off today's card; the data API drops `internal` fields instead of rejecting; `schema-history.json` lists released versions only. Council: `RunDeps.aborted` (a run that outlives the switch-off writes nothing more); planner undo entries carry a scope and are forgotten on `module.disabling`; the ToDo clean-up runs from a live query (stored planner state, gate, marks), so a late mark is cleaned without a restart; `syncSettled()` awaits the running round; a stale page's action ends in one toast (`PlannerOffError`); the seed's `afterSeed` runs the planner once and registers the rows it made for the todos seed's tasks (`ctx.seeded`; a person's own rows and marks stay theirs), the loader purges the outbox of registered rows, `beforeRemove`/`afterRemove` suspend and resume the runs around the removal; the board shows four days a row and seven from 73rem of page width (layout `full`), the minutes lead the meta line, so no row runs past a column; the gate waits for a running sync round only for background runs.
- **One field for entering and saying; one chip per day (2026-11-05, package 2):** the planner page keeps one field: German sentences („Donnerstag frei“, „schieb Steuer auf Fr“, „alles von Do nach Fr“) are read first by stage 0 (`core/plan/instructions.ts`, quick-capture date/end-time extractors, `pickTarget`/`withinOneEdit`), everything else stays a ToDo; a sentence never writes directly – it ends in `PlanPreview` (moved with cause, new, waits) and „Übernehmen“ is one `undoable`. Two equal matches ask, a planning verb with an unreadable rest explains, a thing is named without a verb only word for word („Müll raus“ stays a ToDo). Other languages keep „Eintragen“ and the ⋯ actions. The calendar gets one all-day chip per planned day (never one per session), switchable; the „Heute“ card, the agenda block and the head line skip it. Quick capture `p`/„plan:“ saves in two stages (ToDo through the `todo` target, then `planner_item` `todos:<id>` through the manifest repo; undo removes both). The lists' „Wochenplanung“ routine becomes a link to „Woche prüfen“ while the planner is on (focus checklist 9).
- **Heute follows the plan, nothing disappears (2026-11-06, sweep N02):** while the planner is on, a later day it gave a ToDo (`planMark.date === plannedFor`) wins over an older due date – the ToDo page (list, board, head count, „Als Nächstes“) and the „Heute“ card's „Jetzt dran“ treat it as „Demnächst“ until that day (`viewOf(…, planner)`, `isLaterInPlan`); a user's own date and an overdue thing the planner has not placed keep the plain rule, so the counts can differ by the unplaced ones; in „Alle“ and „Demnächst“ such a thing stays grouped by its due date („Wartet noch“, with „im Plan: Tag“ in Demnächst). „Alle auf heute“ steps back like „Neu planen“. Board: seven columns only from 95rem of page width (a column keeps ~210 px; titles never break inside a word).
