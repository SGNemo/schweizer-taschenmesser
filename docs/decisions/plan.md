# Decisions – Day and week planning (`planner`)

Index: [DECISIONS](../DECISIONS.md). Concept and prototype: [design/plan/CONCEPT.md](../design/plan/CONCEPT.md), packages: [design/plan/PACKAGES.md](../design/plan/PACKAGES.md).

- **Own module `planner` in the area Planen, not part of ToDos (2026-11-05, phase 1 answers):** own tables `planner_day`, `planner_item`, `planner_assignment`; the manifest sets `dataApi: false` (the plan, blocker labels and day notes describe the user's days); `requires: ['todos']`. Ids are deterministic through `repo.upsert` (day = date, item = `module:id`, session = `<itemKey>#<k>`), plain indexes only (`day.date`, `assignment.date`/`itemKey`) – a synced LWW table must merge two offline edits of the same day, not collide on a unique index; a unit that stops being placed is `remove`d, one that returns is `restore`d (`upsert` keeps a tombstone). Why an own module: ToDos stay the calm list; invoices, cancellation deadlines and notes need a contract anyway; a week-load widget needs its own place. Rejected: `/todos/plan` inside the ToDo module.
- **Source contract `contributions.plannable` with write-back callbacks, requests over the bus (2026-11-05):** a source lists its open items and offers `onAssign`/`onDone`/`onEstimate`; other modules put something into the plan with `plan.requested` (mirrors `todo.requested`). The source owns what it already has (title, done, priority, due, estimate); the planner stores only planning facts (pin, split, exclusion, a hard due marked in the plan or written as „bis <Tag>“ in the planner's field, the user's earliest, overrides for sources without a field; own titles stay empty in v1). `accounts` never gets the contribution – already pinned by the vault's fixed contribution keys in `exclusion.test.ts`. Blockers come from timed `calendarItems` of kind `event`/`external` only; reminders never block. The run is driven by live queries over the sources, the timed calendar items and the planner's tables, not by `core/db/writeHook` (one listener, owned by the automation engine).
- **Every open ToDo is plannable by default; the one field makes a ToDo (2026-11-05):** no own entry type in v1 (opt-out per item „Nicht planen“; `someday` and subtasks excluded; no estimate = 30 min). The planner writes `plannedFor` and a new optional `planOrder` back for every item of a day, so the „Heute“ card (sorted by `planOrder ?? order`, `planLimit` shown plus „+ n mehr“), the morning digest, „Später“ and the focus round keep working unchanged; the card and „Anfangen“ keep using the ToDo's whole estimate, the session length lives on the board (accepted). **`planOrder` is the marker:** only the planner writes it and every ToDo-side writer of `plannedFor` clears it in the same patch, so a value is recognisably planner-own or user-set without any stamp or row ordering. A user `plannedFor` (also „Später“, „Auf morgen schieben“, inbox sorter) is read as **earliest**, never as a pin, is copied to the planner-owned `item.earliest` before the first overwrite, is replaced by any later user change (a clear removes it) and is restored when the module is disabled; pins come only from the planner's „Festnageln“. On the ToDo page a planner-written date behaves like a user date (Heute/Bald) with a quiet „im Plan“ label. Rejected: a write-back cap per day (splits „today“ between card and board), treating user dates as pins, a stored write stamp (unknowable before the write and racy under paged pulls).
- **Runs write back idempotently; user actions are one `undoable` (2026-11-05, council rounds 2–3):** every run writes only planner-own values and only when they differ. A run started from the planner UI runs inside the user's `undoable`, write-backs included; every other run (ToDo-page edit, calendar change, sync, day change, app start, undo) is background: serialised, not undoable, same idempotent write-back; runs triggered by sync-applied writes wait until the pull has finished. Convergence comes from determinism: the input hash (today, settings, items, days, stored and calendar blockers) leaves out `prev` and the planner's own rows, a run whose output equals the stored rows writes nothing, the fixpoint `plan(x, prev = plan(x)) == plan(x)` holds, and a sync-applied assignment change triggers one recompute that writes only differing rows (tests: zero follow-up writes, fixpoint, undo stays undone, two devices converge, a new appointment replans). A later-stamped background write-back may beat a concurrent offline „Später“ from another device under field LWW – accepted, as for every synced field. Write-backs that touch only `plannedFor`/`planOrder` emit no `todos.task.updated`: a new `ignoreFields` on `AutomationEventDef` in core (`module.ts`, honoured in `ingest.ts`), which also silences a user's date-only tap (accepted; `todos.task.completed` is unaffected). Disabling the module first stops the run subscription; with the keep policy it restores user dates from `item.earliest`, with the delete policy (rows already wiped by `disableModule`) it clears every planner-own value. Rejected: "background runs never write back" (the „Heute“ card shows `plannedFor ≤ today`, so a morning without a planner action must still move yesterday's leftovers) and an origin signal (live queries have none).
- **Engine in `core/plan/` is pure and deterministic (2026-11-05):** rules in a fixed order (capacity with buffer → pinned → hard due inside the horizon before priority, the only rule that pulls forward → priority before age with kept over carried → honest leftovers with every cause named); nothing is pulled forward by itself (a done item frees room and the rest stays); causes name only units that outrank the moved one, never a session of the same item, and a later session „folgt auf Teil 1“; sessions of one item go on different days except under deadline pressure; main items per day reuse `focus.planLimit`; `free = usable − planned` is the figure every surface shows; `alles neu mischen` (`prev = []`) is the only explicit reshuffle. Rejected: recomputing per device without stored rows (plans would differ while sync lags).
- **AI replanning is local-only (2026-11-05, maintainer answer 1):** stage 0 rules (also with „KI aus“) and stage 1 local model (desktop with a downloaded model; sees titles, nothing leaves the device; gated on `(await isAiOn())`); no cloud stage. The planner keeps an `aiSchema` for rule hints and the local grammar, so the exclusion is a **cloud-only filter** (`aiSchema.cloud: false`, `cloudModules()` in `core/ai/scope.ts`) applied on every cloud path of `core/ai/assistant.ts` (system prompt, tools, `schemaHash`, `writable` for privacy; tiers 2/3 on `ctx.manifests`/`known` for consistency, so a guessed `planner` op is `unknown-module` and `show_agenda` collects no plan chips); the chat module never offers the planner as context, for any engine, because stored context is replayed after an engine switch. The four planner actions are transitions with `aiActionHandlers` that upsert the day by date (the generic path would create a second row for an unstored day). `aiModules()` stays unchanged. A ToDo attached as chat context carries its `plannedFor`/`planOrder` as it always carried its fields. Rejected: cloud with title-less numbers (dates and durations are still personal data; ~1 €/month for little gain), filtering in `aiModules()` (would switch stages 0 and 1 off), filtering chat context only while the engine is cloud (the engine can change later).
- **Plan in the calendar = one chip per day plus a link, not a tab (2026-11-05, answer 2):** the planner contributes one summary `calendarItems` chip per day (`kind: 'plan'`, switchable), the „Heute“ card and the home agenda skip it, and the calendar's view switcher gets a „Plan“ entry that links to the planner. Rejected: a tab (modules never import each other), a sixth calendar view, one chip per assignment (crowds month cells, duplicates the card).
- **Calm by construction (2026-11-05, council rounds 1–3):** the board head carries one figure (today), the week lives in the widget; rows show title and minutes, the reason sits behind „Warum hier?“; the field is „Eintragen“ in package 1 and „Eintragen oder sagen“ from package 2, German only; „Woche prüfen“ is a quiet line on Mondays (switch `focus.weekCheck`, dismissal device-local per ISO week), never a dialog that opens by itself; the overload figure lives in the head of the waiting group and is toasted only when it first goes above zero, at most once per week (switch) – no attention item; no automation action and no `watch` on the planner (only the `planner.overloaded` event; `decisions/automation.md`: modules opt in to `create` only); „Neu planen“ of the ToDo page is hidden while the planner is enabled (it rewrites due dates); the widget uses `ProgressList` (`key`, `title`, `value`, `max`, `detail`) without `overText`; `formatMinutes` moves the timetrack duration helper into `core/i18n/format` and adds a compact form for boards; learning from time tracking, energy profile, habit blocks and the week review are a later concept of their own.
- **Package 1 = the minimum to plan a week (2026-11-05, answer 4):** engine, contract, module with week board, ToDos source (plus the optional ToDo field `planOrder` and the core `ignoreFields`), available time and blockers per day, write-back, widget, undo; starts after `feat/identity-v3-frame` is merged (hotspot `core/modules/types.ts`); packages 2–5 follow in sequence. Identity: `indigo`/`cobalt`, head `kennzahl`, widget `fortschritt` (week load), signature `weekBars`, `order: 15`, `maturity: 'preview'` until package 3; the 26° distance to cobalt and violet is re-checked after the frame merge.
