# Decisions – Day and week planning (`planner`)

Index: [DECISIONS](../DECISIONS.md). Concept and prototype: [design/plan/CONCEPT.md](../design/plan/CONCEPT.md), packages: [design/plan/PACKAGES.md](../design/plan/PACKAGES.md).

- **Own module `planner` in the area Planen, not part of ToDos (2026-11-05, phase 1 answers):** own tables `planner_day`, `planner_item`, `planner_assignment`, all `dataApi: false` (the plan, blocker labels and day notes describe the user's days); `requires: ['todos']`. Why: ToDos stay the calm list; invoices, cancellation deadlines and notes need a contract anyway; a week-load widget needs its own place. Rejected: `/todos/plan` inside the ToDo module (grows the module, no place for non-ToDo sources).
- **Source contract `contributions.plannable` with write-back callbacks, requests over the bus (2026-11-05):** a source lists its open items and offers `onAssign`/`onDone`/`onEstimate`; other modules put something into the plan with `plan.requested` (mirrors `todo.requested`). The source owns what it already has (title, done, priority, due, estimate); the planner stores only planning facts (pin, split, exclusion, a hard due marked in the plan, overrides for sources without a field). `accounts` never gets the contribution – already pinned by the vault's fixed contribution keys in `exclusion.test.ts`. Blockers come from timed `calendarItems` of kind `event`/`external` only; reminders never block.
- **Every open ToDo is plannable by default; the one field makes a ToDo (2026-11-05):** no own entry type in v1 (opt-out per item „Nicht planen“; `someday` and subtasks excluded; no estimate = 30 min). The planner writes `plannedFor` back for at most `planLimit` items per day in plan order, so the „Heute“ card, the morning digest, „Später“ and the focus round keep working unchanged. A `plannedFor` the user set (also „Später“, „Auf morgen schieben“, inbox sorter) is read as **earliest**, never as a pin; pins come only from the planner's „Festnageln“. A `plannedFor` equal to the planner's last write or the current assignment is the planner's own (sync-safe). Rejected: treating user dates as pins (evening leftovers would pile onto tomorrow) and a second „today“ surface in the planner.
- **Engine in `core/plan/` is pure and deterministic; assignments are stored with deterministic ids (2026-11-05):** rules in a fixed order (capacity with buffer → pinned → hard due inside the horizon before priority → priority before age with kept over carried → honest leftovers with every cause named); row id `<itemKey>#<k>/<of>`, so devices that run before they sync write the same rows and a run updates in place. A user action awaits its run inside one `undoable` (including the write-backs); background runs (sync, day change) are serialised, not undoable, and never write back; runs ignore the writes they caused. Nothing is pulled forward by itself except by a deadline; sessions of one item go on different days except under deadline pressure; main items per day reuse `focus.planLimit`. Rejected: recomputing per device (plans would differ while sync lags), `core/db/writeHook` as the trigger (one listener, owned by the automation engine).
- **AI replanning is local-only (2026-11-05, maintainer answer 1):** stage 0 rules (also with „KI aus“) and stage 1 local model (desktop with a downloaded model; sees titles, nothing leaves the device; gated on `isAiOn()`); no cloud stage. The planner keeps an `aiSchema` for rule hints and the local grammar, so the exclusion is a **cloud-only filter** (`aiSchema.cloud: false`, `cloudModules()` in `core/ai/scope.ts`) applied to the assistant's cloud prompt, the write pipeline's cloud stage and the chat context with a cloud engine (including `calendarItems` of kind `plan`); `aiModules()` stays unchanged. Every instruction ends in a preview with a diff and an undo toast. Rejected: cloud with title-less numbers (dates and durations are still personal data; ~1 €/month for little gain) and filtering in `aiModules()` (would switch stages 0 and 1 off).
- **Plan in the calendar = chips plus a link, not a tab (2026-11-05, answer 2):** the planner contributes `calendarItems` (`kind: 'plan'`); the calendar's view switcher gets a „Plan“ entry that links to the planner. Rejected: a tab (modules never import each other, so it would be a link in disguise) and a sixth calendar view.
- **Calm by construction (2026-11-05, council round 1):** overload is a head line and a toast („2 h 40 mehr zu tun als frei“), not an attention item; no automation action on the planner (only the `planner.overloaded` event; `decisions/automation.md`: modules opt in to `create` only); rows show title and minutes, the reason sits behind „Warum hier?“; „Neu planen“ of the ToDo page is hidden while the planner is enabled (it rewrites due dates); the week review, learning from time tracking, energy profile and habit blocks are a later concept of their own.
- **Package 1 = the minimum to plan a week (2026-11-05, answer 4):** engine, contract, module with week board, ToDos source, available time and blockers per day, write-back, widget, undo; starts after `feat/identity-v3-frame` is merged (hotspot `core/modules/types.ts`). Identity: `indigo`/`cobalt`, head `kennzahl`, widget `fortschritt` (week load, overrun as text), signature `weekBars`, `order: 15`, `maturity: 'preview'` until package 3; the 26° distance to cobalt and violet is re-checked after the frame merge.
