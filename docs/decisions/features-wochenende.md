# Decisions in full – features – use case „Wochenende retten“

Part of [features](features.md). Index of areas: [DECISIONS](../DECISIONS.md).

- **Use case „Wochenende retten“ (2026-11-14, maintainer answers in `docs/design/usecases/wochenende/TARGET.md` §5, packages in `PACKAGES.md`):** (1) one entry „Tage einteilen“ – a sheet in three steps (things → time per day as chips → planner preview → take), reached from the welcome card and the empty planner, switches the planner on only on tap and never switches a module off; (2) the order of a day is said with optional day parts Vormittag/Nachmittag/Abend per plan item (planner's own row and `core/plan` only, no `plannable` change; the engine orders inside a day only, a part never changes the day), a break is a blocker that shows its own length and is never totalled, summed across days or rated; (3) sleep is a planner „Tagesende“ (optional per weekday group, caps the day's capacity, things that do not fit move on; an in-app head line near the end, no notification), no sleep data, no habit code (a habit „Ins Bett bis …“ is only pointed to); (4) Sunday/Monday reminders: only what the person sets, once at its time, never repeated – every reminder made by the quick capture or the planner field carries „einmal“ (calendar field `once`, visible on the row: exactly one notification at its time, no lead, stage or repeat), a timed line becomes a reminder only with a trigger word („erinnere mich“, „falls nötig“, „ggf.“); the deadline reminder „1 Std vorher“ is opt-in per deadline and sent by the ToDo itself (gone when it is done, deleted or moved); reminders set in the calendar dialog keep the global repeat rule. Health: the app stores only the typed title, no field, category or inference. Not now: a shared Google OAuth client (W15), auto-enabling time tracking (W14), WhatsApp access.
- **Revision after the second opinion (2026-11-15, maintainer: „wie empfohlen“; `docs/design/usecases/wochenende/REVIEW-FABLE.md`):** day parts are parked – the typed line order is the order of the day (package 2), built now are the break and estimates only; „Als Pause“ converts the ToDo into a blocker (no open ToDo for leisure; one additive `PlannableSource.onRemove?`); „Tagesende“ is one optional time and a head sentence with the existing „Rest verteilen“ link, no engine cap, no per-day row, no „Tagesbeginn“; reminders: `once` as decided, but „erinnere mich“ stays the only trigger word („falls nötig“, „ggf.“ dropped – the preview row switches to „Erinnerung“ in one tap); the deadline time (`due.time`, „1 Std vorher“) and „Beantwortet?“ on mail rows are parked (the latter until the W15 decision), the „Antworten: …“ line is dropped; each package lowers `MAX` for its own paths.
- **All packages are built (2026-11-15, maintainer):** the parked parts are released – day parts (4b, with fixed clock borders 12:00 and 18:00 cut to the window, never thirds), the deadline time (5b) and „Beantwortet?“ on mail rows (7, without the „Antworten: …“ line; W15 stays its own decision). The second opinion's advice against 4b and 5b is on record in `REVIEW-FABLE.md`; the maintainer decided to build them.
- **Package 5a follow-up (2026-11-15, maintainer: „Empfehlung umsetzen“, #904):** the row pick „Termin“ → „Erinnerung“ costs two taps (open the row target, pick); B and G accept taps 2 → 4 for one detour less each, no one-tap chip on every timed row (more stimulus); a recurring reminder from the capture also carries `once` (one notification per occurrence, no follow-ups, as Q4 a says „every reminder“); the hint of „Ruhig wiederholen“ names the exception.
- **„Beantwortet?“ built without W15 (2026-11-15, package 7 released by the maintainer; part (b) only):** a planned mail whose newest message carries `SENT` asks „Beantwortet? · Erledigt“ on its row (setting „„Beantwortet?“ anzeigen“, default on, display only). The flag is `lastFromMe` in mail's sealed, device-local thread header, read from `summarize`'s `lastLabelIds` (newest message only, never the union) and written only by the list (`useMailbox`, `saveThreads(…, { list: true })`); the background check (`notifyService`) and the head/widget refresh (`useSummary`) never set it and their header refresh drops it; the row asks only while ToDos are on. „Erledigt“ sends `todo.doneRequested` (the ToDo id only); the todos module ticks it off like a tap (`setDone`), the mail page wraps the emit in `undoable` for „Rückgängig“. No field on the ToDo or plan row, nothing closes by itself. The demo mailbox has an own address (`DEMO_EMAIL`) so a seeded answer never names a ToDo.
- **W23/W24 after the re-measure (2026-11-15, `fix/plan-weekend-w23-w24`):** „Tage einteilen“ reads a line with the quick capture's one line reader (`quickCapture/ui/batch.ts` `readLine`, also used by the capture's rows) and saves it through that target, so Termin, reminder (`once`), ToDo with deadline and hour, and break each land on the typed day; the sheet never asks (an unclear line is a ToDo as typed, a payment reminder the ToDo „Mahnung … prüfen“) and has no row pick (switching a line to „Erinnerung“ stays the capture's); its preview names the kinds with the capture's kinds line instead of the count. Known difference: „Frist So“ is a hard deadline in the planner field but a soft date in the sheet and the capture (the parser knows „bis“/„spätestens“ only; no new word here). „Als Pause …“ stays on the row's day and offers „Heute“ beside it when the plan put the thing elsewhere; a waiting thing has no day on the board, so it takes today, named in the sheet.
