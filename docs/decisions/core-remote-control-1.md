# Decisions in full – Core – remote control (concept, packages 1a–1b)

Part of [core](core.md). Index of areas: [DECISIONS](../DECISIONS.md).

- **Remote control: the phone steers the PC over the paired LAN hub (2026-11-10, `design/remote-control-concept`; the maintainer chose all four recommendations 2026-11-10: grant once per device, media with a locked PC, keyboard as its own package, module name „Fernbedienung“):** pairing is not permission. Input travels in an own session of the hub (same listener, keys and trust list, handshake mode 3, binary one-way records), never in the sync session and never on a new port; shown in the prototype with an assumed store time: input on a shared session waits as long as the store works, on its own session it does not. Accepted only on the stored home network. Grant per device, off by default, set only at the PC (device-local, native confirmation for every widening, none while a mouse/keyboard session is open), two levels: media/volume/lock without any simulated input, mouse/keyboard via `SendInput` (`windows` crate in a new `crates/remote-input`, no `enigo`, Windows only). Visible on the PC, one click ends and pauses the grant; locked PC: media only; never screen, clipboard, files, titles; input is never logged. Phone: module `remote` (`platforms: ['android']`, no collections); PC: a settings section. Rule in force since package 0 (2026-11-10): `docs/rules/remote-control.md` (own file because `RULES.md` is at its size budget), short line in root `CLAUDE.md` and in `RULES.md`. [CONCEPT](../design/remote-control/CONCEPT.md), [PACKAGES](../design/remote-control/PACKAGES.md).
- **Remote control package 1a: input session and grant in `crates/lan-sync` (2026-11-10, `feat/remote-hub-session`):** `src/input/` = `wire` (tags `0x20`–`0x26`, 4-byte records, every target), `remote` (master switch `MasterSwitch`/`FileSwitch`, grants, the one controller slot), `session` (hello → open → events through the gate), `limits`, `sink` (`InputSink`, typed `Action`s; the shell passes one in with `Router::with_input`, without it every input session is refused). Decided while building: (1) where input is not accepted (not the home bind, nothing wired) the hub answers message 1 with the **same authenticated `unknown-device` refusal** a stranger gets, not silence – no transport is kept, and the phone can tell it from an old hub (which stays silent) by trying sync; (2) binds carry `is_home` from the stored network id (also with a window open, fail-closed), checked by the **local address** a connection came in on; a flag that changes restarts no listener (`Launcher::home_changed`); (3) the grant is not a field of `Device` but `TrustStore::remote_of`/`set_remote` (defaults closed), stored per device in `trust.json` as `remote`, `remotePaused`, `remoteUnlock` (`serde` defaults, old files open with no grant, an unknown level is a broken file); (4) a session's level is fixed in `Remote::claim`; the same device opening anew replaces its older session, another device gets `busy`; (5) "Fernsteuerung beenden" marks the session (it says `ended` on its next tick) and pauses the device; the master switch off marks it `remote-off` the same way and refuses every later `open`; a grant that changes while its device controls ends that session without a reason when something is left (the phone opens again and reads its new grant from `opened`), with `not-granted`/`paused` when nothing is; none of this touches a sync session. A bind that stops being home (`Router::set_binds`) closes every input session; (6) limits per session: 500 events/s (burst 250), clicks 20/s, keys 30/s, text 512 B/s, media 10/s, volume up 5/s, lock 1 per 10 s; 2000 drops, then 200/s, close with `limit`; (7) the PC's state is polled from the sink on the connection's tick and sent at most every 200 ms; that never counts as activity. (8) home = the connection came in on a home bind **and** its peer is in that bind's subnet (a peer on a pairing-window network that dials the home address is not home); (9) widening needs a `Ticket` taken before the PC's confirmation: the setter refuses without one (`Unconfirmed`) and when a mouse/keyboard session is open or was opened since (`BusyControlled`); a session counts as open until its connection has finished, not until it was told to end; (10) a session remembers the mouse buttons it pressed: letting go of one of those passes every limit and the lock, and at its end it lets go of exactly those (the sink has no "release all"; a session never lets go of a button it did not press itself, so never of another device's); any other release is an ordinary, limited event; what a locked PC does not take counts as a drop; after frames came in the hub tells its state once within about half a second even if unchanged (the phone's sign that they arrived); the hub keeps reading for up to 500 ms after its last frame so the reason arrives while the phone still sends; (11) an app version from before this package rewrites `trust.json` without the three fields, so a downgrade loses all grants (closed). Phone side: `InputError::NoAnswer` = the hub hung up on the first message (a hub from before remote control, not this hub, or a hub shedding load), `InputError::Closed` = a send on a session that is over, `UnknownDevice` = authenticated refusal (never a reason to unpair), `Event::Closed(None)` = open again on the next touch. `input_client::InputSession` (reader thread, the Noise state behind a mutex held only to seal or open one frame).
- **Remote control package 1b, part 1: PC side in Rust (2026-11-10, `feat/remote-host-media`):** package 1b is split – this part is Rust only, the settings page, chip and web seam follow as their own PR (one topic per PR; the commands are complete without them). `crates/remote-input` knows neither the hub nor Tauri: typed commands in, four facts out (volume, mute, playing, locked), one worker thread that owns COM/WinRT, a bounded queue that drops instead of waiting, a state that is refreshed only when somebody asks. Media keys are **not** simulated (`VK_MEDIA_*` would be input): play/pause/next/previous go to the system media session, volume to the audio endpoint. The shell's `Sink` drops every non-media action until packages 3/4. `src/remote.rs`: every widening = `Remote::ticket()` → native blocking dialog (device name as plain capped text, level, last contact in whole days) → setter with the ticket; a narrowing never asks; one dialog at a time; an unreadable switch file = a switch that stays off. The ticket is taken **before** the "is a mouse/keyboard session open" check, and after the dialog the stored grant must still be the one the question described (`changed` otherwise). The claimed name never sits inside a sentence: own labelled line, invisible/direction characters dropped, quotation marks replaced; no name = a label with the first id characters. Narrowings of this run are remembered in the process and re-applied when a restarted hub reloads switch and grants from disk (without a ticket, so they can only narrow). The controls live in their own state (`RemoteHost`), not behind the hub lock, so the tray's "Fernsteuerung beenden" never waits for a slow hub command; they exist only while the hub runs. Tray: the page's labels, tooltip and "Heute" block are stored and every rebuild goes through one function that adds the controller from Rust state; updates from other threads are handed to the main thread (the tray state is only locked there); one thread is the only writer of the controller (commands and the tray click only wake it), and the tooltip names the controller first because Windows cuts tooltips at the end. Under "Fernsteuerung beenden" a grey line says that the device stays paused. `Worker::state` answers at once while somebody keeps asking; only the first question after a quiet time (reading older than 2 s, e.g. the `open` of a session) waits for a fresh one, at most 150 ms – an `open` must not be answered from a stale "unknown, locked" (the `InputSink` contract says so now), repeated refresh requests take one queue place, and `supported` is decided on the worker thread (a failed COM setup = unsupported). Native texts German/English in `texts.rs`. Guards: `tests/commands.rs` (async, no command simulates input, ticket before dialog before setter, hub wires and drops the controls), source tests in the crate.
- **Remote control package 1b, part 2: settings, chip, web seam (2026-11-10, `feat/remote-host-settings`):** seam `getPlatform().remoteHost` (status, setEnabled, setDevice, end; web stub unsupported, E2E fake `fakeRemoteHost.ts` that follows the shell's rules and lets a test answer the "Windows dialog"). The page never confirms a widening itself – no in-app confirm dialog on top of the native one (two questions for one step would teach clicking through); it says once that Windows will ask. `cancelled` is the person's answer and shows no message. The choice is a plain select per device, inactive with one sentence while the master switch is off. **Held back until package 3:** the level "mouse and keyboard" and the "Am Handy entsperren" option – nobody should confirm in a Windows dialog what does nothing yet and would then switch on silently (a level set elsewhere still shows). A paused device shows only "Wieder einschalten". A change sends one field merged into a reading made at that moment, so a device paused from the tray a second ago is not un-paused by lowering its level. State lives in a transient store (`core/remote/host.ts`, never persisted, device names in memory only; diagnostics canary added): the open section reads every 4 s, the always-mounted top-bar chip only while this PC is the home-network hub – no hub, no polling. Chip = neutral surface, icon + "Fernsteuerung: <device>" (icon alone in a narrow window), no motion, absent when nobody controls; a failed reading drops the controller from the page (the tray, drawn by Rust, stays the authority), and answers that overtake each other are dropped by a sequence number. Section is `preview`, visible on desktop only, and stays listed while the switch is on (`inUse.remote`). The shell's own texts (tray rows, tooltip, dialogs) now follow the app language: the page sends `lang` with the tray labels, Rust maps it to its fixed German/English texts (system language until then; kept in its own lock, so the tray state stays main-thread-only); the quit question follows it too.
- **Remote control: earlier narrowings are on the controls before the hub listens (2026-11-11, `fix/remote-narrowed-before-listen`):** `remote::parts` re-applies what was taken away at this PC earlier in this run (master switch off, a pause, a lower level whose write may have failed) right after it builds the controls from disk – before the router and the listener get them. Until now `attach` did it, after the supervisor's first round: for that moment a device could open a session with the grant from disk. Found in the review of the full-level notice (#689).
