# Decisions in full – Native, distribution, releases, security

Full text (decision, reason, source). One-line summary table: [DECISIONS](../DECISIONS.md).

## Native & distribution
- **Tauri 2 shell around the unchanged web app; thin by design.** PWA build stays the fallback; native builds drop the service worker (`TAURI_ENV_PLATFORM`). Source: commit fb1400b; architecture.md "Native distribution".
- **`PlatformService` is the only browser/native seam** (`@tauri-apps/*` only in `core/platform/tauri/**`, enforced by ESLint). Source: commit fb1400b.
- **Portable Windows exe instead of NSIS/MSI installers** (`tauri build --no-bundle`), with own signed self-update: `tauri-plugin-updater` can only launch installers, so it just checks/downloads; `portable.rs` re-verifies the minisign signature and swaps the running exe with rollback. `latest.json` has only `windows-x86_64-portable`. Breaking change: old installed 0.2.0-beta.1 cannot self-update. Source: commit 6a0f1aa.
- **Android APK signed by `scripts/android-sign.mjs`, not by Gradle** (no dependence on patches to the generated project); `gen/` is git-ignored and generated in CI. Source: architecture.md "Android".
- **Android `versionCode` derived from SemVer incl. pre-release rank** (monotonic; Tauri's default ignores pre-releases). Source: architecture.md "Versioning".
- **Bundle identifier `io.github.sgnemo.taschenmesser` never changes**; Android keystore and updater key must never be lost. Source: CLAUDE.md.
- **Closed-app reminders on Android via OS scheduling** (WebView has no Web Push); in-app scheduler stays quiet then. Source: architecture.md.
- **Secrets in OS keystore (Credential Manager / Android Keystore); Windows Hello is a consent gate, not cryptographic binding** – documented limit, master password stays the real protection. Source: architecture.md step 11b.

## Releases & security
- **Conventional Commits; release notes generated from them** (`scripts/changelog.mjs`). Source: architecture.md; CLAUDE.md.
- **Integration branch `develop`, PRs go there; `main` only for releases.** Source: PRs #2–#4 (base `develop`, PR #2 text: `main` would bury changes in the release diff); tag/merge history (`Merge develop into main (release 0.2.0)`).
- **Tag `vX.Y.Z[-beta.N]` triggers a signed release; tag must equal `web/package.json`; run fails without signing secrets.** Second way: `workflow_dispatch` on `main` with input `version` (must equal `web/package.json`, tag must not exist) creates tag + release itself; never use both for one release. Pushes to `develop` touching native/scripts and dispatch without `version` are dry runs. Source: architecture.md "Releases & CI".
- **Public-repo safety by construction:** gitleaks over history, `scripts/audit-release.mjs` on artifacts (secret values, key markers, forbidden file names, `.sig` key id), keystore file with `umask 077` + cleanup. Do not weaken. Source: architecture.md "Public downloads are safe by construction".
- **Windows binaries carry no Authenticode certificate** (SmartScreen warning documented); updater payload is verified with the updater key. Source: architecture.md.

- **Dev-Preview: rolling pre-release `dev-preview`, built after every green push to `develop`.** Why a job in `ci.yml` calling a reusable `dev-preview.yml` instead of `workflow_run`: `workflow_run` and `workflow_dispatch` only fire for workflow files on the default branch, i.e. never for `develop`. Only the latest state is kept (stable links, no clean-up logic). The tag `dev-preview` is not SemVer and never `v*.*.*`, so `release.yml`, `releases/latest`, the stable updater (`latest.json`) and the beta channel (`pickUpdate`, SemVer tags only) ignore it; the workflow compares `releases/latest` before/after. Same signing, audit, keystore handling as releases; no unsigned previews. Source: PR #28 (2026-10-01).
- **Dev-Preview is a separate app (the one sanctioned exception to "identifiers never change"):** Android package and Tauri identifier `io.github.sgnemo.taschenmesser.dev`, name "Nemo Dev", only in the dev flavor (`tauri.dev.conf.json`, merged by the workflow; stable config untouched, `brand-ids.test.ts` pins the relation). Why: with one package id every preview would need an Android `versionCode` between the previous preview and the next stable (the SemVer-derived codes leave about nine slots per patch version) and a broken build would damage the stable data; separate id = parallel install, separate data, independent monotone `versionCode` (minutes since the epoch). Windows: own data via the identifier, own portable folder `data-dev`, own Credential Manager service (`plugins/secure-store`, the stable service name equals the stable identifier, so existing entries are unchanged), share intent targets `${applicationId}.MainActivity`.
- **Dev-Preview signs with its own updater key** (`tauri.dev.conf.json` `plugins.updater.pubkey`, key id `FA423702E1D8B9CE`; secrets `TAURI_DEV_SIGNING_PRIVATE_KEY(_PASSWORD)`): a preview binary never carries a valid stable signature and vice versa, dry runs of `release.yml` stay unsigned, signed previews build only from `develop`. The Android keystore stays shared (different package id). `brand-ids.test.ts` pins both keys. Source: security launch review 2026-10-06, PR #90/#94.
- **Dev channel exists only in dev builds.** `UpdateChannel` gained `dev`, but the stored preference stays `stable|beta`; `effectiveChannel` returns `dev` only if the build was made with `VITE_RELEASE_CHANNEL=dev`. A stable app can therefore never offer a preview, whatever the settings say. Rust accepts `dev-latest.json` / `Nemo-Portable-dev.exe` only at `…/releases/download/dev-preview/`, the exe only if the identifier ends with `.dev`.
- **Dev version `<next stable>-dev.<commit count>` (+`<sha7>` for display), set only at build time** (`web/scripts/dev-preview.mjs`, `package.json` never written). Below the next stable by SemVer rule, above the previous stable and previous previews; the commit count is monotone on `develop` and independent of run counters.
- **`dev-latest.json` is uploaded last;** a client reading it between binary and manifest upload sees an exe whose signature does not match and refuses; the next check heals. Concurrency `cancel-in-progress` is kept as requested.
- **Actions in `dev-preview.yml` use the same refs as `release.yml`** (no new actions); the repository's workflows are not SHA-pinned yet, which is a separate follow-up for all workflows.
