# Decisions in full – Core – remote control (package 4)

Part of [core](core.md). Index of areas: [DECISIONS](../DECISIONS.md).

- **Remote control package 4, part 1: the PC types text and the keys of the fixed list (2026-11-11, `feat/remote-keyboard-host`):** package 4 is three PRs like package 3 – part 1 the PC side (this), part 2 the phone's client (text and key actions in `remote_client_send`), part 3 the page Tastatur. New file `crates/remote-input/src/keyboard.rs`: the keyboard part of `SendInput`, the second and last place that simulates input. **No "any key":** `Key` is the hub's list of sixteen, mapped one to one in the shell (`key_of`, written out – a key added on one side does not compile until it is decided there); the one combination (Alt+Tab) is one id, pressed and released inside one call, and if the system took only part of a call the releases are sent once more; no key is held between two calls. No Windows key, no Ctrl, no Shift, no media or volume key (pinned by name in `tests/rules.rs`, together with the exact sets of virtual keys and flags). **What is pressed is planned in plain code** (`strokes(key)`, `typed(text)`: a list of strokes – a key of the keyboard or a unit of text, down or up), which every system compiles and `tests/keyboard.rs` checks: each key that goes down comes up in the same plan, last down first; Alt exists only inside Alt+Tab. The Windows part only turns one planned stroke into one event – Linux never compiles it, so `tests/rules.rs` pins the file whole from the handle on (the thread, the way to the system's keyboard, the Windows part): an exact copy, comments and layout aside – a change fails the test on purpose and is updated together with a review. The plan above it may not use conditional compilation (the same plan on every system), and the crate is exactly its five files (no `#[path]`, `include!`, macro or sub-module that the reading tests would not see). Lists of forbidden spellings were tried first and kept leaking (a held Alt through a changed condition, an extra flag in one line, a swapped key). The two input files may also hold no `static`, lock or cell: nowhere a key or a text could stay. An earlier version built the events in the Windows part itself; review showed that a held Alt or a smuggled key there would have passed every test. **Text is typed as Unicode units** (`KEYEVENTF_UNICODE`, each down and up): the characters arrive whatever the PC's keyboard layout is; a unit never becomes a virtual key. The hub already refuses control characters and over-long text and applies nothing on a locked PC; the keyboard file drops control characters (and the two Unicode line breaks U+2028/U+2029 – a line break is the key Enter) and caps the length once more for itself (512 UTF-16 units, cut at a whole character). **Its own thread** (`remote-keys`), bounded queue of 32, one more is dropped: a line of text and the Enter after it keep their order; between keyboard, pointer and media there is no order – "lock, then a key" in one frame may still type the key before the PC is locked (nothing the phone could not do by sending the key first); on a locked PC the hub applies nothing and Windows refuses injected input. The text is moved from the hub's action into the one action that types it, never copied; nothing is logged, counted or stored. `crates/lan-sync` is unchanged (it has carried `Key` and `Text` since 1a). Nothing changes for users yet: no client sends a key. **Not verified:** compiled and linted for `x86_64-pc-windows-msvc`, but nothing was typed on a real Windows PC (hand tests come with the page: umlauts, emoji, a long word, an elevated window, a locked PC).
- **Remote control package 4, part 2: the phone's client sends keys and text (2026-11-11, `feat/remote-keyboard-client`):** `remote_client_send` takes sixteen key names (`key-enter` … `key-alt-tab`, one table `key_from`; anything else is `bad-action`) next to the media and mouse-button names – a key needs the mouse-and-keyboard level and is left out while the PC is locked, like a press. New command `remote_client_text(session, text)`: the text is checked whole first (1–2048 bytes of UTF-8, no control character and neither Unicode line break – a line break is the key Enter, never part of a text; else `bad-text`), then the session, the level (`bad-level`) and the lock (`locked`: nothing was typed, and the page is told – unlike a pointer move, typed text must not vanish silently); it is cut into frames of at most 256 bytes at whole characters and written **at the PC's pace**: the hub takes 512 bytes of text at once and 512 a second per session and drops what is over without a word, so the shell keeps its own reckoning of that budget (a little below it) and waits before a frame that would not fit – 2 KB take about four seconds and arrive whole. An earlier version wrote everything at once; review showed that long text would have arrived with gaps and still been reported as sent. Before every frame the lock and the session are asked again: stopped after a part was written is `cut`. **The text is passed on and forgotten:** no state, DTO, event or error carries it (the worker that writes answers with a fixed word – its error type cannot hold a text), nothing logs or formats (guards in `tests/commands.rs` pin the one `send_text`, the check before it, the sixteen names and that no DTO has a text field). Web: `RemoteService.text`, `RemoteKeyAction`; `core/remote/session.ts` gets `key(action)` and `type(text, enter)` on the same ordered queue as the pad – a line and the Enter after it keep their order, also against a click before them; a text is never dropped silently: `sent` (handed to the connection, whole – the PC does not confirm text), `locked`, `busy` (the queue is full, nothing typed), `failed`, or `partial` (a part was typed, or the Enter after it did not go: look at the PC before sending again) – also when the session ends or the page leaves while it waits; pasted control characters and line breaks become a space; long text goes in pieces of 400 characters. The E2E fake mirrors the shell and lets a test read back what was typed (the real shell keeps nothing). Still no page. **Not verified:** the `cfg(mobile)` paths are compiled only by the Android build after the merge; nothing ran on a phone.
