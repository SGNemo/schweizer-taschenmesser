# Decisions in full – features – use case „Kopf leer“

Part of [features](features.md). Index of areas: [DECISIONS](../DECISIONS.md).

- **Use case „Kopf leer“ – capture and mail (2026-11-08, maintainer answers in `docs/design/usecases/kopf-leer/TARGET.md` §6, packages in `PACKAGES.md`):** (1) A many-lines capture never books money: an invoice word makes an invoice, a reminder word first looks for the open invoice (module-free lookup in the capture layer: reference, then payee prefix with amount ≥ open rest within a fee tolerance, oldest overdue; ties stay a ToDo „… prüfen“) and raises it through `CaptureTarget.amend?` (writes only `dunningLevel` ≤ 3, `dunnedAt` and one note line; undo restores only that and never removes), everything else becomes a ToDo with the amount and a chip „Als Ausgabe buchen“; the single sheet keeps the draft and „Buchen“ – why: an overwhelmed batch must not stop for one money line, and the finance rule stays untouched because nothing books. (2) The mail row action „In den Plan“ and the invoice line „Anlegen“/„Mahnung vermerken“ write without the capture sheet – the one named exception to the „Vorschau-Pflicht“ of 2026-11-02 – because the values the sheet would preview (title „<Absendername> · <Betreff>“; payee, amount, date) are visible in the row before the tap and an undo follows it; a missing value falls back to the sheet, the folder batch keeps a real preview, `automation.md` („suggest, never silent create“) is unchanged. (3) Entries made from a mail get deterministic ids `mail-<hash>` from the thread id (ToDo) or the message id (invoice) only – never an address or the device-local account key – written create-if-absent via `createMany` (an existing id, live or tombstoned, stops both stages, registers no undo; a tombstone offers „Wieder einplanen“); the guarantee against duplicates holds once the first device's entry has synced; the mail module's link row is of type `todo`; the ToDo link is `kind: 'mail'`. (4) Stored Gmail links lose `?authuser=<address>`; shared text never splits (first line = title, the body only behind a tick). Rejected: bookings in a batch behind a named button (Q1 b) and no new shape at all (Q1 c) – both keep a stop or the selects; the minimal mail package (Q2 b) – still opens every mail; the name-only title with the fixed label „Mail“ (Q3 b) – loses the topic, two mails of one person would read the same; the explicit mode „Abladen“ now (Q1 d) and the automation „Label → Plan“ (Q2 c, reverses „mail only reports“) – later, own decisions.
- **„Kopf leer“ package 1 – what a batch turns into a ToDo (2026-11-08, maintainer: recommendation taken):** only lines that would be a booking (`requiresConfirm`, i.e. finance, also via `$`) become a ToDo with the amount and „Als Ausgabe buchen“; a subscription line („Netflix 12,99 monatlich“) or an invoice read from a due date without an invoice word („Strom 84 € bis 30.10.“) keeps its target – why: only bookings fall under the confirmation rule, these are open items. Narrows (1) of the bullet above.
- **„Kopf leer“ package 2 – the capture contract (2026-11-08):** a save with a fixed id goes through `createMany` (never `create`, which would overwrite or revive a tombstone); an empty result is read once more to tell `existed: true` from `'tombstone'`, and either stops both stages, registers no undo and is skipped by batch undo/rollback; `reinstateCapture` brings both records back through `restore`. `findOpenInvoice` order: reference → payee name prefix (also after „im Auftrag von“) with an amount from the open rest up to rest + max(20 €, 25 %) → oldest overdue; ties, a known payee whose amount does not fit, or a payee paid in the last 45 days or without a payment date (reminder and payment crossed) come back as candidates (the line becomes a ToDo „Mahnung … prüfen“; without ToDos it asks for a target), a new invoice only when no invoice of that payee exists; what is saved must be what the preview showed (any other outcome at save → the ToDo; no save while the lookup runs); a target picked by hand in the sheet is final when it differs from what the line shows at the moment of the pick, an unsure line included (decided then, not later; a preset such as the mail dialog's is no pick). `amend` reads and writes in two steps (a payment in between is a known, seconds-wide gap). `amend` writes only level + 1 (max 3), `dunnedAt`, one note line; its undo removes only that line and resets the two values only while they still hold what was written, never removes. The lookup runs at preview time and again at save; a settled invoice falls back to the ToDo. Why: a typed reminder never doubles an open invoice and never changes money.
- **„Kopf leer“ package 3b – the invoice line (2026-11-09):** a deleted invoice made from a mail offers „Anlegen“ again and that brings back the same invoice (no „Wieder anlegen“ wording: for money the verb stays the one the row showed); „not personal“ is not read as a newsletter for the invoice line (Gmail files invoices under updates) – the guard is `sure`: one amount, a date and a payee name (never an address), else the tap opens the sheet; the plan row of a noted reminder reads only the note line the reminder wrote; an invoice filed through the sheet keeps the sheet's random id, so only the device that filed it knows the row is done (its link row is device-local): on another device the row offers „Anlegen“ again and one tap would add a second invoice beside it, and on the same device a sheet-filed invoice of an older message of the thread counts only with the row's amount and due day (else offered again) – both until the follow-up lets the sheet take the message id. Why: one verb per row, no money from a guess, nothing of the person's own note in the plan.
- **„Kopf leer“ Nachlese (2026-11-09, maintainer: follow-up taken):** a plannable entry may carry a short `detail` the plan row shows after the minutes (a noted reminder: „Mahnung · 92,40 € bis …“), so its title stays „… bezahlen“ and the head's next step reads plainly; the capture sheet takes a fixed id per type (`idFor`, single save only, never a batch) and the mail dialog passes the invoice's message id, so the sheet and the row find one invoice (closes the cross-device gap of 3b); `plannedOn` in the capture layer reads the day the planner placed an entry on (key from the plan target's `via.id`), and the invoice line says „Im Plan · Mi“ only then (for the invoice under the row's id; one under the second id or filed through the sheet says „angelegt“); a deleted invoice comes back only while it holds exactly what the row would write and nothing else (no part payment, currency, account, repeat rule or reference only an edit sets) – otherwise the shown values are saved anew (the row: under a second id from the message and those values, so a repeat tap finds it – when that one too was deleted with other values, under a new id this device alone knows; the sheet: under its own id, known as done on this device through its link row); the many-lines sheet keeps its save button in view (sticky) and shows each line in one row. Why: the two misses of the remeasure (package 4) and the two follow-ups of 3b, each the smallest change.
