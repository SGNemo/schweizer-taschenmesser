## 1. Ist-Stand

- **Op:** `FieldOp {collection, id, field, hlc, value}`; HLC `"<ms13>-<ctr4>-<deviceId>"`, compared as strings, drift ≤ 1 h (N§3.1–2).
- **LWW:** twice – client `mergeOps` (`web/src/core/sync/ops.ts:39-77`, decision `:55`), server SQL `WHERE excluded.hlc > field_state.hlc` (`server/src/store.ts:172-178`); both read `contract/lww-cases.json` (10 cases) (N§5).
- **Engine:** pull (pages of 1 000, server `seq` cursor, `epoch` reset → all dirty), then push (≤ 2 000 ops / 3 MB); triggers start, 60 s, `online`, visible, 1.5 s after a write; Web Lock across tabs (N§3.4–6).
- **E2E:** optional, preselected; AES-256-GCM per value, AAD `collection/id/field`, key from passphrase via Argon2id (64 MiB, t 3), salt + check value on the server; only `value` is hidden (N§3.7). Key = non-extractable `CryptoKey` in Dexie `_secrets`, not in `getPlatform().secrets` (N§3.8).
- **Server role:** Fastify + SQLite, stores per field only the greatest HLC and a `seq`, never merges; device tokens (SHA-256), revoke/rotate; also Web Push and a feed proxy; binds `0.0.0.0:8787`, CORS `*` (N§4).
- **Local API:** desktop only, off by default, loopback hard-coded with no setting, token as SHA-256, refuses `Origin`; it is the AI import API, not sync (N§6).
- **Shell:** tray + autostart exist (autostart starts hidden in the tray); "In den Tray minimieren statt beenden" and "Mit Windows starten" both default off (`web/src/quickCapture/device.ts:25-26`). Android has no background service (N§7).

**Empfehlung: (b).** Ein kleiner Rust-Hub im Desktop-Shell erfüllt Svens Wunsch ohne Extra-Installation, hält das Bundle bei ~10 MB statt ~60–135 MB und läuft auch dann, wenn die WebView im Tray schläft. Der Preis ist eine dritte LWW-Kopie – eine einzige SQL-Bedingung wie im Server –, die per `cargo test` dieselben zehn Fälle aus `contract/lww-cases.json` bestehen muss, plus ein kleiner Vertrag für Push/Pull-Seiten, Cursor und Epoch. (c) ist die Alternative, falls Sven „so wenig Kopien wie möglich“ höher gewichtet als Robustheit im Tray (Frage 1) – ob (c) wirklich ohne zweite LWW-Entscheidung auskommt, ist offen (Tabelle).

**Shape of (b).** New crate `web/src-tauri/crates/lan-sync` (testable on Linux like `local-api`): `store` (SQLite `field_state`/`device`/`meta` like `server/src/store.ts:112-154`, LWW in SQL), `noise` (snow), `discovery` (mdns-sd), `hub`, `client` (Android and a second PC; discovery behind a trait: desktop `mdns-sd`, Android fed by the Kotlin plugin of package 4, until then the address hint). TS reaches it only through `getPlatform().lanSync` (`pair`, `request`, `status`; on the hub PC `request` is dispatched in-process to the hub, on clients over Noise) – `core/sync` never names a Tauri command (`docs/RULES.md:14`). One new `SyncAdapter` `lan` (push/pull/info map 1:1 to today's routes, N§3.5). Meaning stays in TS (`mergeOps`); the hub only stores and numbers, like the Node server.

**Key ownership (b).** Rust owns the raw keys it needs while the WebView may sleep: the device's static Noise key and, on the hub, the raw data key – kept in the OS keystore from Rust (desktop: unsicher which crate/API, e.g. Windows Credential Manager/DPAPI; Android: Keystore-wrapped through the existing `secure-store` plugin, N§7). TS never holds the static key; it receives the data key once per start (hub) or after pairing (client), and on the hub again after a rotation, before the epoch changes and imports it as a non-extractable `CryptoKey` in `_secrets`, as today (N§3.8). unsicher: the WebCrypto fallback of `getPlatform().secrets` (`secureStore.ts:3-4`) is not reachable from Rust, so it cannot be the hub's store.

## 4. Entdeckung & Kopplung

- **mDNS/DNS-SD:** service `_nemo-sync._tcp.local`; instance name random and **new on every start** (`nemo-3fa2`, never the PC's name); TXT `v=1`, `h=<first 8 bytes of HMAC-SHA256(key = SHA-256(hub static key), msg = UTC date)>` – rotates daily; paired devices know the hub key and accept yesterday/today/tomorrow (midnight, clock skew; prototype `hintsAround`). This only helps because the handshake never reveals the hub key to a stranger (`IK`, below); a stranger cannot recognise the hub across days. The display name travels only inside the encrypted channel.
  - Rust: [`mdns-sd`](https://crates.io/crates/mdns-sd) 0.21.7, Apache-2.0 OR MIT (announce + browse); alternative responder [`libmdns`](https://crates.io/crates/libmdns) 0.10.1, MIT.
  - Android: platform [`NsdManager`](https://developer.android.com/develop/connectivity/wifi/use-nsd) (no extra license); a raw multicast socket needs a [`WifiManager.MulticastLock`](https://developer.android.com/reference/android/net/wifi/WifiManager.MulticastLock) – both need an own Kotlin plugin (no Tauri API; unsicher: whether `mdns-sd` works on Android with only the lock).
  - Fallback: the QR carries the hub's IPv4:port; the phone remembers the last working address and tries it when mDNS finds nothing (multicast filtered). Pinning makes a wrong address harmless.
- **QR content** (59 bytes → `NEMO1:` + base64url, 85 characters, measured): version · hub **static public key** (32 B – long-lived and confidential by convention: never sent over the network, but kept by everyone who ever saw a QR, including revoked devices; see §5) · one-time pairing secret (16 B) · expiry (2 min) · port · IPv4 hint. **No long-term *secret* in the QR:** the pairing secret is single-use and expires; while the dialog is open the PC silently shows a fresh QR every 2 minutes. The hub checks the **current** secret already in message 1 (`IKpsk1`) and only then burns the window and shows a code – a stranger without the hub key (prototype `windowSurvivedStranger`) and a holder of the hub key with an old secret (old QR, revoked device, replay of an earlier window's message 1; prototype `oldQrHolderCannotBurn`) are dropped without effect; a second attempt with the used secret is dropped (prototype `reusedQrRefused`). The hub never answers a pairing attempt it cannot authenticate (no refusal byte, so nobody can probe whether a window is open); the phone maps a dropped connection during pairing to „Kopplung nicht möglich – am PC neu zeigen“. Rest: an on-path attacker who drops the real message 1 and replays it can burn the window (DoS only); if no `hello` follows within 10 s, the PC shows a fresh QR. The data key is never in the QR. No typed code form in round 1 (§2 „Zwei PCs“). QR scan on Android: official [`tauri-plugin-barcode-scanner`](https://crates.io/crates/tauri-plugin-barcode-scanner) 2.5.3, Apache-2.0 OR MIT (the WebView `BarcodeDetector` path is unsicher on Android, N§6).
- **Key exchange:** each device has a static X25519 key (created on first use, owned by Rust, §3; never synced, never in a backup). Noise pattern **`IK`** ([spec rev. 34](https://noiseprotocol.org/noise.html#handshake-patterns), §7.5 interactive patterns): the phone already knows the hub's static key (QR, then pinned), sends its own static key encrypted in message 1, and the hub **never sends its static key** – unlike `XX`, where the responder reveals it to anyone who connects. Pairing = **`IKpsk1`** (spec §9 pre-shared keys; the PSK is mixed in at the end of message 1, so the hub verifies it before anything else happens). After message 2 the phone sends a first transport frame (`hello` with its name); message 1 alone is replayable (spec §7.7), so frame limits, „zuletzt gesehen“ and the code on the PC wait for that frame. Both screens then show a 6-digit **short authentication string** from the handshake transcript (prototype `sasMatch`) – same idea as the extension's 6-digit pairing code (`docs/decisions/features.md:48`); the PC trusts the key and sends the data key only after the tap, which is bound to this attempt's code (prototype `keyAfterConfirm`). „Neu koppeln“ on a device always creates a fresh static key, so a revoked key is never trusted again. Residual: `IK` encrypts the phone's identity under `es` only, so whoever later steals the hub's private key can read which phones connected in recorded traffic (no initiator identity forward secrecy). Sessions: the hub accepts only keys in its trust list and answers others with an **authenticated** `unknown-device` (prototype `strangerRefused`); a host without the hub's private key cannot read message 1 and cannot answer (prototype `impostorRefused`). The prototype follows this shape, not the exact Noise message layout (§9).
- **Device trust:** the hub keeps `device {id, name, staticKey, pairedAt, lastSeenAt, revokedAt}` (same shape as today's `device` table, N§4); a new key is trusted only after the confirmation tap on the PC with matching codes. "Kopplung lösen" sets `revokedAt`. Devices are never trusted by address.
- **Only private addresses – and only the home network:** the hub binds the addresses of private interfaces only (10/8, 172.16/12, 192.168/16, 169.254/16; later IPv6 `fe80::/10`, `fc00::/7`), never `0.0.0.0`, never loopback, never a user-entered address; it drops peers from other ranges before the handshake; the phone refuses hubs announced at other addresses (prototype `isLanV4`). Because café/hotel/company Wi-Fi also uses private ranges, the hub additionally listens only on the network it was paired on (identified by the default gateway's address + MAC, remembered at pairing – unsicher: reliable on Windows; alternative: only when Windows classifies the network as "Private", unsicher: API and user confusion). **Fail-closed:** if the current network cannot be positively identified as the saved home network (one entry), the hub does not listen – with one exception: a pairing window the user opens on the PC listens on the current private network for its duration. Only the **first** pairing saves that network as home; later pairings elsewhere leave it unchanged. Changing it is explicit (new router): „Neuer Router? Dieses Netz als Heimnetz verwenden“ → „Ist das dein Heimnetz zu Hause? Nur dann bestätigen.“ [Verwenden] [Abbrechen] (§8). The PC cannot tell a café from a new router, so it never suggests this on its own. While listening the tray menu shows „Heimnetz-Abgleich aktiv“. Tailscale is out for round 1: its `100.64.0.0/10` addresses are shared address space ([RFC 6598](https://www.rfc-editor.org/rfc/rfc6598)), not private.
- **Guest / company Wi-Fi (phone side):** client isolation or filtered multicast → nothing is found; the phone sends only mDNS queries (they reveal the service name `_nemo-sync._tcp`, unsicher: tolerable). No SSID is read (needs location permission on Android, unsicher: from API 27/29) – pinning replaces it. Status stays the neutral banner from §2.
- unsicher: the Windows firewall prompts when the hub first listens (expected for a new inbound listener) and may file the network as "Public" and block silently; the pairing dialog says beforehand „Windows fragt gleich, ob Nemo im Heimnetz erreichbar sein darf – wähle „Zulassen““, and the hub state „Windows blockiert den Abgleich“ (§8) names the next step.

## 5. Sicherheit

E2E stays mandatory in LAN mode (no switch): the hub stores only `enc:v1:` values and rejects other pushes (test in package 2). The data key is random (32 B), created by the hub, sent to a newly paired device only inside the Noise channel and only after confirmation. **What E2E protects here, honestly:** the hub PC holds the data key itself, so against anyone with access to that PC it adds nothing; it protects the hub's store file and its copies (file backups, a copied disk image) and keeps the hub "server-blind" like an E2E server today.

**Schlüssel erneuern (key rotation):** like the server's `reset` (`server/src/store.ts:73-75,219-222`) the hub creates key version n+1, hands it to its own hub-local client, ends all open sessions, **wipes its field store** and starts a new `epoch`. At each device's next session it hands over the new key first; every push and pull – remote or in-process – carries the key version and is refused while it is n (the version is part of the request, not of `enc:v1:` – no format change), so an in-flight push encrypted under n cannot land in the wiped store. Every device then sees the new epoch, marks all records dirty and re-pushes under n+1 (`web/src/core/sync/engine.ts:66-69`); without the wipe the hub's LWW would keep the old-key ciphertext, because re-pushed ops carry the same HLCs. The lost device is revoked first, so it never receives version n+1. Tests in package 2: no version-n value left after rotation, also for a push encrypted under n that arrives after the wipe.

**Transport: Noise via [`snow`](https://crates.io/crates/snow) 0.10.0 (Apache-2.0 OR MIT), not TLS.** Reasons: (1) mutual authentication by static keys is Noise's native model – no certificates, no expiry, no clock dependence (HLC drift is already a sync error, N§3.6); (2) PSK pairing is a spec pattern (`IKpsk1`, spec §9), while rustls has no external-PSK support (unsicher); (2b) `IK` keeps the hub key away from strangers, TLS sends the server certificate to anyone; (3) pinning = compare 32 bytes, as in the prototype. unsicher: `snow` has no published third-party audit as far as checked; the council of package 2 decides. What would overturn it: an audit preference for rustls (already in the lock file) with pinned self-signed certificates plus a separate PSK proof and SAS after the TLS handshake – equally possible, more moving parts.

**Regel-Abgrenzung.** The Local API rule (`docs/RULES.md:8`: loopback only, never a bind-address setting) stays **unchanged**; the LAN hub is a separate service in a separate crate and must never share code paths that widen the Local API's address. **Vorschlag** for a new hard-rule line in root `CLAUDE.md` (+ full text in `docs/RULES.md`), only in package 1, only after Sven's yes:

> - **LAN sync (desktop hub):** separate from the Local API (whose loopback rule is unchanged); listens only while a pairing window is open or at least one device is paired, and only on a network positively identified as the paired home network (otherwise not at all); binds only private interface addresses (RFC 1918, link-local – never `0.0.0.0`, loopback or a user-entered address; tests exempt via `#[cfg(test)]` only) and drops other peers and oversized pre-handshake frames, with a per-address handshake rate limit; Noise `IK` (the hub never sends its static key), only devices in the trust list; frame limits are raised and device activity recorded only after the first authenticated transport frame; pairing only through the QR with a single-use secret ≤ 2 min, consumed and a code shown only after the initiator proved the current secret, plus matching codes and confirmation on the PC; a pairing window opened by the user may listen on the current private network for its duration (only the first pairing saves the home network; changing it needs an explicit confirmation); the data key only inside the channel after confirmation, never in the QR; values always E2E-encrypted; never log payloads, keys or pairing secrets; its LWW copy (`crates/lan-sync`) passes `contract/lww-cases.json`.

and the Sync rule becomes (**Vorschlag**): "…the rule exists three times (`core/sync/ops.ts`, `server/src/store.ts`, `crates/lan-sync/src/store.rs`) and is pinned by `contract/lww-cases.json` – change all or none."

## 6. Wann wird abgeglichen

- **Android, in the foreground (package 4):** today's triggers stay (start, 60 s, visible, online, after a write, N§3.6). New: an own Kotlin plugin registers a [`ConnectivityManager.NetworkCallback`](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback) for `TRANSPORT_WIFI`; on "Wi-Fi available" it emits an event → `syncNow()`. Works while the process is alive and its WebView may run JS – unsicher: Android may freeze cached background apps, so "recently backgrounded" may not be enough; package 4 measures it on a device (MANUAL-TESTS row „Handy kommt heim, App im Hintergrund“). Tauri 2 mobile has no network-change API of its own (unsicher: no official plugin found) → own plugin like `share-intent` (N§7).
- **Android, really in the background (not in round 1):** [WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started) with `NetworkType.UNMETERED`, periodic ≥ 15 min. Problem: the sync logic and the data live in the WebView (IndexedDB); a worker has no WebView – it would have to start one headless or move the engine to Rust. unsicher: feasibility and battery; therefore Frage 3.
- **PC:** the hub runs while the app process runs (window or tray). Autostart exists and starts hidden in the tray (N§6), but both "Mit Windows starten" and "Im Tray weiterlaufen" default off (`device.ts:25-26`). The pairing dialog therefore shows both switches **preselected** with one line „Damit dein Handy abgleichen kann, wenn du heimkommst“ (visible, one tap to turn off). They live in the device settings as today; the sync page shows only a fact line when one is off („Nemo startet nicht mit Windows · Ändern“).
- **Fallback:** opening the app always syncs (today's start trigger).
- **Conflicts:** unchanged field LWW (`mergeOps`), conflict list `SyncConflicts` stays (N§8).

## 7. Migration

- Server users keep their path: `selfHosted` adapter, settings and docs unchanged; LAN is offered as a second way, not forced.
- Switch without data loss: ① automatic backup first (existing backup, mandatory step in the switch dialog) ② the dialog lists every device the server still knows (existing device list, N§8) and says: „Diese Geräte gleichen weiter über den Server ab, bis du sie auch umstellst“ – with **Am Server sperren** per device ③ „Vom Server trennen“ (local data stays, `docs/user/sync.md:91`) ④ couple with the PC ⑤ first LAN sync: hub store is new → both sides push everything (`markAllDirty`), LWW merges.
- Rest risk: a device left on the server keeps diverging until it switches too; the warning in ② is the mitigation, nothing merges the two worlds automatically.
- E2E passphrase: LAN mode does not use it (random data key, handed over in the channel). The server's vault and passphrase stay on the server untouched; going back = connect with the passphrase as today. Users who want a recoverable copy keep the encrypted backup (unchanged).
- Hub reinstalled/lost: devices re-pair with the new hub (§2); nothing is lost because every device holds its data.
- One sync path at a time per device (no server + LAN in parallel in round 1): avoids two cursors/epochs in one engine (Frage 2).

## 9. Prototyp

[`proto/`](proto/), run `node docs/design/sync-lan/proto/run.mjs` (Node ≥ 20, no install, no dependencies). `hub.mjs` (A) announces `_nemo-sync._tcp` via an own minimal mDNS (`mdns.mjs`, `dgram`) with the daily hint, opens a one-time pairing window and prints the QR payload; `phone.mjs` (B) finds it, pairs with a Noise-*like* handshake in the `IK`/`IKpsk1` shape (`channel.mjs`: X25519 + HKDF + AES-GCM, hub key from the QR, PSK mixed into message 1, `hello` frame, SAS – **not** Noise, the product uses `snow`), shows the SAS, receives the data key after the simulated confirmation, pushes 1 000 E2E-encrypted ops (`enc:v1:`, same AAD as `crypto.ts`), pulls 2 000 back (1 000 from the PC + its own), decrypts, reconnects without PSK and runs the refusal checks. `run.mjs` plays the user: it compares both SAS and writes „confirm <code>“ to the hub (the tap is bound to the code). Refusals: `no-pairing-window` is an unauthenticated byte (shown only inside the pairing flow), `unknown-device` is encrypted under the session keys, so only the real hub can send it. Left out on purpose: LWW in the hub's store (append-only log), key rotation, the home-network check, rate limits, the exact Noise message layout.

Measured 2026-11-06, container, both processes on one host over the interface address (not real Wi-Fi), 9 rounds (the default of `run.mjs`), Node v22.23.4, Xeon 2.1 GHz:

| Measure | median | min | max |
|---|---|---|---|
| Discovery (mDNS query → resolved) | 5.5 ms | 4.5 | 9.3 |
| Pairing handshake + simulated confirmation + data key | 5.2 ms | 3.9 | 6.7 |
| Encrypt 1 000 values (E2E) | 15.2 ms | 13.6 | 26.9 |
| Push 1 000 ops (244 KiB) | 5.9 ms | 4.8 | 13.5 |
| Pull 2 000 ops (2 pages) | 10.7 ms | 8.3 | 20.7 |
| Decrypt 1 000 values | 11.9 ms | 9.9 | 14.2 |
| Reconnect (session handshake + empty pull) | 4.8 ms | 4.1 | 5.4 |
| Throughput push / pull | ≈ 169 000 / 187 000 ops/s | | |

Checks, all 9 rounds ok: `windowSurvivedStranger`, `oldQrHolderCannotBurn`, `sasMatch`, `keyAfterConfirm`, `decryptedOk`, `sessionUpToDate`, `reusedQrRefused`, `strangerRefused`, `impostorRefused`, `oversizeDropped`. They show that the handshake logic refuses what it should; they do not prove the product's transport secure (that is `snow`'s and package 2's council's job). Reading: crypto and transport cost nothing noticeable; on real Wi-Fi discovery is dominated by mDNS timing (responders may delay answers 20–120 ms, [RFC 6762 §6](https://www.rfc-editor.org/rfc/rfc6762#section-6)) and Wi-Fi latency – unsicher: real numbers need a phone (package 4 measures them). A first full sync of a large database is bounded by the existing engine (pages of 1 000), not by the LAN.

## 10. Entschieden (vorläufig)

- **Variant (b), Rust hub in the desktop shell.** Why: no extra install, +1–3 MB instead of +50–125 MB, runs while the WebView sleeps in the tray. Overturned by: Sven weighting fewer LWW copies over tray robustness (→ (c), after checking whether (c) needs a second LWW decision at all), or a measurement showing hidden WebView2 is never throttled.
- **Star topology, exactly one hub (a PC); phones and further PCs are clients; only the hub offers „Gerät koppeln“.** Why: one `seq` per store keeps today's cursor model; no phone listens (battery). Overturned by: a real need for phone↔phone without PC.
- **Transport Noise (`IKpsk1` pairing, `IK` + trust list afterwards) via `snow`; the hub's static key travels only in the QR; activity and frame limits only after the first transport frame.** Why: §4–5; `XX` would hand the hub key to anyone who connects. Overturned by: a security review preferring rustls with pinned certificates.
- **QR carries no long-term secret;** single-use 16-byte secret, checked in message 1 and burned only by a sender who proved it, 2 min, renewed silently while the dialog is open, plus a 6-digit code on both screens and a confirmation tap before the key is trusted and the data key sent; no typed code form in round 1. Overturned by: a pairing test showing the code comparison confuses people (then: keep the tap, show the code smaller).
- **E2E always on in LAN mode, random data key handed over in the channel, no passphrase; rotation wipes the hub store, new epoch, key version in every request.** Why: no typing; hub store holds only ciphertext. Overturned by: Sven wanting a passphrase-recoverable LAN store (then Argon2id as today, typed once per device).
- **Raw keys (static Noise key, hub data key) owned by Rust in the OS keystore; TS gets the data key as a non-extractable `CryptoKey`.** Why: the hub must work while the WebView sleeps. Overturned by: no usable OS keystore from Rust on Windows (then a key file with user-only ACL, unsicher).
- **Only private addresses, only a network positively identified as the paired home network (fail-closed), daily-rotating mDNS hint; no Tailscale in round 1.** Why: §4. Overturned by: Sven wanting LAN sync on the go (then a separate rule for the Tailscale interface).
- **Third LWW copy pinned by a Rust contract test; a small shared contract only for push/pull paging, cursor, epoch and the error codes the engine relies on (`contract/sync-paging-cases.json`); device management stays per transport.** Why: "LWW only where the contract checks it"; the engine's assumptions hold for both stores. Overturned by: choosing (c).
- **Server path stays; one path per device at a time; switch dialog warns about devices still on the server.** Overturned by: Frage 2.
- **Android: foreground + Wi-Fi callback while the process lives; no WorkManager in round 1.** Overturned by: Frage 3.
- **Pairing suggests „Mit Windows starten“ and „Im Tray weiterlaufen“ preselected (only in the pairing dialog).** Why: "PC an" must mean "Nemo an". Overturned by: Sven's answer to Frage 1.
- **Unauthenticated refusals never change the phone's state beyond the neutral banner;** „gelöst“ only after an answer authenticated by the hub. Why: an ARP spoofer must not push the user into re-pairing.
