## Idea 1 – share → planner

**Exists.** Android `ACTION_SEND` for `text/plain` (≤ 20 000 characters), PWA `share_target`, both land on `/share` (`pages/ShareTarget.tsx`): a card „Geteilt“ with the raw content; a card „Vorschlag“ with the quick-capture `CaptureForm` (`oneEntry`, `initialText` = the first line, `initialType?`, `extra`), which stores on its own „Speichern“ (U17) and calls `onSaved(saved)` – `saved` has `id`, `type`, `moduleId` and `undo()`; the unticked tick „Text als Notiz“ puts the rest into `extra.note`; under „oder im Modul öffnen“ links that only open a module's form. The capture type `plan` exists (`quickCapture/targets/adapters.ts`: a ToDo plus its planner item; a thing that comes into the plan this way has no day and lies under „Noch ohne Tag“).

**Behaviour.** (1) Share from any app → Nemo opens `/share`. (2) With the planner on, the „Vorschlag“ card's form starts with `initialType="plan"` (its target word is the capture's own for that type, „Planer“); he can change the kind in the form as built – then the two lines below go and the page behaves exactly as built (other capture targets drop `extra.note`). Under `plan` the form parses as built: a typed day word becomes the ToDo's own date, not a planner day – the thing lies under „Noch ohne Tag“. The line is as built (`sharedLine`); the built parser takes an address out of the title. Planner off: the page is exactly as today. No new target list, no radio group, no day chips, no new button – the button is the form's „Speichern“. No bus event is involved. (3) Under the form one line „Landet im Planer unter „Noch ohne Tag“.“ (only while the type is `plan`); for shared content with an http/https address of ≤ 2 048 characters, again only while the type is `plan`, a second line „Der Link wird mit abgelegt: {host}“ – the address is then stored as the first line of the ToDo's note (`extra.note`), also without the tick; a longer or non-http address is not stored as a link (it stays part of the text). „Text als Notiz“ as built for the rest; the rest is cut to 4 000 characters minus the address line („Gekürzt auf 4 000 Zeichen.“ says so). The card „Geteilt“ shows the whole shared content as built, so nothing stored is hidden: the title in the form, the address and the rest in the „Geteilt“ card, the second line names that the address is stored. (4) After „Speichern“ (`onSaved`) the page does not navigate home but shows „Abgelegt.“ with „Ansehen“ (`/planner?item=todos:<id>`, no day; 10b's `?item=` unfolds „Noch ohne Tag“), „Rückgängig“ (`saved.undo()`) and „Fertig“ (Android: back to the sharing app; PWA: opens the planner). The capture's own toast stays as built (`announceSaved`). One undo, kept in step: the page follows the saved ToDo live; when it is gone (its own „Rückgängig“ or the toast's) the page shows „Zurückgenommen.“ and no „Ansehen“. (5) The row carries the way back: the ToDos source hands the address over as `PlannableItem.url?` (package 1) only when the task's own note starts with one bare http/https address of ≤ 2 048 characters and the task has no legacy `links[]` entry and no `origin` link row (a mail-made ToDo's webmail address never becomes a chip); scheme and host are checked when it is read, when the chip is drawn and when it is opened; the host comes from `new URL().hostname`. The planner never reads a ToDo's note. `url?` is display only: the chip uses it; it is never part of the input hash, never in „Plan als Text kopieren“, the calendar chip, the widget or run titles (tests: `linksDisplayOnly`-style, a `copyInput` case). It shows as the chip „Im Browser öffnen · {host}“ – a link, or a control whose accessible name contains the host (opens only on a tap).

**Against LAUNCH-REVIEW-2026-11.** New surface: none in the manifest (same intent filter, same exported activity – NS4's merged-manifest check keeps passing). **B9 line (package 1 updates it in `docs/security/LAUNCH-REVIEW-2026-11.md`):** „the share page stores only on the capture card's own button (since U17). New: with the planner on the planner is the preselected kind, and a shared link's address is stored with the thing; both are shown on the page before the button.“ Any page can still open `/share?…`, which is why everything stored is shown and the caps matter. Q3: the URL is scheme-checked before it becomes a chip. Never fetched: no title lookup, no preview image, no favicon. The title is the built parser's (it takes an address out of the title); nothing here adds decoding or stripping. The text is rendered as text (no HTML, no Markdown, no auto-link in the card). The share page never offers `accounts`. While the app lock or the vault lock is active nothing changes (the planner is not behind it). MOD1: the target is offered only when the planner module is on; the native side still only hands text over.

**Struck part: pictures.** `image/*` would need a new exported filter, content-URI reads, a size and type gate (magic bytes, ≤ 10 MiB) and a place to keep the file – notes have no attachments, Unterlagen's titles must not show in the plan. It lowers no figure the text path does not already lower, and it is the one truly new entry surface. Not built; „Im Nachhinein klären“ in the PR.

**States.** planner off (the page as today) · nothing shared (today's sentence) · link · text with a rest · stored („Abgelegt.“) · undone („Zurückgenommen.“) · save failed (the form's own error as built).

**Target (script, D2).** Shared link ends as a planner row: handles 5 → 2 („Speichern“, „Ansehen“), module switches 2 / 3 → 1 (the planner itself), way back to the URL nein → ja. The script's reading of the way back is changed by package 1: it counts a link to the shared host or a control whose accessible name contains the host.

**Not part of it.** No way back into the source *app* (Android hands no dependable sender; a guessed package name would be a lie), no share *out* of the planner, no background receive.

## Idea 3 – unload with kind recognition

**Exists.** The quick-capture parser knows 15 kinds incl. invoice (amount, „Rechnung“, „Mahnung“), list, event, note, bookmark (`web/src/quickCapture/parser`); the planner's field ignores it and always makes a ToDo. `web/src/quickCapture/targets/lookup.ts` holds only the invoice lookup (`findOpenInvoice`); no name lookup exists yet.

**Behaviour.** (1) While he types, the field asks the same local parser. Only a **sure** reading (rules below) shows one line under the field: „Wird: Rechnung · Stadtwerke · 80,00 € · Frist Fr 4. Dez.“ and the button „Als Aufgabe eintragen“. (2) Enter stores what the line says, through the capture target of that kind, and places it, all in one undoable action – a Rechnung and the shopping list „ohne Tag“, an Aufgabe mit Schritten on the day on the sheet like any field ToDo: the planner's field calls the planner's own place function inside that action (not the bus, which swallows a failure) and takes the created thing back when placing fails. A thing whose plan row exists already is left as it is – typing „Milch“ never lifts a „Nicht planen“ on the shopping list. (3) „Als Aufgabe eintragen“ (or Alt+Enter) stores the plain ToDo; the line is gone for this entry. (4) The toast names it again and says where it lies: „Rechnung angelegt, liegt unter „Noch ohne Tag“. · Rückgängig“, „Aufgabe mit 3 Schritten angelegt, liegt auf Mo. · Rückgängig“; a plain ToDo with a lead chip: „Liegt auf Mi, vor Friseur.“ Only Notiz and Merkliste get the toast's offer „In den Plan“; a Termin gets none (it is a blocker of its day). (5) No line → exactly today's behaviour.

| Kind | Sure when | Lands | Plan |
| --- | --- | --- | --- |
| Rechnung | the word „Rechnung“ **and** an amount („Mahnung“ is not sure: it would duplicate an open invoice; the capture's amend path stays where it is) | Rechnungen (title, amount, deadline if said) | row `invoices:<id>`, „ohne Tag“, with „Vorschlag“ chip if a deadline |
| Einkauf | „kaufen“, „Einkauf:“ … **or** the whole entry is a name the shopping list or pantry already knows (the name lookup package 3 builds, below) | the shopping list (several items by comma) | the list's one row, requested |
| Termin | a clock time **and** a day | Kalender | none (it is a blocker of its day); no offer in the toast |
| Notiz | starts with „Notiz:“ / „Idee:“ | Notizen | none; toast offers „In den Plan“ |
| Link | the entry is one http/https URL | Merkliste | none; toast offers „In den Plan“ |
| Aufgabe mit Schritten | „Name: a, b, c“ with ≥ 2 parts and no other kind sure | one ToDo with checklist (5a; `CaptureFields.checklist?`, package 3) | on the day on the sheet, like any field ToDo – a plain ToDo row: „Thema …“ is offered, no B14 |

Everything else – and every kind whose module is off – is a ToDo. **Order of readings:** the planner's own readings „fest“, „Pause …“, „heute nur …“ and a pasted plan come first and are unchanged; then a sure kind that uses a date (Rechnung: word + amount; Termin: day + clock time) wins over the planner's date reading and takes the date as its deadline / day; a date word without a sure kind („Wäsche morgen“) stays the planner's, as today. Tests: „Rechnung Stadtwerke 80 € bis Fr“, „Mi 15:00 Friseur“, „Wäsche morgen“.

**The name lookup (built in package 3).** In `web/src/quickCapture/targets/lookup.ts`, beside `findOpenInvoice` and read the same way – through the generic manifest repo (core, no module import): pantry item names and shopping-list item names; exact, case-blind, local, only while those modules are on.

**Lead chips and the preview (one slot, an order).** Lead chips stand before the input: A2 from „Vorbereiten …“ (idea 9), T11 while a topic filter is on (idea 11); at most two, A2 first. The K1 preview line still shows under the field. Only a plain ToDo – also one with steps – takes the lead chips (A2 → link and day, T11 → topic). For every other kind (Rechnung, Einkaufsliste, Termin, Notiz, Merkliste) the chips are drawn struck through while K1 shows and are not applied. When a chip gives the day, K1 / the field's toast names that day.

**Never silently wrong.** The line appears before Enter and is the only thing that decides; a reading below the „sure“ rules shows nothing; the wrong kind costs one tap before (button) or one after (undo). Switch „Arten im Feld erkennen“ (on; off = today).

**Data / contract.** None new: `saveCapture(type, …)` (a core capture target – the one way the planner may create a thing in another module, only on his tap and inside its one undo entry, CONCEPT §0 sentence 2). Enter never uses `requestIntoPlan` (the bus emit, which swallows a failure): it calls the planner's own place step inside the action – for „ohne Tag“ (Rechnung, Einkaufsliste) the no-day placement `placeMany(refs, null)`; a plain ToDo / Aufgabe mit Schritten goes the field's normal way (`addFromField`). `requestIntoPlan` is used only by the toast's later offer „In den Plan“ for Notiz and Merkliste. The preview is derived, not stored.

**Risk.** A stale shopping name turning „Batterien“ into a list item when he meant a task: the line says so first. Money never appears in a toast while „Werte ausblenden“ is on (`SensitiveValue` in the line, no amount in the toast).

**Target (script).** A1: `rightKind` 4 → 12 of 12 when the pantry knows the three shopping items, as in the script's seed; rows afterwards 11 → 7; linked to the plan 4 → 10; still 12 handles, 0 per thing, 0 switches. A2 (the capture detour: 33 / 34 handles, 3 / 5 switches, 2 forms) is no longer needed. C1: the round typed as one line – create 11 / 10 → 1 handle, 8 in all, module switches 2 → 0.

**Not part of it.** No new model call and no network (the existing local stage on the desktop stays as it is and never produces a preview line), no kind picker, no second field, no recognition inside „Plan einfügen“.

## Idea 6 – errand round (shrunk to what the script rewards; places and map struck)

**What is built, inside package 5b – no package of its own.** A „Besorgungsrunde“ is a bundle whose members are the errands and the shopping list: one row („Besorgungen · 3 Dinge“), and the list member shows its open items as tick lines right in the bundle's panel, so the round is worked through without leaving the planner. „Los“ walks the members; the list is one step with its tick lines.

**Struck parts** ([ANALYSIS §4](ANALYSIS.md)): a place per stop, the `place` relation, maps as a link target, „Auf der Karte ansehen“, a map inside the planner, the word „Stopps“. None lowers a figure the bundle and the lists panel do not already lower (`mapShown` stays „nicht möglich“ in the script). The drawn version is kept in `handoff/06-errand.md` and `mockups/06-errand.html` for a later „ja“.

**Target (script).** C2: rows 2 → 1, working handles 9 / 8 → 6. Getting the round together costs 14 handles (phone 13) once, including one trip to Listen for „In den Plan“ (a shopping list is a plan row only when asked in), and per thing rises 5 → 7 – so the module switches stay 2.

## Idea 9 – before and after an appointment

**Behaviour.** (1) An appointment is a recessed blocker row on its day. Expanded (idea 4): calendar's panel shows time, place and the linked things; the foot's two quiet buttons „Vorbereiten …“ and „Danach …“ are the planner's own (they act on the planner's field), drawn for blocker rows. (2) A tap puts the cursor into the planner's field with a lead chip „vor Friseur, Mi“ before the input (✕ removes it; the order of lead chips: idea 3); what he enters becomes a ToDo on the appointment's day (before: the day itself, or the day before when he taps the chip's second choice „am Tag davor“, which is hidden when the appointment is today), linked `before` / `after` to the appointment. Only a plain ToDo – also one with steps – takes the lead chips (A2 → link and day, T11 → topic). For every other kind (Rechnung, Einkaufsliste, Termin, Notiz, Merkliste) the chips are drawn struck through while K1 shows and are not applied. When a chip gives the day, K1 / the field's toast names that day. (3) The row shows the chip „vor Friseur“ and sorts before / after the blocker inside its day part. (4) The calendar's „Vorbereitung“ block lists it (reverse links, exists). The panel's tick lines are ToDos: calendar reads them through `linkEntries` and ticks through the bus (`todo.doneRequested` inside `undoable`), never by importing ToDos.

**Contract.** Rels `before`, `after`; calendar `planPanel`. Enter with the lead chip extends the planner's own `addFromField`: day and links inside its one undoable action, with the field's toast – not the bus. No time is given to the thing: the planner stays a day planner (`decisions/plan.md`).

**Target (script, D3).** A prepared thing linked to its appointment: module switches 4 → 0, handles 14 → 4 (Wednesday's tile, expand the blocker, „Vorbereiten …“, the typed line), per thing 0. The script's `linked` is changed by package 9 to read `_links` (`before` from the ToDo to the appointment) instead of `todo.links[]`.

**Not part of it.** No automatic „Vorbereiten“ row, no travel time, no templates per kind of appointment, nothing for all-day events.

## Idea 11 – topic as a bracket

**Why a topic and not a tag.** Tags exist in four modules as loose strings; notebooks, lists and categories in others; Rechnungen, E-Mail and Kalender have none. A cross-module tag would mean a new field in every module. A topic is instead **one planner row with links**: `planner_topic` (a title) and one `topic` link per member in the store that already syncs, reads both ways and survives deletion. No module gets a field; no module needs to know topics exist. It is shown nowhere until he makes one. ToDo tags, lists and notebooks stay what they are; the planner never reads ToDo tags.

**Behaviour.** (1) Row ⋯ or the selection bar: „Thema …“ → choose one or type a new name. Offered only on rows whose module is linkable (`isLinkable`) and on appointment (blocker) rows; never on pile and bundle rows (their members take one). Once a topic was used, a row's ⋯ also offers the last used one directly as „Thema: Umzug“ (T12, above „Thema …“; the last topic is device-local memory). (2) Page ⋯: „Nur ein Thema zeigen …“ → the sheet, the band's bars and „Noch ohne Tag“ show only that topic's things; the page head says „Thema: Umzug · 7 Dinge · Alles zeigen“ in place of its figure. (3) An appointment with the topic stays visible as its blocker row while filtered; blockers without the topic are hidden. Nothing else of the topic is shown outside rows (a thing that is no row cannot be a member). (4) The filter is device state (not synced, survives a reload, ends with „Alles zeigen“). (5) Deleting a topic removes its links in the same undo; no thing is touched. (6) A topic link stores the thing itself (`entityId` where a row is an occurrence), so a subscription keeps its topic over its periods; the filter matches rows by the prefix rule of [CONCEPT §1.2](CONCEPT.md). (7) One topic per thing: „Thema …“ on a thing that has one replaces it in that same action – the only place stale topic links are ever removed. (8) While the filter is on, the field shows the lead chip „Thema: Umzug“ (T11) before the input. Only a plain ToDo – also one with steps – takes the lead chips (A2 → link and day, T11 → topic). For every other kind (Rechnung, Einkaufsliste, Termin, Notiz, Merkliste) the chips are drawn struck through while K1 shows and are not applied. When a chip gives the day, K1 / the field's toast names that day.

**States.** no topic exists (no entry in the page's ⋯ beyond „Thema …“ on rows) · filter on · filter on and empty („In diesem Thema liegt gerade nichts im Plan.“) · topic gone on another device (filter ends, toast-free).

**Target (script, D4).** Rows while working on one topic of 7 among 20 things: 20 → 7; handles to give seven things on five days the topic and switch the filter on: 27 → 22 (phone 22 → 23, a named price: Thursday's invoice waits under the phone's folded „Danach“), per thing 20 / 15 → 15; module switches 2 → 0; `planFilter` ja. Package 11 changes the script to read `rows` and `planFilter` after the filter is on.

**Not part of it.** No topic page outside the planner, no colours per topic, no topic in the capture syntax, no nesting, no topic on `accounts`.
