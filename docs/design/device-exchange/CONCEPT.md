# Device exchange – messages, links, images and files between phone and PC (concept)

Branch `design/device-exchange`, 2026-11-16. Status: **concept; the chat decided everything needed to build** (§11 „Entschieden“); three points stay open for Sven with a recommendation each (§11 „Noch offen“, same list in [CHATS](../../CHATS.md)) – none blocks package 1. Council rounds 1–3 worked in. No product code; prototype in [`proto/`](proto/). Packages and prompts: [PACKAGES.md](PACKAGES.md). Rules it builds on: root `CLAUDE.md` "LAN sync", "Remote control", "AI privacy", "Platform", "Local API"; [RULES.md](../../RULES.md); [rules/remote-control.md](../../rules/remote-control.md); [sync-lan/CONCEPT.md](../sync-lan/CONCEPT.md); [remote-control/CONCEPT.md](../remote-control/CONCEPT.md).

Sven's wish: „Eine Möglichkeit, Daten von Handy und PC hin- und herzuschicken, plus Chat: Nachrichten vom PC ans Handy, Bilder, alles. Vielleicht beim Chat mit einbauen, sonst neues Modul.“

## 0. In one paragraph

A new module **„Austausch“** (id `exchange`, EN „Device drop“, area System, desktop + Android) shows one conversation per paired device: notes, links, copied text, images and files as cards. It travels over the existing LAN hub: a **fourth handshake mode** (`MODE_EXCHANGE = 4`) on the hub's own listener, same keys, trust list, home-network rule and limits as sync and remote control, never mixed into a sync or input session. The phone always dials (it never listens), so the PC keeps an **outbox per device** and hands it over on the next session the phone opens; while the page is open the phone keeps that session open, so PC → phone feels instant. Files go in 64 KB frames with progress, cancel, resume and a SHA-256 check, are written **only to disk** (PC: `Downloads/Nemo`, phone: app storage with „Teilen“ / „Speichern unter“), **never** into IndexedDB, sync or a backup; Nemo never opens or runs anything but a short list of harmless types, and those only on a click. Messages are a device-local table (`local: true`: not synced, not backed up, not searchable, no `aiSchema`, `dataApi: false`), so nothing from it can reach the assistant. Exchange is its own per-device permission at the PC, separate from remote control, confirmed in a native dialog.

## 4. Transport

**Mode 4 on the hub's listener** – the remote-control pattern (`remote-control/CONCEPT.md` §3 option b): own handshake mode byte in the prologue, same `Noise_IK`, trust list, per-address handshake limit; no new listener, port, bind or firewall prompt. Accepted **only on a bind of the stored home network and only when the exchange side is wired** (`handle_first_on` gets `home` and checks per mode: mode 3 `home && input`, mode 4 `home && exchange`; otherwise the authenticated `unknown-device`). **Losing the home network closes exchange sessions** like input sessions (`set_binds` closes every home-only mode; rule test). A sync session refuses exchange tags, an exchange session refuses sync and input tags (both close); the exchange handler never touches the store, its mutex or the input gate. Rule test `exchange_sync_input_stay_apart`.

**Who dials.** Android never listens (rule). So: phone → PC is a push on a session the phone opens; PC → phone waits in the PC's **outbox** and goes out on the next exchange session that phone opens. The phone opens one when no exchange session is open and: the app starts or comes to the foreground; the Wi-Fi changes while the app lives (`lanWatch`, as sync); every 60 s while the app is in the foreground (one handshake ≈ 3–5 ms, prototype). It **keeps one open while the Austausch page is visible** (duplex client like `input_client.rs`, `ping` every 60 s against the 120 s idle close). The hub's idle timer counts only frames **from** the phone, so the phone also sends `ping` every ≤ 60 s **while any transfer or outbox handover runs on the session**, whether the page is visible or not (test: a PC → phone transfer longer than the idle timeout completes). A new exchange session of the same device replaces the old one at the hub (as input does), so the 4-per-IP cap holds. With the app closed nothing arrives until it opens – said in the first-run step and the user docs; a background fetch is §11.

**Wire** (tags `0x30–0x3f`, a test asserts no collision with sync `0x10/0x11` and input `0x20–0x2b`; binary records with explicit lengths, no JSON, every string UTF-8-checked and capped):

| Tag                                                                    | Direction         | Content                                                                                                                                                                                 |
| ---------------------------------------------------------------------- | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0x30 open`                                                            | phone → PC        | `[version, features]` after `hello`                                                                                                                                                     |
| `0x31 opened` / `0x32 refused {code}`                                  | PC → phone        | `opened {features}`; codes `exchange-off` (module off at the PC), `not-granted`, `paused`, `full`                                                                                       |
| `0x33 item`                                                            | both              | `id (16 B) · kind (text, link, clip) · body ≤ 16 KiB`                                                                                                                                   |
| `0x34 ack`                                                             | both              | `id · state (stored, refused)` – sent only after the receiver's **Rust inbox** holds the item; an item counts as sent only then                                                         |
| `0x35 offer`                                                           | both              | `id · size u64 · sha256 (32 B) · name ≤ 255 B · mime ≤ 64 B`                                                                                                                            |
| `0x36 accept {id, from}` / `0x37 wait {id}` / `0x38 refuse {id, code}` | receiver          | `from > 0` resumes; `wait {id, reason}` = needs _Annehmen_ (reason: over 100 MB, or over 1 GB from this device today); codes `too-large`, `full`, `declined`, `not-granted`, `rejected` |
| `0x39 chunk`                                                           | sender            | `id · offset u64 · bytes` (≤ 65 494 B: 65 535 minus tag, header and the 16-byte AEAD tag)                                                                                               |
| `0x3a end {id}` / `0x3b result {id, code}`                             | sender / receiver | code `ok` (0) only when length and SHA-256 match; else `mismatch`, `full`, `failed`                                                                                                     |
| `0x3c cancel {id}`                                                     | both              | either side, any time                                                                                                                                                                   |
| `0x3d ping`                                                            | phone → PC        | every ≤ 60 s while the page is open or a transfer/handover runs (the hub's idle timer counts inbound frames only)                                                                       |

Frame cap of an exchange session: 256 B until the first authenticated frame (as every session today), then 65 535. One file transfer at a time per session (the next waits; a text item may go between two chunks), at most 3 queued offers per direction in flight.

**Delivery state is Rust's.** Each side keeps a Rust **inbox** (received items and finished file cards, app data `exchange/inbox.json`) and **outbox** (`exchange/outbox.json`, items and file references per device); `ack` is sent only after the inbox write. The web view drains the inbox into Dexie `exchange_items` on start and on each event and confirms by id, then Rust drops the entry; outgoing card states in Dexie mirror Rust events and are re-read from `exchange_status` on start. Dexie is the history the user sees, Rust owns „was it delivered“. Nothing is lost when the web view is not loaded, reloads or crashes.

**Integrity and resume.** The receiver writes `.nemo-incoming/<peer>-<hex(id)>.part` (peer = the authenticated device id, id = the validated 16 bytes; never sender text) in the target folder, hashes while writing (re-hashes the existing part on resume), compares length and SHA-256 at `end`, then moves it to the cleaned name **without ever replacing a file** (create-new, „ (2)“ on collision); a mismatch deletes the part and says so. A part is kept 24 h for a resume by the same device (same `id`, `accept.from` = its length), then deleted. Offsets must be contiguous (an out-of-order chunk closes the session). PC → phone files are referenced, not copied: the offer carries the SHA-256 taken when queued, the sender re-hashes while streaming and cancels on a mismatch; **the receiver's check against the offer's hash is the authoritative guard**, also after a resume.

**Limits.** Per file 4 GB (v1). Sender queue on the phone ≤ 2 GB of pending files. Receiver: refuses with `full` when free space would drop below 1 GB (PC) or 500 MB (phone); the phone's inbox in app storage is capped at 2 GB (oldest received files are offered for cleanup, never deleted silently). Without asking up to **100 MB per file and 1 GB per device per day** (fixed in v1; a setting only if hand tests show a need; the daily count lives in Rust per device in the shell's `exchange/` app data and resets at local midnight, never on a restart or reconnect; it counts bytes written to `.part` files as they arrive – cancelled, failed and unfinished transfers included, resumed bytes once – and open parts count toward the `full` check); above either, every offer gets the receiver's _Annehmen_ card – so a granted or compromised phone cannot quietly fill the PC down to the 1 GB floor. Rate: at most 300 items per hour per device (a flood closes the session with `limit`, the cards stay).

**Bandwidth.** Measured (prototype, §10): the exchange layer itself (64 KB frames, ChaCha20-Poly1305, SHA-256) moves ≈ 300 MB/s on one host, so phone → PC is set by the Wi-Fi: unsicher, expected 5–40 MB/s (802.11ac/ax at home) – a 100 MB video in ≈ 3–20 s. **PC → phone is capped today** by the hub's transport loop (one unasked frame per 200 ms pass, `transport/mod.rs:508`): ≈ 0.3 MB/s, 1 GB ≈ 55 min. Package 2 therefore changes that shared loop (keep writing unasked frames while the connection has them and the socket takes them, wait for writability instead of the tick) with a regression test that the input session's latency is unchanged; `transport/mod.rs` is a hotspot of that package. Sync and remote control keep their own connections; on a slow Wi-Fi a running transfer may add latency to the touchpad (TCP shares the air) – package 2 measures it.

**Home network only.** Same rule as LAN sync; what it means for phone → PC: nothing goes while the phone is away, the item waits (§2). No relay through the own sync server in v1 (§11).

## 6. Security

**Permission.** Pairing is not permission. At the PC, per paired device: _Austausch erlauben_. Stored in the hub's device-local `trust.json` (`exchange: { on, paused }`), never synced, never changeable by a network message (rule test as `no_frame_from_the_network_reaches_a_setter`). **Default: off.** Every widening – a device on, un-pausing, the module switched on at the PC while a grant is stored – is confirmed in the **native Rust dialog** of remote control („Svens Handy darf dir Nachrichten und Dateien schicken.“ – _Erlauben_ / _Abbrechen_) and refused while a mouse/keyboard remote session is open (checked again when the dialog returns). Why: the web view renders text, links and names a peer sent, so it must not be able to widen the grant alone; the dialog costs no extra click (it _is_ the confirmation). First run on the PC (module on, at least one paired device): with **exactly one** paired device that switch is preselected; with several, none is, and each row shows the name and „zuletzt gesehen“, because the trust list cannot tell the user's own phone from a family phone paired only for sync. Narrowing (off, pause, module off) needs no dialog.

**Writers on the PC, complete list** (desktop-only Tauri commands): `exchange_set_device` (on/pause, widening via the dialog), `exchange_set_enabled` (Rust mirror of „module on at this PC“, called by the module's enable/disable hooks; on = widening when a grant is stored – so module state arriving by sync never activates a grant without the dialog), `exchange_set_folder` (opens the Rust folder dialog; folder stored in the shell's app data `exchange/settings.json`, not in `trust.json`). The 100 MB limit is a constant on both sides. The phone needs no grant: it receives only on sessions it opens itself, with its module on.

**Never open or run.** Nemo never opens a received file by itself. _Öffnen_ (the OS default app, checked in Rust) appears only for an **allow-list** of types (`jpg jpeg png gif webp heic heif avif bmp mp3 m4a aac ogg opus flac wav mp4 m4v mov mkv webm pdf txt md csv docx xlsx pptx odt ods odp`, prototype `risk`; not `zip`/`7z`: browsing or extracting an archive exposes entries (`.url`, `.lnk` …) that were never cleaned or defused, and 7-Zip drops the origin mark – archives get _Im Ordner zeigen_ only); **every other type** – programs, scripts, shortcuts, installers, disk images, `msc`, `chm`, `appref-ms`, HTML/SVG (local script), unknown endings – is „andere“: only _Im Ordner zeigen_ plus the line „Diese Datei öffnet Nemo nicht. Öffne sie nur, wenn du sie selbst geschickt hast.“ An allow-list on purpose: a deny-list always misses a handler. **Shortcut-like types** (`url lnk scf library-ms searchconnector-ms search-ms desktop website appref-ms theme themepack deskthemepack`) make Explorer resolve an icon or target just by showing the folder – an SMB path there leaks the user's NTLM hash to the LAN – so Rust appends `_` to their extension before the final move (`Ordner.url` → `Ordner.url_`; prototype `fileNames`); the card says `„Verknüpfung – als ‚{name}‘ gespeichert, damit Windows sie nicht von selbst öffnet.“` and offers _Im Ordner zeigen_. The check runs on the **final** name, after every cut, so shortening a long name can never uncover such an extension. The card always shows the extension (`Rechnung.pdf.exe`). On Android Nemo never asks for `REQUEST_INSTALL_PACKAGES`.

**Proposed hard-rule line** (root `CLAUDE.md`; full text in a new `docs/rules/device-exchange.md`; own PR, Sven merges – package R, §11):

> - **Device exchange (phone ↔ PC):** only in the LAN hub's exchange session (mode 4: same listener, keys, trust list and home-network rule; never the sync or input session, a new listener or the Local API); only for a device granted at the PC (off by default, device-local, widened only in a native dialog, never set over the network); files and thumbnails only on disk, never in IndexedDB, sync or backup, paths only in Rust; names cleaned, Nemo opens only allow-listed types on a click and runs nothing; clipboard read only on a tap, never written by itself; never from `accounts`; no `aiSchema`, search or data API; never log contents or names. Full text: `docs/rules/device-exchange.md`.

- **Notification:** PC only. ## 10. Prototype

[`proto/`](proto/), run `node docs/design/device-exchange/proto/run.mjs` (Node ≥ 20, no install). `pc.mjs` (own process, listener) receives into a temp folder; `run.mjs` plays the phone. Channel: X25519 + HKDF + ChaCha20-Poly1305 per frame with a u16 length prefix and the 65 535-byte Noise frame limit, plus an 8-byte stand-in for the authenticated device id – a stand-in for the hub's `snow` session, whose handshake and trust checks [sync-lan/proto](../sync-lan/proto/) already exercises. The prototype's PC answers on the same socket without the hub's tick, so it does **not** show the outbound cap of §4. Measured 2026-11-16, container, both processes on one host over the interface address (not real Wi-Fi), 5 rounds, Node v22.23.4, Xeon 2.1 GHz:

## 11. Für Sven entschieden / Noch offen / Im Nachhinein klären

**Entschieden (vom Chat, mit Grund):**

1. Eigenes Modul „Austausch“ (EN „Device drop“) im Bereich System, nicht im KI-Chat, nicht in der Fernsteuerung (§3).
2. Modus 4 auf dem Listener des Hubs, eigene Tags, nur Heimnetz, schließt bei Heimnetz-Verlust; PC wählt nie, Ausgang je Gerät am PC; Zustellung gehört Rust (Ein-/Ausgang als Datei) (§4).
3. Nachrichten gerätelokal (`local: true`), nicht synchronisiert, nicht im Backup, 30 Tage fest (§5).
4. Dateien und Vorschaubilder nur auf der Platte (`Downloads/Nemo`, Handy App-Speicher), Pfade nur in Rust, PC → Handy per Referenz mit Prüfsumme (§4, §5).
5. Freigabe je Gerät am PC, Standard aus, jede Erweiterung im nativen Dialog; beim ersten Einschalten nur dann vorausgewählt, wenn genau ein Gerät gekoppelt ist (§6).
6. Ohne Rückfrage bis 100 MB je Datei und 1 GB je Gerät und Tag (fest), darüber _Annehmen_; Verknüpfungs- und Theme-Typen entschärft (geprüft am fertigen Namen); Öffnen nur für eine Erlaubnis-Liste, sonst nie; Herkunftsmarke unter Windows (§6).
7. Zwischenablage nur auf Tipp senden, am PC nie automatisch übernehmen (§6, §9).
8. Benachrichtigung bei Eingang: nur PC, Standard aus (Fokus-Regel); Widget und Tray-Zeile tragen die Nachricht (§7).

**Noch offen (Empfehlung zuerst; blockiert kein Paket):**

1. **Handy bei geschlossener App:** nichts, beim Öffnen holen (empfohlen für v1) · Hintergrund-Abruf über WorkManager wie LAN-Sync-Paket 5 (Akku, eigener Paket-Aufwand).
2. **Unterwegs:** nur Heimnetz (empfohlen, wie LAN-Sync) · über den eigenen Sync-Server weiterleiten (Ende-zu-Ende, aber Dateien auf dem Server – eigene Regel nötig).
3. **Name:** „Austausch“ (empfohlen) · „An mich“ · „Hin & her“.
