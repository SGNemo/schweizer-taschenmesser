## 0. In one paragraph

A new module **`planner`** („Planer“, area Planen) distributes everything that has to get done over the coming days: the open ToDos (the backlog stays in ToDos, nothing is duplicated), later invoices, cancellation deadlines and notes marked „In den Plan“. Per day the user states **available time** and **blockers** (appointments come from the calendar by themselves). A pure, deterministic engine in `core/plan/` turns items + days into **assignments** (item → day, session minutes, reason), a short list „waits for a free day“ and a diff to the previous plan. Hard deadlines beat priority, priority beats age, a buffer is never planned, large items become sessions, existing assignments move only when they must, nothing is pulled forward except by a deadline, and every move names its cause. The planner writes `plannedFor` and a plan order back to the ToDo, so the existing „Heute“ card, the morning digest, the focus round and „Später“ keep working unchanged. AI enters in two stages: rules (free, offline, also with „KI aus“) and the local model (desktop with a downloaded model; sees titles, nothing leaves the device). The planner's tables, schema and actions never reach the cloud – a cloud-only filter on every cloud path, and the planner is never offered as chat context (a ToDo attached as chat context carries its `plannedFor` as it always did); pinned by tests. Everything goes through a preview with a diff and an undo toast.

## 2. Data model

Three synced collections (`planner_day`, `planner_item`, `planner_assignment`; envelope + `createRepo`, dates `YYYY-MM-DD`, times `HH:mm`, minutes as integers). The manifest sets `dataApi: false` for the whole module – the plan, blocker labels and day notes describe the user's days and are never offered to the import API or MCP. **Deterministic ids through `repo.upsert`**, plain indexes, no unique indexes (two devices that touch the same day offline must merge, not collide):

| Collection   | Id                        | Index             | Fields                                                                                                                                                                                                                                                 | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------ | ------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `day`        | `date`                    | `date`            | `availableMin?` 0–1440 · `blockers: [{ id, label, min, from?, to? }]` · `note?`                                                                                                                                                                        | Only days the user touched are stored; a missing day = the weekday default. **Calendar appointments are not stored** – they are read live from `calendarItems`. `from`/`to` are optional windows (package 5).                                                                                                                                                                                                                                                                                                                         |
| `item`       | `sourceKey` (`module:id`) | –                 | `source: { module, id }` · `title?` (own entries; **empty in v1** – the field, `plan.requested` and the prefix create ToDos) · `durationMin?` · `priority?` · `due?: { date, hard }` · `earliest?` · `pinned?` · `splittable?` · `excluded?` · `order` | One row per planned thing. For a sourced item the planner stores **only what the source does not have** (see ownership), plus the hard due when the user marks „Frist“ or writes „bis <Tag>“ in the planner's field (a copy; if the source date drifts the row shows „ToDo-Datum jetzt Fr“), and the user's own `earliest` (see write-back).                                                                                                                                                                                          |
| `assignment` | `<itemKey>#<k>`           | `date`, `itemKey` | `k`, `of` · `minutes` · `order` · `reason` · `bumpedBy?: string[]` · `late?`                                                                                                                                                                           | Session `k` of `of`. Deterministic ids, so two devices that run before they sync write the **same rows** (field LWW merges them) and a run updates rows in place; when `of` changes, sessions inherit the previous days by index. A unit that stops being placed (waits, excluded, done, surplus session) gets `remove(id)` (tombstone); a unit that is placed again gets `restore(id)` + `upsert` – `upsert` alone would keep the tombstone (`repo.ts` keeps `deletedAt`). Test: done → undone on the ToDo page → row visible again. |

**Planner-own or user-set?** `planOrder` is written **only** by the planner, so a `plannedFor` on a ToDo with `planOrder` set is the planner's, one without is the user's. Every writer of `plannedFor` on the ToDo side (editor, „Später“, „Auf morgen schieben“, inbox sorter, board column move) clears `planOrder` in the same patch (one helper in `modules/todos`). No stamp is needed and no ordering of synced rows matters: both fields sit on the same record.

Runs and write-back (one rule set, package 1 pins it with tests):

- **Every run writes back idempotently:** only planner-own values (`plannedFor` + `planOrder`), only when different. A user `plannedFor` (no `planOrder`) is copied to the planner-owned `item.earliest` before the first overwrite; **any** later user change replaces it, a cleared date removes it. On the ToDo page a planner-written date behaves like a user date (Heute/Bald views) with a quiet „im Plan“ label; such moves happen without a toast, the board explains them.
- **User action vs background:** a run started from the planner UI (add, done, Später, pin, instruction, „Neu verteilen“) runs **inside the user's `undoable`**, write-backs included, so the toast's „Rückgängig“ restores everything. Every other run (ToDo-page edit, calendar change, sync-applied change, day change, app start, undo) is background: serialised after any open user action, not undoable, same idempotent write-back. Why not "background never writes back": the „Heute“ card shows `plannedFor ≤ today`, so a morning without a planner action must still move yesterday's leftovers.
- **Sync:** runs triggered by sync-applied writes wait until the pull has finished (sync status idle), so a paged pull cannot present a planner value as user-set half-way (test: „ToDo row arrives before the planner rows → no `earliest` copied“). A later-stamped background write-back can still beat a concurrent offline „Später“ from another device under field LWW – accepted and stated, as for every synced field.
- **Convergence:** input hash in `_meta` = `today` + settings + items + days + stored blockers + timed calendar items (`event`/`external`) – not `prev`, not the planner's own rows, not planner-own `plannedFor` values; identical hash → no run; a run whose output equals the stored rows writes nothing (test „one run → zero follow-up writes“); fixpoint `plan(x, prev = plan(x)) == plan(x)` (test). After a sync-applied assignment change one background recompute writes only rows whose fields differ (test „two devices converge“). An undo restores the inputs too, so the following background run writes nothing (test „undo stays undone“). The live query that drives runs covers `collectPlannable`, the planner's own tables **and** the timed calendar items, so a new appointment replans at once.
- **Automation:** patches that touch only `plannedFor`/`planOrder` emit no `todos.task.updated`: a new `ignoreFields` on `AutomationEventDef` (`core/automation/module.ts`), honoured in `core/automation/ingest.ts` `eventsOf` against `before`/`data`, set by the ToDo `watch` for `task`. This also silences a user's „Später“ tap (a date-only change) – accepted; `todos.task.completed` is unaffected (test „one run → zero automation events“).

Settings (synced scope `planner`, registry section of the module, folded „Weitere Einstellungen“): `defaultAvailable` per weekday (Mo–Fr 240, Sa 120, So 0) · `bufferShare` 0 / 10 / **20** / 30 % · `horizonDays` 7 / **14** / 28 · `maxSessionMin` 45 / 60 / **90** / 120 · `minSessionMin` 25 · `autoReplan` on · `calendarBlocks` on · `allDayBlocks` off · `calendarChips` on (package 2) · `overloadToast` on (package 3). The Monday line „Woche prüfen“ is an attention aid: switch `focus.weekCheck` in „Fokus & Aufmerksamkeit“ (package 2), dismissal device-local per ISO week in `_meta`. The number of main items per day **reuses** `focus.planLimit` (no second setting). Device-local (`_meta`): the last run's input hash, the week-check dismissal, the week of the last overload toast.

Module dependency and switching off: `requires: ['todos']` (the field and `plan.requested` create ToDos through the capture target). On `module.disabled` for `planner` the service **first stops its run subscription**, then: with the keep policy it restores every planner-own `plannedFor` (ToDo with `planOrder`) to the user's `item.earliest` or clears it and clears `planOrder`; with the delete policy the planner rows are already gone when the event fires (`disableModule` wipes first), so it clears every `plannedFor`/`planOrder` on ToDos that carry a `planOrder` – no restore (tests for both policies: „Später Do → assigned Sa → disable → plannedFor = Do“ and „… → user clears date → disable → plannedFor empty“).

Schema impact outside the planner: one optional ToDo field `planOrder` and the `ignoreFields` entry in core automation (package 1); package 5 adds optional day windows inside the planner only.

## 3. Engine – `core/plan/` (pure, deterministic, tested)

Files: `types.ts` (contract, `DEFAULT_MIN = 30`), `capacity.ts`, `units.ts` (splitting), `engine.ts` (`plan()`), `diff.ts`, `explain.ts` (reason → German sentence via `t.planner.reasons`), `instructions.ts` (stage-0 parser, §6c). No clock inside; `today` is an input. Figures use one `formatMinutes(min, { compact? })` in `core/i18n/format`: the timetrack helper `duration(minutes)` (`modules/timetrack/components/format.ts`, „3 Std 5 Min“, five languages) moves there and gains a compact form for boards and bars („1 h 30“, „45 Min“); timetrack keeps calling the full form. (Distinct from the disk module's `formatDuration(ms)`.)

```ts
plan({ today, days: PlanDay[], items: PlanItem[], prev: Assignment[], settings }) → {
  assignments: Assignment[],                      // unit → day, minutes, order, reason, bumpedBy?, late?
  unplaced: { unit, reason: 'horizon' | 'too-long' | 'after-hard-due', bumpedBy? }[],
  diff: { added, moved: { unit, from, to, reason, by? }[], removed: { unit, from, reason, by? }[], unchanged },
  load: Record<date, { raw, usable, planned, free, over, mains }>, overflowMin }
```

Definitions: `raw = available − Σ blockers` · `usable = raw × (1 − buffer)` · **`free = usable − planned`** (this is the figure every surface calls „frei“) · `overflowMin = demand − Σ usable` of the horizon („mehr zu tun, als Zeit frei ist“). `plan()` slices `days` to `today … today + horizonDays − 1`; the scenarios pass `horizonDays: 7`.

Rules, in the order they are applied per day:

| #   | Rule                         | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Capacity**                 | Blockers = stored blockers + calendar items of kind `event`/`external` with a time (minutes = end − start, else 60 as in the calendar's `DEFAULT_BLOCK_MINUTES`); reminders (`kind: 'reminder'`) and plan chips never block; all-day items 0 unless `allDayBlocks`.                                                                                                                                                                                                                                                                                                                               |
| 2   | **Units**                    | An item longer than `maxSessionMin` and `splittable` becomes `ceil(min / max)` sessions of equal length (≥ `minSessionMin`); an item without an estimate counts `DEFAULT_MIN`; sessions of one item go on different days, except under deadline pressure.                                                                                                                                                                                                                                                                                                                                         |
| 3   | **Pinned first**             | A pinned item (planner action „Festnageln“ only) is placed on its day whatever the capacity (overload is counted, not refused).                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 4   | **Hard due before priority** | Only a hard due **inside the horizon** is pressure. `latestStart(unit)` walks back from the due date over days that actually have room (a free Thursday does not count). A unit whose latest start is today is placed now – it may use the buffer, a second session of the same item may land on the same day, and this is the **only** rule that pulls a unit forward from a later planned day. Order inside: latest start, due date, priority.                                                                                                                                                  |
| 5   | **Priority before age**      | The rest, never a unit planned for a later day: priority ↓, then **kept** (planned for this day before) ↑ **carried** (planned for an earlier day) ↑ new, then soft due ↑, then `createdAt` ↑, then id. A unit is placed when it fits the remaining usable minutes and the day has fewer than `planLimit` main items (≥ 30 min); small things fill the rest.                                                                                                                                                                                                                                      |
| 6   | **Stability**                | An item keeps its day whenever it still fits; a new item with the same priority never displaces it. A higher priority or a deadline may: the diff lists the units that **outrank** the moved one and took room on that day (`bumpedBy`, largest first, never a session of the same item) – also for a unit that drops out of the horizon. A later session that cannot follow its earlier part names the part (`after-part`). Nothing is pulled forward on its own: a done item frees room and the rest stays where it was (S5); the explicit reshuffle is „alles neu mischen“ (`prev = []`, §6c). |
| 7   | **Honest output**            | Items without room in the horizon → `unplaced: horizon`; longer than any day → `too-long`; placed after a hard due → `late` + `after-hard-due`. Numbers, never alarms.                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 8   | **Reasons**                  | `pinned` · `deadline` · `deadline-buffer` · `new` · `kept` · `carried` (not done earlier) · `pulled` (a deadline pulled it forward); moves and drop-outs: `bumped` (by whom, list) · `after-part` („folgt auf Teil 1“) · `capacity` (the day shrank) · `done` (removed because finished). Every reason has one calm sentence with day names („muss bis Do fertig sein“, „weiter von Di“, „Platz nahmen Steuerbescheid, Steuer Teil 2“).                                                                                                                                                           |

Tests (package 1, Vitest, fixtures `core/plan/__fixtures__/*.json` = the five scenarios with `horizonDays: 7`): determinism (same input → same output, twice), fixpoint (`plan(x, prev = plan(x))` equals `plan(x)`), stability (unchanged input → zero moves; a kept item never loses to a carried one of the same priority; a done item never pulls anything forward), deadline (every hard due inside the horizon is met whenever the capacity allows, otherwise flagged; a due beyond the horizon is ignored), buffer (usable never exceeded except `deadline-buffer`/`pinned`), split (sessions ≤ max, distinct days unless deadline), limit (≤ `planLimit` main items per day), diff (every move and drop-out names its cause; never a session of the same item), blockers (reminders never block), explain (every reason has a sentence in all five languages → `check:i18n`).

## 4. Source contract – `contributions.plannable`

```ts
export interface PlannableItem {
  id: string; kind: string; title: string; to: string;         // route with ?open=<id>
  durationMin?: number; priority?: 0 | 1 | 2 | 3;
  due?: { date: string; hard: boolean }; earliest?: string; plannedFor?: string; planOrder?: number;
  done?: boolean; personId?: string;
  link?: { kind: 'note' | 'mail' | 'invoice' | 'event'; id: string; label: string };
}
export interface PlannableSource {
  list(ctx: { today: string; until: string }): Promise<PlannableItem[]>;      // open, plannable things only
  onAssign?(id: string, date: string | undefined, order?: number): Promise<void>; // ToDo: plannedFor + planOrder
  onDone?(id: string): Promise<void>;                                        // ToDo: done; invoice: never (paid stays in the module)
  onEstimate?(id: string, minutes: number): Promise<void>;                   // ToDo: estimateMin
}
contributions.plannable?: () => Promise<{ default: PlannableSource }>;
```

- Lazy like `calendarItems`; collector `collectPlannable(manifests)` in `core/modules/contributions.ts` (a failing source never breaks the others, modules read only their own data). Write-back is the **callback surface of the same contract** (typed, testable, no module import). Requests _into_ the plan from other modules use the bus, mirroring `todo.requested`: `'plan.requested': { title; durationMin?; priority?; due?; link? }` – the planner service turns it into a ToDo (quick-capture target) plus a planner item.
- The run is driven by live queries over `collectPlannable`, the timed calendar items and the planner's own tables (not by `core/db/writeHook`, which has one listener that belongs to the automation engine and never sees sync-applied writes).
- Blockers need no new contract: timed `calendarItems` of kind `event`/`external` (not `reminder`, not `plan`, not done) are blockers.
- `accounts` never gets `plannable`: already pinned by `exclusion.test.ts`, which fixes the vault's contribution keys to `onboarding` and `services` – no new test needed. The automation engine already excludes the vault. Retired modules: no contribution (registry rule).
