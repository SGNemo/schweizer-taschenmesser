## 0. In one paragraph

A new module **`planner`** („Planer“, area Planen) distributes everything that has to get done over the coming days: the open ToDos (the backlog stays in ToDos, nothing is duplicated), later invoices, cancellation deadlines and notes marked „In den Plan“. Per day the user states **available time** and **blockers** (appointments come from the calendar by themselves). A pure, deterministic engine in `core/plan/` turns items + days into **assignments** (item → day, session minutes, reason), a short list „waits for a free day“ and a diff to the previous plan. Hard deadlines beat priority, priority beats age, a buffer is never planned, large items become sessions, existing assignments move only when they must, nothing is pulled forward except by a deadline, and every move names its cause. The planner writes `plannedFor` and a dated plan mark back to the ToDo, so the existing „Heute“ card, the morning digest, the focus round and „Später“ keep working unchanged. AI enters in two stages: rules (free, offline, also with „KI aus“) and the local model (desktop with a downloaded model; sees titles, nothing leaves the device). The planner has **no `aiSchema`**, so it does not exist for the assistant, the cloud, the full-text search or chat context – like mail or music today; the local stage uses its own prompt and grammar; pinned by tests (a ToDo attached as chat context carries its `plannedFor` as it always did). Everything goes through a preview with a diff and an undo toast.

## 2. Data model

Three synced collections (`planner_day`, `planner_item`, `planner_assignment`; envelope + `createRepo`, dates `YYYY-MM-DD`, times `HH:mm`, minutes as integers). The manifest sets `dataApi: false` for the whole module – the plan, blocker labels and day notes describe the user's days and are never offered to the import API or MCP. **Deterministic ids through `repo.upsert`**, plain indexes, no unique indexes (two devices that touch the same day offline must merge, not collide):

| Collection   | Id                        | Index             | Fields                                                                                                                                                                                                                                                 | Notes                                                                                                                                                                                                                                                                                                                                        |
| ------------ | ------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `day`        | `date`                    | `date`            | `availableMin?` 0–1440 · `blockers: [{ id, label, min, from?, to? }]` · `note?`                                                                                                                                                                        | Only days the user touched are stored; a missing day = the weekday default. **Calendar appointments are not stored** – they are read live from `calendarItems`. `from`/`to` are optional windows (package 5).                                                                                                                                |
| `item`       | `sourceKey` (`module:id`) | –                 | `source: { module, id }` · `title?` (own entries; **empty in v1** – the field, `plan.requested` and the prefix create ToDos) · `durationMin?` · `priority?` · `due?: { date, hard }` · `earliest?` · `pinned?` · `splittable?` · `excluded?` · `order` | One row per planned thing. For a sourced item the planner stores **only what the source does not have** (see ownership), plus the hard due when the user marks „Frist“ or writes „bis <Tag>“ in the planner's field (a copy; if the source date drifts the row shows „ToDo-Datum jetzt Fr“), and the user's own `earliest` (see write-back). |
| `assignment` | `<itemKey>#<k>`           | `date`, `itemKey` | `k`, `of` · `minutes` · `order` · `reason` · `bumpedBy?: string[]` · `late?`                                                                                                                                                                           | Session `k` of `of`. Deterministic ids, so two devices that run before they sync write the **same rows** (field LWW merges them) and a run updates rows in place; when `of` changes, sessions inherit the previous days by index. A unit that stops being placed (waits, excluded, done, surplus session) gets `remove(id)` (tombstone).     |

All three collections are written through **one helper** `putRow(repo, id, data)` = restore if tombstoned, then `upsert` – `upsert` alone keeps `deletedAt` (`repo.ts`), which would hide a unit that returns, a day touched again after a delete-policy disable, or a blocker set by package 4. Tests: „done → undone on the ToDo page → row visible again“, „disable (delete) → enable → Tag frei on that date is visible“.

What syncs and backs up: the three collections (free text only in `day.note` and `blockers[].label`; `item.title` stays empty in v1); never appointments, never titles of sourced items (they live at the source).

**Planner-own or user-set?** The mark carries its date: a `plannedFor` is planner-own **only if `planMark.date === plannedFor`**; every other combination (no mark, a mark for another day, a mixed LWW merge of the two fields) reads as user-set – the safe direction, because sync merges each field on its own (`buildUpdated` stamps only changed keys), so a bare marker could win a merge next to a user's date. Every writer of `plannedFor` on the ToDo side (`TaskEditor`, `InboxSorter`, `NextWidget` wrap-up and „Für heute“, `TodosPage` create-on-Heute, `postpone.ts`, `views.ts movePatch`) goes through one helper that clears the mark **only when `plannedFor` actually changes** (a title-only save keeps it); the ToDo import and data-API write path strips `planMark` (`internal` only hides a field from the format, it does not drop it from a write). While the planner is inactive the ToDo side ignores `planMark` entirely. Tests: both LWW interleavings, one unlisted writer, an import carrying a mark.

Runs and write-back (one rule set, package 1 pins it with tests):

- **Every run writes back idempotently:** only planner-own values (`plannedFor` + `planMark`), only when different. A user `plannedFor` (mark missing or for another day) is copied to the planner-owned `item.earliest` **and into `planMark.prior`** before the first overwrite; **any** later user change replaces it, a cleared date removes it. On the ToDo page a planner-written date behaves like a user date (Heute/Bald views) with a quiet „im Plan: Mi“ label in Bald only (never repeated in Heute); such moves happen without a toast, the board explains them.
- **User action vs background:** a run started from the planner UI (add, done, Später, pin, instruction, „Neu verteilen“) runs **inside the user's `undoable`**, write-backs included, so the toast's „Rückgängig“ restores everything. Every other run (ToDo-page edit, calendar change, sync-applied change, day change, app start, undo) is background: serialised after any open user action, not undoable, same idempotent write-back. Why not "background never writes back": the „Heute“ card shows `plannedFor ≤ today`, so a morning without a planner action must still move yesterday's leftovers.
- **Sync gate:** live queries carry no origin, so a run copies to or clears `item.earliest` and overwrites a user-set date **only while `syncSettled()` is true** – a new core helper in `core/sync/service.ts`: true when sync is not configured; otherwise it requires the service's own lock/chain to be free and the last pull to have ended complete (`more: false`, a flag `core/sync/engine.ts pullAll` records device-locally in `_meta`). While the gate is closed the run uses the user's date as `earliest` in memory only and neither copies nor overwrites it; a paged or failed pull can split the field ops of one record across pages (tests: „no sync configured → `earliest` copied“, „gate closed → user date not overwritten“, „ops of `plannedFor`/`planMark` split across two pages → no `earliest` copied“). The planner never touches `navigator.locks` itself. A later-stamped background write-back can still beat a concurrent offline „Später“ from another device under field LWW – accepted and stated, as for every synced field.
- **Convergence:** input hash in `_meta` = `today` + settings + items + days + stored blockers + timed calendar items (`event`/`external`) – not `prev`, not the `planner_assignment` rows, not planner-own `plannedFor` values, not `planMark`; identical hash → no run; a run whose output equals the stored rows writes nothing (test „one run → zero follow-up writes“); fixpoint `plan(x, prev = plan(x)) == plan(x)` (test). After a sync-applied assignment change one background recompute writes only rows whose fields differ (test „two devices converge“). An undo restores the inputs too, so the following background run writes nothing (test „undo stays undone“). The live query that drives runs covers `collectPlannable`, the planner's own tables **and** the timed calendar items, so a new appointment replans at once.
- **Automation:** patches that touch only `plannedFor`/`planMark` emit no `todos.task.updated`: a new `ignoreFields` on `AutomationEventDef` (`core/automation/module.ts`), carried through `registry.ts` (`watched` is a boolean callback today) and `start.ts` into `ingest.ts` `eventsOf`, checked as `Object.keys(signal.before) ⊆ ignoreFields` for `kind: 'updated'` only, set by the ToDo `watch` for `task`. This also silences a user's „Später“ tap (a date-only change) – accepted; `todos.task.completed` is unaffected (test „one run → zero automation events“).

Settings (synced scope `planner`, registry section of the module, folded „Weitere Einstellungen“): `defaultAvailable` per weekday (Mo–Fr 240, Sa 120, So 0) · `bufferShare` 0 / 10 / **20** / 30 % · `horizonDays` 7 / **14** / 28 · `maxSessionMin` 45 / 60 / **90** / 120 · `minSessionMin` 25 · `autoReplan` on · `calendarBlocks` on · `allDayBlocks` off · `calendarChips` on (package 2) · `overloadToast` on (package 3). The Monday line „Woche prüfen“ is an attention aid: switch `focus.weekCheck` in „Fokus & Aufmerksamkeit“ (package 2; **off by default** like its siblings `weekReview`/`streaks`, hidden while the planner is disabled), dismissal device-local per ISO week in `_meta`. The number of main items per day **reuses** `focus.planLimit` (no second setting). Device-local (`_meta`): the last run's input hash, the week-check dismissal, the week of the last overload toast.

Module dependency and switching off: `requires: ['todos']` (the field and `plan.requested` create ToDos through the capture target). `disableModule` wipes the collections (delete policy) **before** it emits `module.disabled`, and the planner's service is stopped by a live query whose timing is incidental, so the cleanup needs a new additive, **awaited `module.disabling`** event emitted before the state write and before any wipe (`core/modules/activation.ts`, `core/events/events.ts`, package 1). On it the planner stops its runs and restores every planner-own `plannedFor` (mark matches) to `planMark.prior` or clears it, and clears the mark – in both policies, because the rows are still there. `bus.emit` swallows handler errors, so the state write and the wipe proceed even if the handler throws; the fallback is the ToDo side: while the planner is inactive it ignores `planMark`, and whenever it sees a **stored** `_modules` row with `enabled: false` **and** `syncSettled()` it restores from `planMark.prior` or clears, idempotently – it needs no planner table for that. A late write-back from a device that was offline while another disabled the planner is cleaned the same way; if its user date was never in `prior` it is lost – accepted and tested. Tests: „Später Do → assigned Sa → disable (keep and delete) → plannedFor = Do, no active planner row“, „… → user clears date → disable → plannedFor empty“, „disabling handler throws → state and wipe proceed, next start cleans the marks“, „late write-back after disable → cleaned on the next start“.

Schema impact outside the planner: one optional ToDo field `planMark`, the `ignoreFields` entry in core automation, the `module.disabling` event and the `syncSettled()` helper with its pull flag (package 1); package 5 adds optional day windows inside the planner only.

## 3. Engine – `core/plan/` (pure, deterministic, tested)

Files: `types.ts` (contract, `DEFAULT_MIN = 30`), `capacity.ts`, `units.ts` (splitting), `engine.ts` (`plan()`), `diff.ts`, `explain.ts` (reason → German sentence via `t.planner.reasons`), `instructions.ts` (stage-0 parser, §6c). No clock inside; `today` is an input. Figures use one `formatMinutes(min, { compact? })` in `core/i18n/format`: the timetrack helper `duration(minutes)` (`modules/timetrack/components/format.ts`, „3 Std 5 Min“, five languages) moves there and gains a compact form for boards and bars („1 h 30“, „45 Min“); timetrack keeps calling the full form. (Distinct from the disk module's `formatDuration(ms)`.)

```ts
plan({ today, days: PlanDay[], items: PlanItem[], prev: Assignment[], settings }) → {
  assignments: Assignment[],                      // unit → day, minutes, order, reason, bumpedBy?, late?
  unplaced: { unit, reason: 'horizon' | 'too-long' | 'after-hard-due', bumpedBy? }[],
  diff: { added, moved: { unit, from, to, reason, by? }[], removed: { unit, from, reason, by? }[], unchanged },
  load: Record<date, { raw, usable, planned, free, over, mains }>, overflowMin }
```

Definitions: `raw = available − Σ blockers` · `usable = raw × (1 − buffer)` · **`free = usable − planned`** (this is the figure every surface calls „frei“) · `overflowMin = demand − Σ usable` of the horizon („mehr zu tun, als Zeit frei ist“). `plan()` slices `days` to `today … today + horizonDays − 1`; the scenarios pass `horizonDays: 7`.

Rules, in the order they are applied per day:

| #   | Rule                         | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Capacity**                 | Blockers = stored blockers + calendar items of kind `event`/`external` with a time (minutes = end − start, else 60 as in the calendar's `DEFAULT_BLOCK_MINUTES`); reminders (`kind: 'reminder'`) and plan chips never block; all-day items 0 unless `allDayBlocks`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 2   | **Units**                    | An item longer than `maxSessionMin` and `splittable` becomes `ceil(min / max)` sessions of equal length (≥ `minSessionMin`); an item without an estimate counts `DEFAULT_MIN`; sessions of one item go on different days, except under deadline pressure.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 3   | **Pinned first**             | A pinned item (planner action „Festnageln“ only) is placed on its day whatever the capacity (overload is counted, not refused).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 4   | **Hard due before priority** | Only a hard due **inside the horizon** is pressure. `latestStart(unit)` walks back from the due date over days that actually have room (a free Thursday does not count). A unit whose latest start is today is placed now – it may use the buffer, a second session of the same item may land on the same day, and this is the **only** rule that pulls a unit forward from a later planned day. Order inside: latest start, due date, priority.                                                                                                                                                                                                                                                                                                                                                      |
| 5   | **Priority before age**      | The rest, never a unit planned for a later day: priority ↓, then **kept** (planned for this day before) ↑ **carried** (planned for an earlier day) ↑ new, then soft due ↑, then `createdAt` ↑, then id. A unit is placed when it fits the remaining usable minutes and the day has fewer than `planLimit` main items (≥ 30 min); small things fill the rest. The **order inside a day** is then recomputed without `prev` (tier from the placing rule – pinned set, deadline set, rest – then priority ↓, due ↑, `createdAt` ↑, id), so the fixpoint holds over (unit, date, minutes, order) and a rerun never rewrites the „Heute“ card's order; a unit that keeps its day keeps its stored `reason` and cause (the prototype carries them forward), fixtures snapshot (unit, date, minutes, order). |
| 6   | **Stability**                | An item keeps its day whenever it still fits; a new item with the same priority never displaces it. A higher priority or a deadline may: the diff lists the units that **outrank** the moved one and took room on that day (`bumpedBy`, largest first, never a session of the same item) – also for a unit that drops out of the horizon. A later session that cannot follow its earlier part names the part (`after-part`). Nothing is pulled forward on its own: a done item frees room and the rest stays where it was (S5); the explicit reshuffle is „alles neu mischen“ (`prev = []`, §6c).                                                                                                                                                                                                     |
| 7   | **Honest output**            | Items without room in the horizon → `unplaced: horizon`; longer than any day → `too-long`; placed after a hard due → `late` + `after-hard-due`. ## 4. Source contract – `contributions.plannable`

```ts
export interface PlannableItem {
  id: string; kind: string; title: string; to: string;         // route with ?open=<id>
  durationMin?: number; priority?: 0 | 1 | 2 | 3;
  due?: { date: string; hard: boolean }; earliest?: string; plannedFor?: string; planMark?: { date: string; order: number };
  done?: boolean; personId?: string;
  link?: { kind: 'note' | 'mail' | 'invoice' | 'event'; id: string; label: string };
}
export interface PlannableSource {
  list(ctx: { today: string; until: string }): Promise<PlannableItem[]>;      // open, plannable things only
  onAssign?(id: string, date: string | undefined, order?: number): Promise<void>; // ToDo: plannedFor + planMark; no order = clear the mark
  onDone?(id: string): Promise<void>;                                        // ToDo: done; invoice: never (paid stays in the module)
  onEstimate?(id: string, minutes: number): Promise<void>;                   // ToDo: estimateMin
}
contributions.plannable?: () => Promise<{ default: PlannableSource }>;
```

- Lazy like `calendarItems`; collector `collectPlannable(manifests)` in `core/modules/contributions.ts` (a failing source never breaks the others, modules read only their own data). Write-back is the **callback surface of the same contract** (typed, testable, no module import). Requests _into_ the plan from other modules use the bus, mirroring `todo.requested`: `'plan.requested': { title; durationMin?; priority?; due?; link? }` – the planner service turns it into a ToDo (quick-capture target) plus a planner item.
- The run is driven by live queries over `collectPlannable`, the timed calendar items and the planner's own tables (not by `core/db/writeHook`, which has one listener that belongs to the automation engine and never sees sync-applied writes).
- Blockers need no new contract: timed `calendarItems` of kind `event`/`external` (not `reminder`, not `plan`, not done) are blockers.
- `accounts` never gets `plannable`: already pinned by `exclusion.test.ts`, which fixes the vault's contribution keys to `onboarding` and `services` – no new test needed. The automation engine already excludes the vault. Retired modules: no contribution (registry rule).

## 6. AI layer

**a) The planner has no `aiSchema`.** Like mail, music and feeds today it does not exist for the assistant: not in the cloud prompt, the tools, the full-text search, the data API or chat context (`core/ai/scope.ts aiModules()` is the single filter; `exclusion.test.ts` pins the list of modules without a schema and package 1 adds `planner` to it; the `ai.ts` that `gen:module` copies into `modules/planner/` is deleted together with the `aiSchema` import in the generated manifest; the shared template stays). Decided by this chat and the council rounds (German one-liner each):

- **Daten:** Jedes offene ToDo ist planbar (Ausnahme „Nicht planen“, `someday`, Unteraufgaben); ohne Schätzung 30 Min („~30 Min“); das eine Feld legt ToDos an, Planer-Einträge haben in v1 keinen eigenen Titel; Ids über `upsert` (Tag = Datum, Item = `module:id`, Sitzung = `<itemKey>#<k>`) mit einem Helfer, der Tombstones vorher aufhebt; Indizes `day.date`, `assignment.date/itemKey`; ganzes Modul `dataApi: false`; `requires: ['todos']`.
- **Rückschreiben – was der Nutzer merkt:** die „Heute“-Karte zeigt die geplanten Dinge in Planreihenfolge, die ToDo-Seite zeigt sie in Heute/Bald mit „im Plan: Mi“; ein selbst gesetztes Datum (auch „Später“) bleibt eine Untergrenze, nie ein Pin; Rückgängig stellt alles wieder her; beim Abschalten des Planers kommen die eigenen Daten zurück.
- **Rückschreiben – Mechanik:** `plannedFor` + `planMark = { date, order, prior }`; planer-eigen nur, wenn `planMark.date === plannedFor`, alles andere gilt als Nutzerdatum (sichere Richtung, weil Sync je Feld mischt); `prior` trägt das überschriebene Nutzerdatum mit, damit jede Seite es ohne Planer-Tabellen wiederherstellen kann; ToDo-seitige Schreiber löschen die Marke nur bei echter Datumsänderung; Import und Daten-API streifen die Marke; Nutzerdatum wird nach `item.earliest` kopiert, jede Änderung ersetzt es, Löschen entfernt es; ein zurückgeschriebenes `prior` nur, wenn es nicht in der Vergangenheit liegt.
- **Läufe – was du merkst:** der Plan ändert sich nur, wenn sich etwas geändert hat; Rückgängig bleibt rückgängig; ein eigenes Datum geht nicht verloren, auch nicht während ein Sync läuft. Mechanik: jeder Lauf schreibt idempotent zurück; Nutzeraktionen in einem `undoable`, Hintergrundläufe serialisiert und nicht undoable; Nutzerdaten werden nur kopiert oder überschrieben, solange `syncSettled()` gilt (ohne Sync immer; sonst Lock frei und letzter Pull vollständig), sonst nur im Speicher als Untergrenze genutzt; Hash ohne `prev`, Marke und eigene Zeilen, mit Kalender-Blockern; LWW-Rennen mit einem Offline-„Später“ hingenommen; Tests: null Folgeschreibungen, Fixpunkt (Tage, Minuten, Reihenfolge), Undo bleibt, zwei Geräte konvergieren, null Automations-Ereignisse (`ignoreFields` im Core, trifft auch Datums-Taps), Deaktivieren über `module.disabling` in beiden Politiken.
- **Engine – was du merkst:** Fristen gehen vor, Wichtiges kommt früher, nichts springt von selbst nach vorn, jede Verschiebung hat einen Grund. Mechanik: Reihenfolge Kapazität → Pin → Frist (nur im Horizont, einzige Regel, die vorzieht) → Priorität (kept vor carried vor neu); Tagesreihenfolge ohne `prev` neu sortiert (Stufe aus der Platzierungsregel), Gründe bleiben stehen, solange der Tag bleibt; nichts rückt von selbst nach vorn; Sitzungen an verschiedenen Tagen außer unter Fristdruck; Hauptsachen je Tag = `focus.planLimit`; `free = usable − planned`; Erinnerungen blocken nie; Ursachen nennen nur Höherrangige, nie eine Sitzung desselben Dings, eine spätere Sitzung „folgt auf Teil 1“; `alles neu mischen` ist das einzige explizite Neumischen.
- **Oberfläche:** Kopf = eine Zahl (heute; „Heute ist frei.“ bei 0 Minuten), Woche im Widget („Bis So“); Zeilen nur Titel und Minuten, Grund hinter „Warum hier?“; Toast nennt höchstens zwei Verschiebungen plus „n weitere“; Feld in Paket 1 „Eintragen“, „oder sagen“ ab Paket 2 nur auf Deutsch; „Woche prüfen“ immer über ⋯ erreichbar, zusätzlich als stiller Textlink am Montag ab Paket 2 (Schalter `focus.weekCheck`, Standard aus, Wegklicken per × je Kalenderwoche gerätelokal), nie ein Dialog von selbst; Toast höchstens zwei Namen plus „n mehr“, unter 68 Zeichen je Zeile; Überlast im Kopf der Gruppe „Wartet auf freie Zeit“, Toast nur beim ersten Auftreten je Woche (Schalter), kein „Jetzt wichtig“-Eintrag, und der Hinweis „Neu planen möglich“ dort entfällt; ein Chip je Tag im Kalender, abschaltbar, Karte und Agenda überspringen ihn; Karte und „Anfangen“ nutzen weiter die ToDo-Schätzung, Sitzungslänge nur im Brett; „Neu planen“ der ToDo-Seite ausgeblendet, solange der Planer aktiv ist; keine Automations-Aktion und kein `watch`, nur das Ereignis; Widget `ProgressList` (`key`, `title`, `value`, `max`, `detail`) ohne `overText`; `formatMinutes` aus dem Zeiterfassungs-Helfer, kompakte Form für Bretter; Dauer-Stufen 5/15/30/60 (Fokus-Richtlinie) plus freie Eingabe; Widget-Zeile „Bis <letzter gezeigter Tag>“; Identität `indigo`/`cobalt`/`kennzahl`/`fortschritt`/`weekBars`, `order: 15`, `maturity: 'preview'` bis Paket 3.
- **KI:** kein `aiSchema` (Eintrag in der Liste von `exclusion.test.ts`, die kopierte `ai.ts` im Planer gelöscht); eine Zeile in der Nutzerdoku sagt, dass Plan-Sätze ins Planer-Feld gehören, nicht in die globale Leiste; lokale Stufe mit eigenem Prompt und eigener Grammatik, nur Desktop und nur bei eingeschalteter KI; das Planer-Feld ruft nie den Router; Planer-Änderungen aus Text wendet der Planer selbst an.
- **Später, eigenes Konzept:** Zeitfenster sind Paket 5; Lernen aus der Zeiterfassung, Energie, Gewohnheiten als Blöcke, Wochenrückblick kommen danach.
