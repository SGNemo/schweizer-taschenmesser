## 0. In one paragraph

A new module **`planner`** („Planer“, area Planen) distributes everything that has to get done over the coming days: the open ToDos (the backlog stays in ToDos, nothing is duplicated), later invoices, cancellation deadlines and notes marked „In den Plan“. Per day the user states **available time** and **blockers** (appointments come from the calendar by themselves). A pure, deterministic engine in `core/plan/` turns items + days into **assignments** (item → day, session minutes, reason), a short list „waits for a free day“ and a diff to the previous plan. Hard deadlines beat priority, priority beats age, a buffer is never planned, large items become sessions, existing assignments move only when they must, nothing is pulled forward except by a deadline, and every move names its cause. The planner writes `plannedFor` and a plan order back to the ToDo, so the existing „Heute“ card, the morning digest, the focus round and „Später“ keep working unchanged. AI enters in two stages: rules (free, offline, also with „KI aus“) and the local model (desktop with a downloaded model; sees titles, nothing leaves the device). The cloud never gets the planner's schema, actions or data – a cloud-only filter on every cloud path, and the planner is never offered as chat context; pinned by tests. Everything goes through a preview with a diff and an undo toast.

## 2. Data model

Three synced collections (`planner_day`, `planner_item`, `planner_assignment`; envelope + `createRepo`, dates `YYYY-MM-DD`, times `HH:mm`, minutes as integers). The manifest sets `dataApi: false` for the whole module – the plan, blocker labels and day notes describe the user's days and are never offered to the import API or MCP. **Deterministic ids through `repo.upsert`**, plain indexes, no unique indexes (two devices that touch the same day offline must merge, not collide):

| Collection   | Id                        | Fields                                                                                                                                                                                                                                                                                   | Notes                                                                                                                                                                                                                                                                                                                                                 |
| ------------ | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `day`        | `date`                    | `date` (index) · `availableMin?` 0–1440 · `blockers: [{ id, label, min, from?, to? }]` · `note?`                                                                                                                                                                                         | Only days the user touched are stored; a missing day = the weekday default. **Calendar appointments are not stored** – they are read live from `calendarItems`. `from`/`to` are optional windows (package 5).                                                                                                                                         |
| `item`       | `sourceKey` (`module:id`) | `source: { module, id }` · `title?` (own entries; **empty in v1** – the field, `plan.requested` and the prefix create ToDos) · `durationMin?` · `priority?` · `due?: { date, hard }` · `earliest?` · `pinned?` · `splittable?` · `excluded?` · `wrote?: { plannedFor, stamp }` · `order` | One row per planned thing. For a sourced item the planner stores **only what the source does not have** (see ownership), plus the hard due when the user marks „Frist“ or writes „bis <Tag>“ in the planner's field (a copy; if the source date drifts the row shows „ToDo-Datum jetzt Fr“). `wrote` remembers the last write-back and its HLC stamp. |
| `assignment` | `<itemKey>#<k>`           | `itemKey` · `k`, `of` · `date` (index) · `minutes` · `order` · `reason` · `bumpedBy?: string[]` · `late?`                                                                                                                                                                                | Session `k` of `of`. Deterministic ids, so two devices that run before they sync write the **same rows** (field LWW merges them) and a run updates rows in place; when `of` changes, sessions inherit the previous days by index, surplus rows get a tombstone; only units that disappear (done, excluded) are tombstoned.                            |

What syncs and backs up: the three collections (free text only in `day.note` and `blockers[].label`; `item.title` stays empty in v1); never appointments, never titles of sourced items (they live at the source).

| `someday`, subtasks, recurrence                                   | ToDo                                     | excluded (`someday`, `parentId`); only the current occurrence                                                                                                                                                                                                       | –                                                                                                                                                                                                                                                                                                                                                                                                                            |

Runs and write-back (one rule set, package 1 pins it with tests):

- **Every run writes back idempotently:** only values the planner owns (`plannedFor` equal to `wrote.plannedFor` or to the item's current assignment, `planOrder`), only when different. The planner stores `wrote` (value + HLC stamp) **before** it calls `onAssign`, so a synced device recognises the value as planner-own even if the rows arrive in that order.
- **User action vs background:** a run started from the planner UI (add, done, Später, pin, instruction, „Neu verteilen“) runs **inside the user's `undoable`**, write-backs included, so the toast's „Rückgängig“ restores everything. Every other run (live query after a ToDo-page edit, sync-applied change, day change, app start, undo) is background: serialised after any open user action, not undoable, same idempotent write-back. Why not "background never writes back": the „Heute“ card shows `plannedFor ≤ today`, so a morning without a planner action must still move yesterday's leftovers; convergence comes from determinism, not from an origin signal (live queries have none).
- **Convergence:** input hash in `_meta` = `today` + settings + items + days + blockers (not `prev`, not the planner's own rows, not planner-own `plannedFor` values); identical hash → no run; a run whose output equals the stored rows writes nothing (test „one run → zero follow-up writes“). After a sync-applied assignment change one background recompute writes only rows whose fields differ (two devices converge; test „two devices converge“). An undo restores the inputs too, so the following background run writes nothing (test „undo stays undone“).
- **Automation:** write-backs that touch only `plannedFor`/`planOrder` do not emit `todos.task.updated` (the ToDo automation `watch` ignores such patches; test „one run → zero automation events“), so no rule fires on a reshuffle.

Settings (synced scope `planner`, registry section of the module, folded „Weitere Einstellungen“): `defaultAvailable` per weekday (Mo–Fr 240, Sa 120, So 0) · `bufferShare` 0 / 10 / **20** / 30 % · `horizonDays` 7 / **14** / 28 · `maxSessionMin` 45 / 60 / **90** / 120 · `minSessionMin` 25 · `autoReplan` on · `calendarBlocks` on · `allDayBlocks` off · `weekCheck` on (the Monday line) · `calendarChips` on (package 2). The number of main items per day **reuses** `focus.planLimit` (no second setting). Device-local (`_meta`): the last run's input hash.

Module dependency and switching off: `requires: ['todos']` (the field and `plan.requested` create ToDos through the capture target). On `module.disabled` for `planner` the service, before its teardown, restores every planner-own `plannedFor` to the user's `item.earliest` or clears it, and clears `planOrder` (test: „Später Do → assigned Sa → disable → plannedFor = Do“).

Schema impact outside the planner: one optional ToDo field `planOrder` in package 1 (version bump, no-op migration); package 5 adds optional day windows inside the planner only.

## 3. Engine – `core/plan/` (pure, deterministic, tested)

Files: `types.ts` (contract, `DEFAULT_MIN = 30`), `capacity.ts`, `units.ts` (splitting), `engine.ts` (`plan()`), `diff.ts`, `explain.ts` (reason → German sentence via `t.planner.reasons`), `instructions.ts` (stage-0 parser, §6c). No clock inside; `today` is an input. Figures use one `formatMinutes(min)` in `core/i18n/format` (new, five languages: „1 h 30“, „45 Min“; distinct from the disk module's `formatDuration(ms)`).

```ts
plan({ today, days: PlanDay[], items: PlanItem[], prev: Assignment[], settings }) → {
  assignments: Assignment[],                      // unit → day, minutes, order, reason, bumpedBy?, late?
  unplaced: { unit, reason: 'horizon' | 'too-long' | 'after-hard-due', bumpedBy? }[],
  diff: { added, moved: { unit, from, to, reason, by? }[], removed: { unit, from, reason, by? }[], unchanged },
  load: Record<date, { raw, usable, planned, free, over, mains }>, overflowMin }
```

Definitions: `raw = available − Σ blockers` · `usable = raw × (1 − buffer)` · **`free = usable − planned`** (this is the figure every surface calls „frei“) · `overflowMin = demand − Σ usable` of the horizon („mehr zu tun als frei“). `plan()` slices `days` to `today … today + horizonDays − 1`; the scenarios pass `horizonDays: 7`.

Rules, in the order they are applied per day:

| #   | Rule                         | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **Capacity**                 | Blockers = stored blockers + calendar items of kind `event`/`external` with a time (minutes = end − start, else 60 as in the calendar's `DEFAULT_BLOCK_MINUTES`); reminders (`kind: 'reminder'`) and plan chips never block; all-day items 0 unless `allDayBlocks`.                                                                                                                                                                              |
| 2   | **Units**                    | An item longer than `maxSessionMin` and `splittable` becomes `ceil(min / max)` sessions of equal length (≥ `minSessionMin`); an item without an estimate counts `DEFAULT_MIN`; sessions of one item go on different days, except under deadline pressure.                                                                                                                                                                                        |
| 3   | **Pinned first**             | A pinned item (planner action „Festnageln“ only) is placed on its day whatever the capacity (overload is counted, not refused).                                                                                                                                                                                                                                                                                                                  |
| 4   | **Hard due before priority** | Only a hard due **inside the horizon** is pressure. `latestStart(unit)` walks back from the due date over days that actually have room (a free Thursday does not count). A unit whose latest start is today is placed now – it may use the buffer, a second session of the same item may land on the same day, and this is the **only** rule that pulls a unit forward from a later planned day. Order inside: latest start, due date, priority. |
| 5   | **Priority before age**      | The rest, never a unit planned for a later day: priority ↓, then **kept** (planned for this day before) ↑ **carried** (planned for an earlier day) ↑ new, then soft due ↑, then `createdAt` ↑, then id. A unit is placed when it fits the remaining usable minutes and the day has fewer than `planLimit` main items (≥ 30 min); small things fill the rest.                                                                                     |
| 6   | **Stability**                | An item keeps its day whenever it still fits; a new item with the same priority never displaces it. A higher priority or a deadline may: the diff lists **every unit that took room on that day** (`bumpedBy`, largest first) – also for a unit that drops out of the horizon. Nothing is pulled forward on its own: a done item frees room and the rest stays where it was (S5); „Lücke füllen“ is an explicit action.                          |
| 7   | **Honest output**            | Items without room in the horizon → `unplaced: horizon`; longer than any day → `too-long`; placed after a hard due → `late` + `after-hard-due`. Numbers, never alarms.                                                                                                                                                                                                                                                                           |
| 8   | **Reasons**                  | `pinned` · `deadline` · `deadline-buffer` · `new` · `kept` · `carried` (not done earlier) · `pulled` (a deadline pulled it forward); moves and drop-outs: `bumped` (by whom, list) · `capacity` (the day shrank) · `done` (removed because finished). Every reason has one calm sentence („muss bis Do fertig sein“, „weiter von Di“, „Mi ist voll: Steuerbescheid, Steuer Teil 2“).                                                             |

## 4. Source contract – `contributions.plannable`

```ts
export interface PlannableItem {
  id: string; kind: string; title: string; to: string;         // route with ?open=<id>
  durationMin?: number; priority?: 0 | 1 | 2 | 3;
  due?: { date: string; hard: boolean }; earliest?: string; plannedFor?: string;
  done?: boolean; personId?: string;
  link?: { kind: 'note' | 'mail' | 'invoice' | 'event'; id: string; label: string };
}
export interface PlannableSource {
  list(ctx: { today: string; until: string }): Promise<PlannableItem[]>;      // open, plannable things only
  onAssign?(id: string, date: string | undefined, order?: number): Promise<void>; // ToDo: plannedFor + planOrder
  onDone?(id: string): Promise<void>;                                        // ToDo: done; invoice: never (paid stays in the module)
  onEstimate?(id: string, minutes: number): Promise<void>;                   // ToDo: estimateMin
}
contributions.plannable?: () => Promise<{ default: PlannableSource }>;
```

- Lazy like `calendarItems`; collector `collectPlannable(manifests)` in `core/modules/contributions.ts` (a failing source never breaks the others, modules read only their own data). Write-back is the **callback surface of the same contract** (typed, testable, no module import). Requests _into_ the plan from other modules use the bus, mirroring `todo.requested`: `'plan.requested': { title; durationMin?; priority?; due?; link? }` – the planner service turns it into a ToDo (quick-capture target) plus a planner item.
- The run is driven by live queries over `collectPlannable` and the planner's own tables (not by `core/db/writeHook`, which has one listener that belongs to the automation engine and never sees sync-applied writes).
- Blockers need no new contract: timed `calendarItems` of kind `event`/`external` (not `reminder`, not `plan`, not done) are blockers.
- `accounts` never gets `plannable`: already pinned by `exclusion.test.ts`, which fixes the vault's contribution keys to `onboarding` and `services` – no new test needed. The automation engine already excludes the vault. Retired modules: no contribution (registry rule).

## 6. AI layer

**a) Entering by speech or text** uses the existing write pipeline (`core/ai/write/*`, preview, undo). „Steuer zwei Stunden bis Donnerstag, wichtig“ in the global bar → ToDo `create` (title, dueDate, priority; package 4 adds `estimateMin` to the ToDo `aiSchema` fields so the estimate survives – the quick-capture extractor already yields it). A sentence typed into the **global** bar travels like any other assistant input (rules → local → cloud if allowed); the cloud never receives the planner's schema or actions and a cloud answer naming `planner` is rejected as `unknown-module`, so it cannot produce planner ops – only ToDo ops. The **planner's own field** never calls the router: it runs `instructions.ts` and, on the desktop, the local stage, nothing else (fetch spy test). Planner actions (package 4, `aiSchema.actions`): `available` (update `day`: „Donnerstag zwei Stunden“), `block` (create blocker: „Donnerstag 14 bis 16 Uhr Werkstatt“), `pin` (transition on `item`: „Steuer auf Freitag“), `exclude` („Keller nicht planen“). Five eval inputs each in `web/tests/ai/eval-set.json`.

Decided by this chat and the council rounds (German one-liner each):

- **Daten:** Jedes offene ToDo ist planbar (Ausnahme „Nicht planen“, `someday`, Unteraufgaben); ohne Schätzung 30 Min („~30 Min“); das eine Feld legt ToDos an, Planer-Einträge haben in v1 keinen eigenen Titel; Ids über `upsert` (Tag = Datum, Item = `module:id`, Sitzung = `<itemKey>#<k>`), keine Unique-Indizes; ganzes Modul `dataApi: false`; `requires: ['todos']`.
- **Rückschreiben:** `plannedFor` und `planOrder` für alle Dinge eines Tages (die Karte zeigt `planLimit` davon plus „+ n mehr“); ein vom Nutzer gesetztes Datum (auch „Später“, „Auf morgen schieben“, Eingang sortieren) ist `earliest`, nie Pin, und wird vor dem Überschreiben in `item.earliest` kopiert; Pins nur über „Festnageln“; `wrote` mit Stempel vor dem Schreiben; jeder Lauf schreibt idempotent zurück, Nutzeraktionen in einem `undoable`, Hintergrundläufe serialisiert und nicht undoable; Hash ohne `prev`; „ein Lauf → null Folgeschreibungen“, „Undo bleibt“, „zwei Geräte konvergieren“, „null Automations-Ereignisse“; Deaktivieren stellt das Nutzerdatum wieder her.
- **Engine:** Reihenfolge Kapazität → Pin → Frist (nur im Horizont, einzige Regel, die vorzieht) → Priorität (kept vor carried vor neu); nichts rückt von selbst nach vorn; Sitzungen an verschiedenen Tagen außer unter Fristdruck; Hauptsachen je Tag = `focus.planLimit`; `free = usable − planned`; Erinnerungen blocken nie.
- **Oberfläche:** Zeilen nur Titel und Minuten, Grund hinter „Warum hier?“; „Woche prüfen“ als stille Zeile am Montag, nie ein Dialog von selbst; Überlast im Kopf der Wartegruppe und als Toast nur beim Auftreten oder Wachsen, kein „Jetzt wichtig“-Eintrag; ein Chip je Tag im Kalender, abschaltbar, Karte und Agenda überspringen ihn; „Neu planen“ der ToDo-Seite ausgeblendet, solange der Planer aktiv ist; keine Automations-Aktion, nur das Ereignis; Widget `ProgressList` ohne `overText`; Identität `indigo`/`cobalt`/`kennzahl`/`fortschritt`/`weekBars`, `order: 15`, `maturity: 'preview'` bis Paket 3.
- **KI:** `aiSchema.cloud: false` + `cloudModules()` auf allen Cloud-Pfaden von `assistant.ts` (System-Prompt, Tools, Stufen 2/3, `writable`), Planer nie als Chat-Kontext; lokale Stufe nur Desktop und nur bei eingeschalteter KI; das Planer-Feld ruft nie den Router.
- **Später, eigenes Konzept:** Zeitfenster sind Paket 5; Lernen aus der Zeiterfassung, Energie, Gewohnheiten als Blöcke, Wochenrückblick kommen danach.
