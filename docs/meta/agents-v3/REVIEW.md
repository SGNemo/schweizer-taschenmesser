## Befund Nr. 1: der Lead delegiert nicht

`nemo-lead.json` (v2) hat **keinen `multiagent`-Block**. Ohne ihn gibt es weder `list_agents` noch `send_to_agent`; der Lead macht alles selbst, die 19 anderen Definitionen werden nie aufgerufen ([MA-multi]: Delegation läuft über `multiagent.subagents`; die Tools erscheinen mit dem Block). Behoben in v3 (`nemo-lead.json`):

```json
"multiagent": { "type": "multiagent_20261001",
  "subagents": { "type": "enabled", "inline_agents": { "type": "disabled" }, "predefined_agents": ["nemo-a11y", … 19 Einträge] },
  "workflows": { "type": "disabled" }, "advisor": { "type": "disabled" } }
```

Belege: Feldnamen und Grenzen [API-agent] (`predefined_agents` ≤ 20, `inline_agents` aus → mindestens ein Eintrag Pflicht, Tiefe 1: ein referenzierter Agent darf selbst keinen `multiagent`-Block tragen, sonst 400); 25 Kind-Threads gleichzeitig, Advisor- und Run-Threads ausgenommen [MA-threads]; `inference_geo` muss bei Lead und allen 19 gleich oder überall ungesetzt sein [MA-multi] (v3: überall ungesetzt, `validate.mjs` prüft das). In der JSON-Quelle stehen Namen; `to-ant.mjs` schreibt daraus Pfade (`./nemo-po.md`), die `ant apply` in Abhängigkeitsreihenfolge zu IDs auflöst ([ant-apply], CLI ≥ 1.40.0). Berichte: der Subagent-Thread bleibt offen, Nachfragen gehen per `send_to_agent` in denselben Thread, der Bericht kommt als `agent.thread_message_received` zurück [MA-multi][MA-threads]. **unsicher:** ob eine zweite Delegation an dieselbe Rolle einen neuen Thread öffnet oder den alten nutzt – die Doku sagt nur, dass Follow-ups möglich sind; Lead-Prompt verlangt deshalb Nachfragen statt Neuaufträge. Alle Threads teilen Sandbox, Dateisystem, Vault und Budget [MA-multi][MA-budget] – darum eigene Worktrees je Agent (SHARED.md).

### 1.2 Workflow zu schwer für kleine PRs?

Ja. v2 schickt jede PR durch reviewer (+ security/design/a11y) und merge, jeder Agent liest 7–9 k Zeichen Prompt und startet `npm test` (13 min). **Leichter Weg (v3, SHARED.md „Light path“):** docs-/test-/i18n-only → nur `nemo-reviewer` (Scope, CI, Übergabeformat; Reviewer-Prompt kennt den Modus) → `nemo-merge`. Entfällt: security, design, a11y, lokale Vollsuiten. **Nicht** leicht (Council-Befund): alles unter `.github/**` (gitleaks, scribble-guard, `permissions:`, Publish-Schritte liegen dort), RULES.md-Bereiche, `CLAUDE.md`, `AGENTS.md`; `docs/meta/agents-v3/**` und `scripts/agents/**` mergt nur Sven selbst (sie sind die live gelesenen Regeln der 20 Agenten und laufen auf seinem Rechner). Grundlage: CI läuft ohnehin auf jeder PR (`ci.yml`: `changes` → nur berührte Pakete + Smoke-E2E; Docs-Budget, Docs-Pairs, gitleaks). Ein Reviewer bleibt Pflicht, weil er der einzige Gate für „ein Thema, Übergabeformat, `no-changelog`“ ist (v2-Lektion: vergessene Labels).

### 1.3 Reichen Prompt-Grenzen bei einem Admin-Token für alle?

Nein, nicht allein – aber die Alternative „eigener Token nur für nemo-merge“ geht in einer Multi-Agent-Session **technisch nicht**: Vault-Credentials gelten für jeden Thread der Session („In multiagent sessions, vault credentials apply to every thread“ [MA-vault]); das Repo-Mount hat genau einen `authorization_token` [MA-github]. Ein Merge-Token nur für `nemo-merge` hieße: nemo-merge in eigener Session mit eigenem Vault (z. B. als geplanter Deployment-Lauf, der MERGE-READY-PRs abarbeitet), nicht als Subagent des Leads. Das ist möglich, kostet aber den direkten Dialog Lead → merge.

Billig und wirksam (Empfehlung, in SETUP.md Schritt 3):

1. **Fine-grained PAT** nur für dieses Repo, **ohne** `Administration` (kein Branch-Schutz änderbar): Contents R/W, Pull requests R/W, Issues R/W, **Actions: Read**, Metadata R. **Kein `Workflows`, kein Actions: write** (Council-Befund): `release.yml` liest die Signier-Secrets direkt aus den Repo-Secrets (kein `environment:`), ein Branch mit `on: push`-Workflow könnte sie auslesen; Actions: write erlaubt `workflow_dispatch` von `release.yml`/`dev-preview.yml`. Beides erst, wenn die Secrets in einem GitHub-Environment mit Sven als Required reviewer liegen. Bis dahin: Workflow-Änderungen als Patch im PR-Text, Sven pusht; flakige Jobs startet Sven neu. Die Doku empfiehlt Minimalrechte: „fine-grained personal access tokens with minimum required permissions … Avoid using tokens with broad access“ [MA-github].
2. **Rulesets** als technische Sperre (ein PAT ohne `Administration` kann sie nicht aufheben): `main` nur über PR **mit 1 Required approval** (der PAT handelt als Sven und kann die eigene PR nicht approven – sonst könnte ein Agent eine develop→main-PR selbst mergen) + Required Checks; **`develop` mit „Require a pull request“ bei 0 Approvals** (sperrt direkte Pushes, API-Merge von nemo-merge geht weiter); **Tag-Ruleset nur `refs/tags/v*`** (Create/Update/Delete; `dev-preview` ausgenommen, siehe 3) – sonst löst Contents: write über einen Tag `release.yml` aus; Immutable releases vorerst nicht (sie frieren auch die rollende Dev-Preview ein). Prüfung nur lesend, SETUP §4 „Erster Testlauf“.
3. **Ehrlich:** bash, git und REST bleiben jeder Rolle; „read-only“ und „nur nemo-merge mergt“ halten nur die Prompts (SHARED.md sagt es so). Und: ohne `Workflows`-Scope sind die Signier-Secrets trotzdem nicht fern – jeder `develop`-Push, den nemo-merge erzeugt, lässt agentengeschriebenen Code in CI-Jobs laufen, die sie halten (`release.yml` Dry-Run bei `web/scripts/**`/`web/src-tauri/**`, Android-Sign mit dem echten Keystore; `ci.yml` ruft `dev-preview.yml` mit `secrets: inherit`). Der echte Zaun ist ein GitHub-Environment mit Sven als Required reviewer; bis dahin Security-Review für Build-Inputs (SHARED.md). Nächste Schritte: dieses Environment, Read-only-Endpunkt `…/mcp/readonly` für Leserollen (zweiter Vault-Eintrag). Tag-Ruleset nur `v*` – `dev-preview` verschiebt die Dev-Preview-Pipeline selbst; Immutable releases erst, wenn die Dev-Preview nicht mehr rollend ist (Tests in SETUP §4 „Erster Testlauf“, nur lesend per `gh api …/rules/branches/…`).
4. **Werkzeug-Sperren statt nur Prompt:** v3 schaltet im GitHub-MCP je Rolle Tools ab (`merge_pull_request`, `enable_pr_auto_merge`, `push_files`, `create_or_update_file`, `delete_file`, `create_repository`, `fork_repository`, `run_secret_scanning` für alle außer merge; PR-/Branch-Schreibtools für Review-Rollen) – per `default_config.enabled: true` + `configs[].enabled: false` [MA-mcp][API-agent]. REST/`git` bleiben; die Sperre ist eine Stolperschwelle, kein Zaun.
5. Prompt-Grenzen bleiben (fünf harte Grenzen in jedem Prompt + SHARED.md). Antwort auf die Frage: Prompt + minimaler Token-Scope + Rulesets (main mit Approval-Pflicht, develop, Tags `v*`) reichen für `main`, `develop` und neue Release-Tags; **nicht** technisch gedeckt sind bestehende Release-Objekte und -Assets (Contents: write darf sie ändern; Immutable releases erst, wenn die Dev-Preview nicht mehr rollend ist, oder ein eigener Publish-Token) und „ein Agent ändert `.github/**`“ (voller Weg mit Security). Die Agenten-Regeln selbst (`docs/meta/agents-v3/**`, `scripts/agents/**`) mergt nur Sven – ein „OK“ in GitHub zählt nicht, jeder Kommentar erscheint als SGNemo. Ein zweiter Account brächte echte Approvals, keine zusätzliche technische Sperre (Frage 1 an Sven).

**unsicher:** ob GitHub-MCP-Toolnamen in `configs` serverseitig geprüft werden; unbekannte Namen sind laut [MA-mcp] „bare tool name as reported by the server“, Session-Create prüft MCP nicht. Toolnamen in v3 stammen aus dem Remote-Server dieser Sitzung (api.githubcopilot.com); Alternative ohne Namenslisten: Read-only-Endpunkt `https://api.githubcopilot.com/mcp/readonly` für reine Leserollen [GH-MCP] – kostet einen zweiten Vault-Eintrag, weil Credentials per URL (Pfad inklusive) gematcht werden [MA-mcp].

## 4 Umgebung und Zugang

- **Environment** (`environment.yaml`): `type: cloud`, `networking.type: limited`, `allow_package_managers: true` (github.com, api.github.com, registry.npmjs.org, crates.io, … [MA-env]), `allow_mcp_servers: true` (sonst 400 beim Session-Create, weil `api.githubcopilot.com` nicht in `allowed_hosts` [MA-env][MA-mcp]). Ohne `networking` wäre die Umgebung **unrestricted** [MA-env]. Environments sind nicht versioniert [MA-env].
- **Repo-Mount**: Session-Ressource `{type: github_repository, url, mount_path: /workspace/schweizer-taschenmesser, checkout: {type: branch, name: develop}, authorization_token}` [MA-github][API-session]. `checkout` fehlte in v2 → Default-Branch `main` (Lektion). Wechsel des Repos = neue Session; Token rotierbar über `sessions.resources.update` [MA-github].
- **Token – drei Stellen, ein PAT** ([MA-vault][MA-github][MA-mcp]): (1) `authorization_token` der Repo-Ressource (clone/push; `session.mjs` nimmt `$GITHUB_TOKEN` aus Svens Shell), (2) Vault-Credential `environment_variable` `secret_name: GITHUB_TOKEN`, `networking.allowed_hosts: [api.github.com]`, `injection_location: {header: true}` – in der Sandbox ein Platzhalter, am Ausgang ersetzt, nur im Header, (3) Vault-Credential `static_bearer` mit `mcp_server_url: https://api.githubcopilot.com/mcp/`. Ein Eintrag für beides gibt es nicht: ein Credential hat genau einen `auth.type`, Schlüssel `secret_name` **oder** `mcp_server_url` [MA-vault]. Max. 20 Credentials je Vault; `vault_ids` nur beim Session-Create (Update lehnt es ab [API-update]). **unsicher:** ob der Mount-Token auch als `GITHUB_TOKEN` im Shell-Environment landet – die Doku sagt nur „used to clone and push“; v3 verlässt sich nicht darauf (Vault-Eintrag 2).
- **Sandbox** ([MA-sandbox]): Ubuntu 24.04, Node 22 (Default), Rust stable + cargo, Python 3.12, Chromium unter `/opt/pw-browsers/chromium` (nicht im PATH; `PLAYWRIGHT_BROWSERS_PATH` gesetzt) – deckt sich mit AGENTS.md; 8 GB RAM, 10 GB Disk; **kein** GTK/WebKit, kein msvc, kein Android-SDK → AGENTS.md-Zeile „Tauri/Windows-Build nicht möglich“ stimmt. **unsicher:** Tool-Call-Timeout (AGENTS.md: ≈ 5 min) – in keiner gelesenen Seite genannt; `nohup`-Regel bleibt.
- **Dateien**: `/mnt/session/uploads/<file_id>` (Session-Ressource `file`) [API-session]; `/mnt/session/outputs` nur im Cookbook – **unsicher**, ob Outputs automatisch abrufbar sind.

## 6 Allgemein

- **JSON gegen API-Referenz** ([API-agent]): v2 nutzte bereits die gültige Objektform `model: {id, effort: {type}, speed}`; `mcp_servers[]` `{type: url, name, url}` ohne Token ✓; `tools[]` `agent_toolset_20260401` + `mcp_toolset` mit `mcp_server_name` ✓. Ungültig wären `advisors`, `mcp_server_id`, `authorization_token` an MCP-Servern, `effort` auf oberster Ebene – kommt in v2 nicht vor. Grenzen: `name` ≤ 256, `description` ≤ 2048, `system` ≤ 100 000, `metadata` ≤ 16 Schlüssel, ≤ 20 MCP-Server, ≤ 256 Tools. `scripts/agents/validate.mjs` prüft all das offline plus: kein Secret/Platzhalter-Token, jeder deklarierte MCP-Server hat ein Toolset (sonst 400 [MA-mcp]), Policies gültig, nur der Lead trägt `multiagent`, Roster vollständig, `inference_geo` einheitlich, SHARED.md referenziert.
- **Widersprüche zwischen den Prompts:** `strings.ts` – frontend „append in your module's block“, i18n „owns“: beide dürfen, i18n besitzt Katalog-Gesundheit, frontend darf nur an sein Modul anhängen (konsistent, bleibt). `ui/tokens.css` – architekt besitzt, design schlägt vor, frontend darf nicht (konsistent). `dependabot.yml` – deps vs. devops (1.1 geklärt). `contract/` – backend „owns … together with architekt/native“ und architekt „owns … together with backend“: Doppelbesitz, in `AGENTS.proposed.md`: architekt besitzt den Vertrag, backend/native je ihre Kopie. `Cargo.toml`-Bumps: native „not without deps“, deps „owns“ ✓. `web/scripts/e2e-smoke.mjs` – devops und qa „with“ einander ✓.
- **Berichtsformat:** v2 hatte drei Varianten (Lead-Erwartung, Shared-Block, je Rolle „## Report“); v3 ein Block in SHARED.md, Rollen-Abschnitte nennen nur noch rollenspezifische Zusatzfelder.
- **GitHub-403-Fallback:** korrekt und weiterhin nötig (GitHub-MCP läuft mit dem PAT als Bearer [GH-MCP]; bestimmte Endpunkte liefern 403 „Resource not accessible by integration“). Ergänzt um: `$GITHUB_TOKEN` nur im Header (Platzhalter-Mechanik), nie für `git`.
- **MERGE-READY + Head-SHA statt Approval:** weiterhin nötig, solange alle Agenten mit Svens Token laufen – GitHub lehnt Self-Approval ab (422). Ein zweiter Token (zweiter Account) im selben Session-Vault würde allen Threads gehören (1.3), also keine getrennten Reviewer-Identitäten. Lösbar nur mit Reviewer/Merge in getrennter Session; Empfehlung: bei MERGE-READY bleiben (Frage 1).
- **`always_allow`:** Agent-Toolset-Default ist `always_allow`, MCP-Default `always_ask` [MA-perm] – v2 hatte beides explizit gesetzt, v3 auch; `session.mjs` zeigt `requires_action` an und kann mit `--auto-approve` antworten.
- **Console vs. `ant`:** `ant apply` adoptiert keine in der Console angelegten Agenten (Doppelanlage) [ant-apply] → alle 20 nur per `ant` (SETUP.md).

## Entschieden (Sven, 2026-11-08: alle Empfehlungen; Bullets in `docs/decisions/meta.md`)

Die vier Fragen mit der jeweils gewählten Option (Empfehlung zuerst, so übernommen):

1. **Token und Rulesets:** (Empfohlen) ein Fine-grained PAT ohne `Administration`/`Workflows`/Actions-write + Rulesets auf `main`, `develop` (PR-Pflicht, 0 Approvals – damit pushen auch deine Claude-Code-Chats `scribble/` nur noch per Mini-PR; CLAUDE.md-Zeile entsprechend ändern) und Tags `v*` + MERGE-READY-Verfahren – oder zweiter Account für merge/reviewer in eigener Session (echte Approvals, mehr Betrieb).
2. **Lead-Modell:** (Empfohlen) Opus 5.5 high ohne Advisor – oder Sonnet 5.5 high mit Opus-Advisor (billiger je Turn, aber jede Konsultation schickt den ganzen Thread; Advisor-Antworten können im Event-Stream redigiert sein [MA-multi]).
3. **Workflows für den Lead:** (Empfohlen) aus – oder an mit Prompt-Grenze „nur auf Svens Wort, ≤ 5 Agenten je Run“.
4. **Fable für creativity:** (Empfohlen) ja, `claude-fable-5-1` ist verfügbar; falls Session-Create `model_not_budgetable` meldet, auf Opus high zurück.
