# CI and Dev-Preview

CI jobs, caches, sharding; rolling Dev-Preview build. Index: [HOW-TO](../HOW-TO.md). Commands run in `web/` unless stated.

## CI layout, caches and sharding
- **Which checks run when:** table in [HOW-TO](../HOW-TO.md). The `changes` job sets per-package flags; plain PR = smoke E2E (`E2E_PROFILE=smoke`, file list `SMOKE_FILES` in `web/playwright.config.ts`: add a file there when it guards a critical path), full run = push `develop`/`main`, `nightly.yml`, label `full-ci` (`full-ci.yml` dispatches `ci.yml`), manual run. `E2E_SEED=0` leaves out the seed project and its second web server (it runs in its own job `e2e-seed`, on every run that runs the app E2E: output `seed` of `changes`). Unit tests: `vitest --shard=i/3`.
- **Concurrency:** a newer push to a PR cancels the older run of that PR; runs for `develop`, `main` and dispatches are never cancelled, they queue (one running, one pending per ref; a newer push replaces a *pending* run). A run that starts therefore finishes and the Dev-Preview of that commit is built and published. A commit that is replaced while pending gets no run of its own: its code is covered by the next run only if that run's push range includes it, so when a code push is replaced by a docs-only push, check the next full run.
- **Small packages** (server, MCP, vault-core, supporter, webhook) share one job `packages` (steps keyed by the pre-check flags): every extra job waits for a free runner.
- **Dev-Preview** is built next to the tests (`stage: build`) and published (`stage: publish`) when the gate is green: gitleaks, licences, static, unit, E2E smoke and the native shell (`rust`). Everything else (rest E2E, sync E2E + seed, small packages, extension, local model, docs checks) runs next to the build and after the publish; a red one turns the run red but the preview is out already. Gitleaks runs next to the builds, not before them, and the publish needs it. The signed build artifacts of a red commit stay in the run for 3 days but are never attached to a release.
- **Windows release cache:** the job builds into `C:/t`, so `CARGO_TARGET_DIR` is set at job level and `rust-cache` gets `cache-directories: C:/t` (it does not follow the variable on its own; own `shared-key` per variant). Releases on `main`/tags only read caches written on `main`: the dry run also runs on `main` pushes, and a manual release run on `main` started right after waits for it (same concurrency group; a tag release runs on its own ref and does not wait; GitHub keeps one pending run per group, so a later push to `main` that touches `web/src-tauri/**` or `web/scripts/**` can replace a manual release that is still pending: do not push to `main` while it waits, or look in Actions and start it again). A skipped CodeQL Rust leg on a PR may show GitHub's note "missing analysis for /language:rust"; that is expected.
- `ci.yml` jobs run side by side: `changes` (pre-check: per-package flags), `secret-scan`, `docs-budget`, `docs-pairs`, `web-static` (version check, format, lint, typecheck, i18n, modules, case), `licences` (lock files only, every code change), `web-unit` (3 vitest shards), `web-e2e` (smoke list, 3 shards, two workers each; everywhere), `web-e2e-rest` (the other tests, 8 shards; full runs only; next to the smoke list, not after it), `packages` (server, MCP, vault-core, supporter + CLI, webhook), `extension`, `e2e-sync`, `e2e-seed` (seed project, 4 jobs: the 12 page walks "every page fits the window" and the other tests, 2 shards each, split with `--grep`/`--grep-invert` so every test runs once; whenever the app E2E runs, so on every PR that can change the web app); browser and its font packages come from `.github/actions/playwright-chromium` (both cached), `rust`, `rust-windows` (native Windows clippy + tests of the shell, `lan-sync`, `disk-scan`, and the release exe size in the job summary; same gate as `rust`), `local-llm`, `stimulus-budget` (blocking, with the ratchet step; below). The job named **Web (lint, types, unit, E2E)** is the aggregate that keeps the old check name; it checks that every part the pre-check asked for succeeded and every other part was skipped: licences, static, unit, E2E smoke, E2E rest, `e2e-seed`, `stimulus-budget`. It is the required context of every merge into `develop`.
- **Documentation-only changes** (everything under `docs/` except `docs/AI-IMPORT*.md` and `docs/user/installation*.md`, plus `CLAUDE.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG.md`, `LICENSE`, issue/PR templates) skip every job except the secret scan and the docs checks (`docs-budget` warns on budgets/links and blocks on images under `docs/`, `docs-pairs` runs `check:readme` and blocks); skipped jobs count as passed. Files that tests read (`README*.md`, the docs above, `contract/`, workflows) always count as code. When a test starts reading another file, add it to `pinned` in the `changes` job. Any doubt (no diff, new branch, error) runs everything.
- **Shards:** tests are split by test, not by file, so a new spec needs no registration for sharding. It runs on plain PRs only if its file name is in `SMOKE_FILES` (`web/playwright.config.ts`), otherwise in full runs only. Locally `npx playwright test --shard=1/6` runs one slice of the full set; `E2E_PROFILE=smoke` runs the PR set. More than two workers per 4-core runner was slower per test and failed under load – add shards, not workers.
- **Caches** (all keyed so that a hit is the normal case): npm per lock file (`setup-node`), Playwright browsers per web lock file, `gitleaks` binary per version, Rust `target` and registry through `Swatinem/rust-cache` (per `Cargo.lock`), Gradle through `setup-java`. Caches are scoped per branch: a pull request restores what `develop` saved, a manual release run on a feature branch starts cold (Android ~9 min instead of ~5 min, Windows ~10 min instead of ~7 min).
- **Cache problems:** a job that is suddenly slow usually missed its cache (look for "cache not found" in the step log). Re-running does not help; changing the lock file or `Cargo.lock` creates a new key. To drop a poisoned cache delete it under Actions → Caches (needs write access), then re-run the job. Never fix a red job by skipping a test or a security step.
- Each job has a `timeout-minutes` so a hang cannot hold a runner for the default six hours.
- Timings before/after: [`docs/perf/BUILD-BASELINE-2026-10-01.md`](../perf/BUILD-BASELINE-2026-10-01.md).

## Stimulus budget and ratchet
Decided with UI audit 2026-11, package 0a-1a ([why](../decisions/meta.md), spec: [PACKAGE-0](../design/ui-audit-2026-11/PACKAGE-0.md)). In force on `develop` since 2026-11-10: script and measurement (PR #627), the maintainer's public key, and the workflow (PR #630): the job `Stimulus budget` blocks, `e2e-seed` runs on every PR that can change the web app, both count for the check `Web`.
- **One-time setup (state 2026-11-10):** done: key pair made with `openssl` only (`openssl genpkey -algorithm ed25519 -aes256 -out ~/.nemo/ratchet.pem`, `openssl pkey -in ~/.nemo/ratchet.pem -pubout`; in Git Bash with `winpty` in front, or the passphrase prompt hangs), its public line is `RATCHET_PUBLIC_KEY` in `web/scripts/ratchet.mjs`; the workflow change is merged (#630; its own run went red on its own hit and green after the label `stimulus-raise` and "Re-run failed jobs", as designed; it was merged by Sven without a signed comment, no console at the time). Open, Sven: (1) rule 7 is in `docs/meta/agents-v3/nemo-merge.json`: it takes effect when the agent is created again from it ([SETUP](../meta/agents-v3/SETUP.md)); (2) once, before the first real use: one run of `--pr` in the `nemo-merge` sandbox and one dry run of the signing command below (`gh auth login` once on your machine); (3) the local deny rules for chats: `Read(~/.nemo/**)` and the commands that set the label `stimulus-raise` (hygiene).
- **Will my PR need Sven?** Yes if it changes: a workflow or action, `web/*.config.*` (also a new entry in `SMOKE_FILES`), `tsconfig*`, `eslint.*`, `web/.env*`, `web/package.json` beyond `version` and plain-range dependencies, `vitest.setup.ts`, `eslint-rules/**`, the guard tools under `scripts/` (`check*.mjs`, `ratchet.*`, `lib/stimulusBudget.ts` …), an entry in `scripts/baselines/*.json`, `e2e/helpers.ts` or another existing helper the guards import (a new helper in a new file is free only while no protected spec or test imports it, or under `e2e/seed/**`), the changelog and precache tooling under `scripts/lib/` that `vite.config.ts` imports, an existing guard spec or test beyond appended cases (nothing at all in the measuring specs `stimulus.spec.ts` and `first-row.spec.ts`), a new nested `package.json`, anything under `node_modules`, a new e2e spec named like a protected one, or if it raises a measured value (more seed rows are free as rows but can raise page values) or removes seed rows. A new module is measured by itself and its own page keys are free, but its widget and library tile raise the overview and library values (frames and shadows are counted exactly): expect a hit. Then: name every hit in the PR text and wait; never set the label yourself.
- **What is measured:** `npm run check:stimulus` (in `web/`) runs `e2e/screenshots/stimulus.spec.ts` (measuring only, writes `inventory.json`) on the seeded build: every parameter-free module route, the library, the overview calm and detailed and a few sub-pages (`e2e/screenshots/stimulusPages.ts` reads the routes from the manifests, so a new module is measured without an edit there), at 1920×1080 (`d1920--`, desktop platform faked) and 412×915 (`p412--`, without the desktop-only modules), all modules and previews on. Per page: `height`, `buttons`, `links`, `icons`, `firstScreenActions`, `borders` (frame on all four sides, ≥ 40×24 px), `shadows` (blurred or offset, not floating things, not rings), `surfaceLanguages` (frames and shadows: 0–2), `colouredAboveFold`, `signatureBlocks`. Formulas: `measurePage()` in `scripts/lib/stimulusBudget.ts` (one fixture test each); runner: `scripts/check-stimulus.mjs`; budget: `e2e/stimulus-budget.json`.
- **Strict on both sides:** a value above its band is over budget, a value below it is red too ("lower the baseline"). Band: height ±10 % or ±50 px (the larger), counts ±10 % but at least ±1; `borders`, `shadows`, `surfaceLanguages`, `signatureBlocks` exact; `colouredAboveFold` ±1. Also red: a page in the budget that was not measured, a measured page without a budget, a missing metric key.
- **Signature blocks:** the only framed blocks that stay are marked with `signatureBlock="…"` on the row (`data-signature-block`), listed in `scripts/baselines/signature-blocks.json`. A marked element is at most 480 × 320 px and frames nothing inside (except the count the file writes down for it: `pantry-label` 1, its amount stepper, until package 0b-5); its own frame is not counted in `borders`, everything inside it is.
- **Lowering a budget (the only way):** the job `Stimulus budget` prints the measured values of its run into the job summary, in the form of the budget file. Take those numbers into `e2e/stimulus-budget.json`. Never commit a local measurement: local and CI values differ and several bands are exact. A new page: push, then copy only that page's keys from the job summary. `npm run stimulus:baseline` rewrites every entry with local numbers: use it to look, not to commit.
- **Seed rows:** all values are measured on the test data, so `scripts/baselines/seed-rows.json` holds the rows per table at `scale: 'medium'` (`scripts/lib/seedRows.test.ts`). More rows: `UPDATE_SEED_ROWS=1 npx vitest run scripts/lib/seedRows.test.ts` and commit. Fewer rows are a ratchet hit.
- **Baselines that only shrink (package 0a-1b; `segmented-views` since 0b-1):** `scripts/baselines/{max-width,grouped-list,own-h1,css-motion,segmented-views}.json` hold today's hits per file, counted by `scripts/lib/{maxWidth,groupedList,ownH1,cssMotion,segmentedViews}.ts` (`grouped-list` reads every component file of a module, not only `routes/`; `css-motion` counts transitions and `@keyframes` in module stylesheets that move something else than `transform`/`opacity`; `segmented-views` counts a `Segmented` in the `views` slot of a page header: the views of a page are `Tabs`) and held by the test of the same name in `web-unit`, strict on both sides (a new hit is red, a removed one is red until the file is lowered). Lower: `UPDATE_BASELINES=1 npx vitest run scripts/lib/<name>.test.ts` and commit; that command also writes a raised number, which is a ratchet hit. What counts as a hit stands at the top of each counter. Next to them, without a baseline: `motionSource` (no `.animate(` / `startViewTransition` outside a motion helper; a helper lies in `src/ui/motion*` **and** is named in `MOTION_HELPERS` of `motionSource.test.ts`, so a new one is a ratchet hit), `src/layout/pageTitle.test.tsx` (one `PageTitle` h1 per module route, in the head) and the ESLint blocks against a fixed `'de-DE'` (`eslint-rules/no-fixed-locale.js`) and against `autoFocus` in JSX (`eslint-rules/no-autofocus.js`; use `data-autofocus`).
- **Ratchet (`web/scripts/ratchet.mjs`):** one file, `node:*` only, reads history with `git show` and never runs a file of the PR. Compared between merge base and head, by meaning, not "file changed":

| What | Hit | Free |
| --- | --- | --- |
| `e2e/stimulus-budget.json` | raised value or tolerance, changed `version`, removed page or metric, new page | lowering; a new page whose route the same PR adds to a `modules/<id>/manifest.ts`; a new metric key |
| `scripts/baselines/*.json` | raised number, new key or list entry, changed text, deleted file | lowering, a new file |
| `scripts/baselines/seed-rows.json` | lowered or removed count | more rows |
| `scripts/baselines/signature-blocks.json` | every new, changed or removed entry (the hit line carries the entry, like the line of a new budget page carries its values: rewriting it after an approval changes the hash) | – |
| `web/package.json`, root `package.json` | every change in `scripts` and in any other field (`type`, `overrides`, …); a dependency whose source is not a plain version range (`npm:` alias, path, URL, git) | `version`; dependencies as plain version ranges (what Dependabot writes) |
| protected files (list `PROTECTED` in the script: workflows and actions, `web/*.config.*`, `tsconfig*`/`jsconfig*` (also nested ones), `eslint.*`, `eslint-rules/**`, `web/.env*`, any `.npmrc`, the script and its test, the guard tools under `scripts/`, `e2e/helpers.ts`, `e2e/seed/**`, the promise specs and tests, and every helper under `e2e/`, `scripts/`, `__tests__/` they import) | every change or deletion; a new file; a new `.skip/.fixme/.todo/.only`, `testIgnore`, `exclude` | new files under `e2e/seed/**`, `src/**/*.test.*`, `scripts/lib/*.test.ts` (never free: new workflows, actions, `web/*.config.*`, `web/.env*`); plain top-level `test('title', async (…) => { … })`/`it(…)` calls appended at the end of a protected test file (no `describe`, `each`, options object, new `import`; a regex directly behind `if/while/for/with (…)` and a `vi.mock`-family call (`mock`, `unmock`, `hoisted`, `doMock`, `doUnmock`, `importActual`, `importMock`) are refused) |

  A new file that a resolver would pick instead of a protected one (`helpers.js` next to `helpers.ts`, `helpers/index.ts`) is a hit everywhere, as is anything under a `node_modules` folder, a new nested `package.json`, and a new spec with the file name of a protected one. Nothing may be appended to the measuring specs (`stimulus.spec.ts`, `first-row.spec.ts`). What `vite.config.ts` imports (changelog and precache tooling under `scripts/lib/`) runs in the guard builds and is protected too. Product code under `web/src/**` is never protected. Known limits (not checked): the reader that decides whether an appended test is "plain" is hand-written and reads JavaScript without a parser (it runs as a single file without dependencies); five review rounds each found and closed a way to hide a top-level statement in it, so treat an appended test in a protected file as reviewed text, not as proven harmless; `package-lock.json` sources, and what a new spec or an appended test does at run time to the worker it shares with other guards (patching shared objects); reviewers look at both. **Workflow changes are therefore hits repo-wide**: Dependabot PRs for actions and release-workflow changes need Sven's approval like any other hit; Dependabot npm bumps and version bumps do not (plain version ranges, no other field).
- **In CI (feedback, not proof):** the last step of the job `Stimulus budget` runs `node scripts/ratchet.mjs --base <merge base> --head <PR head>` and writes the hit table into the job summary. No hits: green without a label. Hits: red, unless the label `stimulus-raise` is on the PR right now. The job and `e2e-seed` are parts of the aggregate check **Web (lint, types, unit, E2E)**. `ci.yml` does not start on `labeled`: after setting the label use "Re-run failed jobs". No ratchet step on pushes, nightly and `full-ci` dispatches (no PR, no label).
- **At the merge (the trust root):** `nemo-merge` rule 7, wording of the spec (its file reference left out): "vor dem Merge in `/workspace/wt-merge`: `git fetch origin develop <head-sha> && git show origin/develop:web/scripts/ratchet.mjs > /tmp/ratchet.mjs && NODE_USE_ENV_PROXY=1 node /tmp/ratchet.mjs --pr <n> --head <head-sha>`; Exit-Code ≠ 0 → kein Merge, die Ausgabe in den Merge-Kommentar; gemergt wird genau dieser `<head-sha>` als `expectedHeadSha`, das Skript endet mit Exit ≠ 0, wenn der Live-Head davon abweicht – keine Lücke zwischen Prüfung und Merge". The same holds for **every** merger ([RULES](../RULES.md)): no merge into `develop` while the `develop` version of `ratchet.mjs --pr` exits ≠ 0. `--pr` needs: the PR is open against `develop` and no other open PR has the same head; exactly one merge base; live head = `--head`; the check run **Web (lint, types, unit, E2E)** of the `pull_request` run of `ci.yml` on that head is `success` (required context; the run must name this PR with base `develop`, so a PR from a fork never passes: Sven pushes its branch into the repo and opens the PR from there; read with `filter=latest`, commit statuses are never read); and no hits, or an approval for exactly this hit table.
- **The approval is a signature, not the label.** A PR comment whose whole text is `stimulus-raise SGNemo/schweizer-taschenmesser#<n> <hash> <signature>`: `<hash>` = SHA-256 over the sorted hit lines, `<signature>` = Ed25519 over `stimulus-raise SGNemo/schweizer-taschenmesser#<n> <hash>`, checked against `RATCHET_PUBLIC_KEY` in the `develop` version of the script. Author, edits and the label play no part; every validly signed comment for the current hash counts. A push that changes the hits (also a second change of an approved file) needs a new comment; merging `develop` in does not, as long as `develop` did not touch a hit file. Empty key = nothing is mergeable.
- **Sven's steps on a hit PR** (Git Bash; always the `develop` version, never the PR's; no repo script ever touches the key):

```bash
git fetch origin develop && git show origin/develop:web/scripts/ratchet.mjs > /tmp/ratchet.mjs && GITHUB_TOKEN=$(gh auth token) node /tmp/ratchet.mjs --pr <n>
```

```bash
printf '%s' 'stimulus-raise SGNemo/schweizer-taschenmesser#<n> <hash>' > /tmp/ratchet-msg.txt && openssl pkeyutl -sign -rawin -inkey ~/.nemo/ratchet.pem -in /tmp/ratchet-msg.txt -out /tmp/ratchet-sig.bin && openssl base64 -A -in /tmp/ratchet-sig.bin; echo
```

  Run both in your clone of the repo. The first prints the hit table, the hash, the message and the second command ready to copy; at this point `Not mergeable yet` (no signature, Web check red) is expected. The second asks for the passphrase and prints the signature (message and signature go through files: OpenSSL 3.0 cannot sign Ed25519 from a pipe; if it hangs at the passphrase in Git Bash, put `winpty` in front of `openssl pkeyutl`). Post message + space + signature as one comment, set the label `stimulus-raise` (CI only), "Re-run failed jobs"; when the run is green, the first command must end with `Mergeable: head …`. After a push with new hits: the same again. The PR text names every hit.
- **Key:** made and used with `openssl` only (commands under "One-time setup"), kept like the updater key (never lost, never committed); local chats get the deny rule `Read(~/.nemo/**)`. A new public key changes `ratchet.mjs` (a hit): that one PR Sven merges himself after his own review, with a decision bullet (the named exception to rule 7). Key lost: make a new pair and do the same; open hit PRs then need a new signed comment.
- **Agents:** never set the label `stimulus-raise` and never post an approval line; say every hit in the PR text and wait.

## Dev-Preview
- **What:** after every green push to `develop` that changed more than docs, `ci.yml` calls `dev-preview.yml`: gitleaks → version → signed Windows exe + Android APK (same signing, audit and keystore-cleanup steps as `release.yml`, plus `verify-sig.mjs` and `apksigner verify`) → rolling **pre-release** `dev-preview` (`--prerelease --latest=false`, assets replaced, tag moved to the commit, `dev-latest.json` uploaded last, link check, `releases/latest` compared before/after). A failed run publishes nothing; the previous preview stays.
- **Never lost:** whether a push to `develop` "changed code" is judged over everything since the last *published* preview (the release name ends in `+<sha7>`, read with `gh release view dev-preview` in the `changes` job), not over the single push. A code merge whose run was replaced by a newer push (GitHub keeps one pending run per group and replaces it, never a running one) is built by the next run, whatever that push contained. Pushes that only touch `scribble/` start no run at all (`paths-ignore`). If `gh` fails or the name cannot be read, the old rule (this push only) applies. A re-run for the commit that is already published rebuilds (the doubt rule), so a re-run never hides a red check.
- **Files:** `Nemo-Portable-dev.exe(.sig)`, `Nemo-dev.apk(.sha256)`, `dev-latest.json` under `…/releases/download/dev-preview/`. List: `DEV_ASSETS` in `web/scripts/lib/devPreview.ts`.
- **Version:** `<next stable>-dev.<commit count of HEAD>` (`node scripts/dev-preview.mjs version`; `full` adds `+<sha7>`), only in the build, `package.json` is never changed. Android `versionCode` = minutes since the epoch (own package id, so no relation to the stable codes).
- **Install:** download the exe/APK from the release page or the README link. It is a separate app ("Nemo Dev", identifier `io.github.sgnemo.taschenmesser.dev`, own data, own Windows Credential Manager entries, portable folder `data-dev`); bring data over via sync or backup.
- **Dev channel:** Dev builds (`VITE_RELEASE_CHANNEL=dev`, set only by the workflow) always follow `dev-latest.json` (Settings → App updates shows "Dev-Preview"); a pre-update backup is made as for stable. Stable builds cannot select the channel and ignore the `dev-preview` release (not SemVer).
- **Back to stable:** install/keep the stable app; the Dev app can simply be uninstalled/deleted.
- **Trigger manually:** Actions → Dev-Preview → Run workflow (`artifact-only`, `dev-preview-test` = throw-away pre-release `dev-preview-test`, or `dev-preview`; both signed targets only from `develop`). Manual runs work once the workflow file is on `main` (GitHub only offers dispatch for the default branch's workflows); otherwise push to `develop`. Delete a test release with `gh release delete dev-preview-test --cleanup-tag`.
- **Cleanup:** the rolling release keeps only the latest state; workflow artifacts expire after 3 days.
