# CI and Dev-Preview

CI jobs, caches, sharding; rolling Dev-Preview build. Index: [HOW-TO](../HOW-TO.md). Commands run in `web/` unless stated.

## CI layout, caches and sharding
- **Which checks run when:** table in [HOW-TO](../HOW-TO.md). The `changes` job sets per-package flags; plain PR = smoke E2E (`E2E_PROFILE=smoke`, file list `SMOKE_FILES` in `web/playwright.config.ts`: add a file there when it guards a critical path), full run = push `develop`/`main`, `nightly.yml`, label `full-ci` (`full-ci.yml` dispatches `ci.yml`), manual run. `E2E_SEED=0` leaves out the seed project and its second web server (it runs in the sync job of full runs). Unit tests: `vitest --shard=i/3`.
- **Concurrency:** a newer push to a PR cancels the older run of that PR; runs for `develop`, `main` and dispatches are never cancelled, they queue (one running, one pending per ref; a newer push replaces a *pending* run). A run that starts therefore finishes and the Dev-Preview of that commit is built and published. A commit that is replaced while pending gets no run of its own: its code is covered by the next run only if that run's push range includes it, so when a code push is replaced by a docs-only push, check the next full run.
- **Small packages** (server, MCP, vault-core, supporter, webhook) share one job `packages` (steps keyed by the pre-check flags): every extra job waits for a free runner.
- **Dev-Preview** is built next to the tests (`stage: build`) and published (`stage: publish`) when the gate is green: gitleaks, licences, static, unit, E2E smoke and the native shell (`rust`). Everything else (rest E2E, sync E2E + seed, small packages, extension, local model, docs checks) runs next to the build and after the publish; a red one turns the run red but the preview is out already. Gitleaks runs next to the builds, not before them, and the publish needs it. The signed build artifacts of a red commit stay in the run for 3 days but are never attached to a release.
- **Windows release cache:** the job builds into `C:/t`, so `CARGO_TARGET_DIR` is set at job level and `rust-cache` gets `cache-directories: C:/t` (it does not follow the variable on its own; own `shared-key` per variant). Releases on `main`/tags only read caches written on `main`: the dry run also runs on `main` pushes, and a manual release run on `main` started right after waits for it (same concurrency group; a tag release runs on its own ref and does not wait; GitHub keeps one pending run per group, so a later push to `main` that touches `web/src-tauri/**` or `web/scripts/**` can replace a manual release that is still pending: do not push to `main` while it waits, or look in Actions and start it again). A skipped CodeQL Rust leg on a PR may show GitHub's note "missing analysis for /language:rust"; that is expected.
- `ci.yml` jobs run side by side: `changes` (pre-check: per-package flags), `secret-scan`, `docs-budget`, `docs-pairs`, `web-static` (version check, format, lint, typecheck, i18n, modules, case), `licences` (lock files only, every code change), `web-unit` (3 vitest shards), `web-e2e` (smoke list, 3 shards, two workers each; everywhere), `web-e2e-rest` (the other tests, 8 shards; full runs only; next to the smoke list, not after it), `packages` (server, MCP, vault-core, supporter + CLI, webhook), `extension`, `e2e-sync`, `e2e-seed` (seed project, 2 shards, full runs only); browser and its font packages come from `.github/actions/playwright-chromium` (both cached), `rust`, `rust-windows` (native Windows clippy + tests of the shell, `lan-sync`, `disk-scan`, and the release exe size in the job summary; same gate as `rust`), `local-llm`, `stimulus-budget` (warning). The job named **Web (lint, types, unit, E2E)** is the aggregate that keeps the old check name; it checks that every part the pre-check asked for succeeded and every other part was skipped.
- **Documentation-only changes** (everything under `docs/` except `docs/AI-IMPORT*.md` and `docs/user/installation*.md`, plus `CLAUDE.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG.md`, `LICENSE`, issue/PR templates) skip every job except the secret scan and the docs checks (`docs-budget` warns, `docs-pairs` runs `check:readme` and blocks); skipped jobs count as passed. Files that tests read (`README*.md`, the docs above, `contract/`, workflows) always count as code. When a test starts reading another file, add it to `pinned` in the `changes` job. Any doubt (no diff, new branch, error) runs everything.
- **Shards:** tests are split by test, not by file, so a new spec needs no registration for sharding. It runs on plain PRs only if its file name is in `SMOKE_FILES` (`web/playwright.config.ts`), otherwise in full runs only. Locally `npx playwright test --shard=1/6` runs one slice of the full set; `E2E_PROFILE=smoke` runs the PR set. More than two workers per 4-core runner was slower per test and failed under load – add shards, not workers.
- **Caches** (all keyed so that a hit is the normal case): npm per lock file (`setup-node`), Playwright browsers per web lock file, `gitleaks` binary per version, Rust `target` and registry through `Swatinem/rust-cache` (per `Cargo.lock`), Gradle through `setup-java`. Caches are scoped per branch: a pull request restores what `develop` saved, a manual release run on a feature branch starts cold (Android ~9 min instead of ~5 min, Windows ~10 min instead of ~7 min).
- **Cache problems:** a job that is suddenly slow usually missed its cache (look for "cache not found" in the step log). Re-running does not help; changing the lock file or `Cargo.lock` creates a new key. To drop a poisoned cache delete it under Actions → Caches (needs write access), then re-run the job. Never fix a red job by skipping a test or a security step.
- Each job has a `timeout-minutes` so a hang cannot hold a runner for the default six hours.
- Timings before/after: [`docs/perf/BUILD-BASELINE-2026-10-01.md`](../perf/BUILD-BASELINE-2026-10-01.md).

## Stimulus budget (warnings only)
- **What:** `npm run check:stimulus` (in `web/`) runs `e2e/screenshots/stimulus.spec.ts` (measuring only, writes `inventory.json`) on the seeded build and compares per page × viewport (phone, desktop) page height, buttons, links, icons and actions on the first screen with `e2e/stimulus-budget.json`. Logic: `scripts/lib/stimulusBudget.ts` (unit-tested); runner: `scripts/check-stimulus.mjs`.
- **Tolerance:** height +10 % or +50 px (the larger), counts +10 % but at least +1. Over budget → list `page · value · budget → measured`, exit 1. A page that is in the budget but not measured, or measured but not in the budget, is a note only.
- **Intended change** (a focus package that folds or adds things): `npm run stimulus:baseline` rewrites the budget (about 1 min); commit `stimulus-budget.json` and name the numbers in the PR. Improvements are never flagged but the budget only tightens when someone re-baselines.
- **CI:** job `Stimulus budget (warnings only)` in `ci.yml` next to `docs-budget`, `continue-on-error: true`, skipped on documentation-only changes (`changes`). Warning only so parallel chats are not blocked ([why](../decisions/meta.md)). `STIMULUS_SHOTS=0` skips the screenshots (set by the runner).

## Bundle budget (warnings only)
- Step `Bundle budget (warnings only)` in E2E shard 1: the E2E build sets `VITE_BUNDLE_REPORT=1`, then `node scripts/check-bundle.mjs --dir dist` compares critical path and precache with `web/scripts/bundle-budget.json` (+5 %), `continue-on-error: true`, no extra build. Locally: `npm run check:bundle`; numbers and rebaseline: [`docs/perf/COLD-START-2026-10.md`](../perf/COLD-START-2026-10.md).

## Dev-Preview
- **What:** after every green push to `develop` that changed more than docs, `ci.yml` calls `dev-preview.yml`: gitleaks → version → signed Windows exe + Android APK (same signing, audit and keystore-cleanup steps as `release.yml`, plus `verify-sig.mjs` and `apksigner verify`) → rolling **pre-release** `dev-preview` (`--prerelease --latest=false`, assets replaced, tag moved to the commit, `dev-latest.json` uploaded last, link check, `releases/latest` compared before/after). A failed run publishes nothing; the previous preview stays.
- **Never lost:** whether a push to `develop` "changed code" is judged over everything since the last *published* preview (the release name ends in `+<sha7>`, read with `gh release view dev-preview` in the `changes` job), not over the single push. A code merge whose run was replaced by a newer push (GitHub keeps one pending run per group and replaces it, never a running one) is built by the next run, whatever that push contained. Pushes that only touch `scribble/` start no run at all (`paths-ignore`). If `gh` fails or the name cannot be read, the old rule (this push only) applies. A re-run for the commit that is already published rebuilds (the doubt rule), so a re-run never hides a red check.
- **Files:** `Nemo-Portable-dev.exe(.sig)`, `Nemo-dev.apk(.sha256)`, `dev-latest.json` under `…/releases/download/dev-preview/`. List: `DEV_ASSETS` in `web/scripts/lib/devPreview.ts`.
- **Version:** `<next stable>-dev.<commit count of HEAD>` (`node scripts/dev-preview.mjs version`; `full` adds `+<sha7>`), only in the build, `package.json` is never changed. Android `versionCode` = minutes since the epoch (own package id, so no relation to the stable codes).
- **Install:** download the exe/APK from the release page or the README link. It is a separate app ("Nemo Dev", identifier `io.github.sgnemo.taschenmesser.dev`, own data, own Windows Credential Manager entries, portable folder `data-dev`); bring data over via sync or backup.
- **Dev channel:** Dev builds (`VITE_RELEASE_CHANNEL=dev`, set only by the workflow) always follow `dev-latest.json` (Settings → App updates shows "Dev-Preview"); a pre-update backup is made as for stable. Stable builds cannot select the channel and ignore the `dev-preview` release (not SemVer).
- **Back to stable:** install/keep the stable app; the Dev app can simply be uninstalled/deleted.
- **Trigger manually:** Actions → Dev-Preview → Run workflow (`artifact-only`, `dev-preview-test` = throw-away pre-release `dev-preview-test`, or `dev-preview`; both signed targets only from `develop`). Manual runs work once the workflow file is on `main` (GitHub only offers dispatch for the default branch's workflows); otherwise push to `develop`. Delete a test release with `gh release delete dev-preview-test --cleanup-tag`.
- **Cleanup:** the rolling release keeps only the latest state; workflow artifacts expire after 3 days.

## Signing (release.yml; Dev-Preview follows)
- **Keys live in GitHub Environments, not repo secrets:** `release-signing` (tags `v*.*.*` and `main` only; the six stable secrets), `site-hook` (same refs; `CF_PAGES_DEPLOY_HOOK`). Sven creates them in Settings; agents never do.
- **Jobs:** `windows`/`android` build UNSIGNED (no environment, no secret; caches only for dry runs) → `sign` (`environment: release-signing`, only steps written in the workflow: no checkout, no repo script, no `npm ci`, no cache, no third-party action; signer installed with `--ignore-scripts` and pinned integrity `TAURI_CLI_*` in `release.yml` – bump with `@tauri-apps/cli`; the secret-value audit runs here as an inline Node step, because only this job has the values) → `verify` (no key: `verify-sig.mjs`, `apksigner verify`, package id, `audit-release.mjs` patterns and markers) → `release` (`contents: write`, no key) → `website` (`site-hook`).
- **Dry runs never sign** (develop/main pushes, manual run without `version`): artifacts are `*-UNSIGNED`, no environment is requested. Publishing (tag or manual run with `version`) additionally requires the commit to be an ancestor of `main` (`prepare`).
- **Rehearsal without a release:** Actions → Release → Run workflow on `main` with `sign_only` ticked and no `version`: runs `sign` with the real environment, uploads and publishes nothing.
- **Release builds restore no cache** (a poisoned cache entry would end up inside a signed binary); slower Windows build.
- Tripwire test `web/scripts/lib/signingEnvironments.test.ts` scans every workflow and composite action: a signing secret only in a job bound to its own environment (`release-signing`, `site-hook`, later `dev-signing`; any other environment name fails), no bulk/computed `secrets` access, no secret at workflow level, no checkout/cache/repo script/`npx`/artifact execution/third-party action in an environment job. `dev-preview.yml` (only `ANDROID_*` and `TAURI_DEV_*` at repo level; never the stable updater key) and `ci.yml` (only `secrets: inherit`) are on its per-file `TEMPORARY` list until the Dev-Preview PR; a stale entry fails the test. It catches honest mistakes; the real boundary is the environment's ref policy in the settings. The ancestor-of-`main` check in `prepare` is a tripwire too (a tag on a commit with an edited `release.yml` drops it).
