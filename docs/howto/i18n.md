# UI languages – add texts, add a language

Background: runtime in `web/src/core/i18n/` (map: [ARCHITECTURE-MAP](../ARCHITECTURE-MAP.md)), terms in [docs/i18n/GLOSSARY.md](../i18n/GLOSSARY.md), user-facing notes in [docs/i18n/README.md](../i18n/README.md).

## How it works (short)
- `web/src/strings.ts` exports `de` (German source, `as const`) and `t`, a view that reads every key **at access time** through the chain current language → English → German. A switch needs no reload: the catalog loads first, then the app remounts.
- Translations: `web/src/i18n/locales/<lang>/<area>.ts`, one file per top-level key of `de`, typed `Strings['<area>']` (same keys, wording free). They load lazily (dynamic import) together with English as fallback.
- Plurals and values: a text is a function (`(n: number) => …`); use `plural(n, { one, other })` and `formatNumber` from `core/i18n/format` for counts in languages with more forms. Dates, numbers, money, sorting: `core/i18n/format` (`numberFormat`, `formatTimestamp`, `compareText`, `relativeDays` …) and `core/time/dates`, never a fixed `'de-DE'`.
- Small feature bundles can live next to the feature: `defineBundle(de, { en, es, fr, 'pt-BR' })` (`core/i18n/bundle`; `get()` / `use()`).
- Preference: localStorage `tm-lang` (`system` or a language), formats `tm-format` (device-local, not synced). An installation that already had data before languages existed keeps German.

## Add texts ("Neue Texte hinzufügen")
1. Add the German text to `de` in `web/src/strings.ts` (in the right area), read it as `t.<area>.<key>` in code. Never write UI text into components (ESLint `i18n/no-ui-literal`) and never read `t.…` into a module-level constant, registry field or default parameter: registries use getters (`get title() { return t.x.title; }`), otherwise the text stays in the first language (`check:i18n` capture scan).
2. Add the same key to `web/src/i18n/locales/{en,es,fr,pt-BR}/<area>.ts`, translated with the glossary terms (tone: en you, es tú, fr vous, pt-BR você). A new area: `npm run i18n:scaffold -- <lang>` creates missing part files (German copies) and never overwrites existing ones.
3. Run `npm run check:i18n`: missing/extra keys, empty or untranslated sentences, lost `${…}` values, plus the literal and capture scans. A sentence that must stay identical (city names, sample input the German parser reads) goes into `web/src/i18n/same-as-source.json` with a reason in the PR.
4. Brand names, codes, file names, shortcuts and `LÖSCHEN` stay as they are; examples a person types into German-only parsers (quick capture, AI bar, calculator) stay German.

## Add a language ("Neue Sprache hinzufügen")
1. `web/src/core/i18n/lang.ts`: add the code to `LANGS` and its endonym to `LANG_NAMES`; `matchLang` maps system languages by primary subtag (check a regional default if needed).
2. `web/src/core/i18n/catalogs.ts`: add a loader; `core/i18n/format.ts`: add a format region to `FORMAT_REGIONS` and the date-fns locale/patterns in `core/time/dates.ts`.
3. `npm run i18n:scaffold -- <lang>`, translate every part file, add the catalog to `web/src/i18n/catalogs.test.ts` and an empty list to `same-as-source.json`; give `defineBundle` callers the new language (or rely on the English fallback where stated).
4. Native texts: `web/src-tauri/src/texts.rs` (`Lang`, `from_primary`, Windows LANGID, both text functions).
5. Glossary column, the issue template `.github/ISSUE_TEMPLATE/translation.yml`, `docs/i18n/README.md`, and one pass through MANUAL-TESTS "Sprachen".
6. `npm run check:i18n`, `npm test`, `npx playwright test e2e/i18n.spec.ts`.
