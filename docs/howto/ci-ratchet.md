# CI – stimulus ratchet: what is a hit

Part of [CI and Dev-Preview](ci.md) ("Stimulus budget and ratchet"). Commands run in `web/` unless stated.

- **Will my PR need Sven?** Yes if it changes: a workflow or action, `web/*.config.*` (also a new entry in `SMOKE_FILES`), `tsconfig*`, `eslint.*`, `web/.env*`, `web/package.json` beyond `version` and plain-range dependencies, `vitest.setup.ts`, `eslint-rules/**`, the guard tools under `scripts/` (`check*.mjs`, `ratchet.*`, `lib/stimulusBudget.ts` …), an entry in `scripts/baselines/*.json`, `e2e/helpers.ts` or another existing helper the guards import (a new helper in a new file is free only while no protected spec or test imports it, or under `e2e/seed/**`), the changelog and precache tooling under `scripts/lib/` that `vite.config.ts` imports, an existing guard spec or test beyond appended cases (nothing at all in the measuring specs `stimulus.spec.ts` and `first-row.spec.ts`), a new nested `package.json`, anything under `node_modules`, a new e2e spec named like a protected one, or if it raises a measured value (more seed rows are free as rows but can raise page values) or removes seed rows. A new module is measured by itself and its own page keys are free, but its widget and library tile raise the overview and library values (frames and shadows are counted exactly): expect a hit. Then: name every hit in the PR text and wait; never set the label yourself.
- **Ratchet (`web/scripts/ratchet.mjs`):** one file, `node:*` only, reads history with `git show` and never runs a file of the PR. Compared between merge base and head, by meaning, not "file changed":

| What | Hit | Free |
| --- | --- | --- |
| `e2e/stimulus-budget.json` | raised value or tolerance, changed `version`, removed page or metric, new page | lowering; a new page whose route the same PR adds to a `modules/<id>/manifest.ts`; a new metric key |
| `scripts/baselines/*.json` | raised number, new key or list entry, changed text, deleted file | lowering, a new file |
| `scripts/baselines/seed-rows.json` | lowered or removed count | more rows |
| `scripts/baselines/signature-blocks.json` | every new, changed or removed entry (the hit line carries the entry, like the line of a new budget page carries its values: rewriting it after an approval changes the hash) | – |
| `web/package.json`, root `package.json` | every change in `scripts` and in any other field (`type`, `overrides`, …); a dependency whose source is not a plain version range (`npm:` alias, path, URL, git) | `version`; dependencies as plain version ranges (what Dependabot writes) |
| protected files (list `PROTECTED` in the script: workflows and actions, `web/*.config.*`, `tsconfig*`/`jsconfig*` (also nested ones), `eslint.*`, `eslint-rules/**`, `web/.env*`, any `.npmrc`, the script and its test, the guard tools under `scripts/`, `e2e/helpers.ts`, `e2e/seed/**`, the promise specs and tests, and every helper under `e2e/`, `scripts/`, `__tests__/` they import) | every change or deletion; a new file; a new `.skip/.fixme/.todo/.only`, `testIgnore`, `exclude` | new files under `e2e/seed/**`, `src/**/*.test.*`, `scripts/lib/*.test.ts` (never free: new workflows, actions, `web/*.config.*`, `web/.env*`); plain top-level `test('title', async (…) => { … })`/`it(…)` calls appended at the end of a protected test file (no `describe`, `each`, options object, new `import`; a regex directly behind `if/while/for/with (…)` and a `vi.mock`-family call (`mock`, `unmock`, `hoisted`, `doMock`, `doUnmock`, `importActual`, `importMock`) are refused) |

  A new file that a resolver would pick instead of a protected one (`helpers.js` next to `helpers.ts`, `helpers/index.ts`) is a hit everywhere, as is anything under a `node_modules` folder, a new nested `package.json`, and a new spec with the file name of a protected one. Nothing may be appended to the measuring specs (`stimulus.spec.ts`, `first-row.spec.ts`). What `vite.config.ts` imports (changelog and precache tooling under `scripts/lib/`) runs in the guard builds and is protected too. Product code under `web/src/**` is never protected. Known limits (not checked): the reader that decides whether an appended test is "plain" is hand-written and reads JavaScript without a parser (it runs as a single file without dependencies); five review rounds each found and closed a way to hide a top-level statement in it, so treat an appended test in a protected file as reviewed text, not as proven harmless; `package-lock.json` sources, and what a new spec or an appended test does at run time to the worker it shares with other guards (patching shared objects); reviewers look at both. **Workflow changes are therefore hits repo-wide**: Dependabot PRs for actions and release-workflow changes need Sven's approval like any other hit; Dependabot npm bumps and version bumps do not (plain version ranges, no other field).
- **In CI (feedback, not proof):** the last step of the job `Stimulus budget` runs `node scripts/ratchet.mjs --base <merge base> --head <PR head>` and writes the hit table into the job summary. No hits: green without a label. Hits: red, unless the label `stimulus-raise` is on the PR right now. The job and `e2e-seed` are parts of the aggregate check **Web (lint, types, unit, E2E)**. `ci.yml` does not start on `labeled`: after setting the label use "Re-run failed jobs". No ratchet step on pushes, nightly and `full-ci` dispatches (no PR, no label).
